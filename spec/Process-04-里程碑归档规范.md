# 里程碑归档规范

> **状态**：生效（2026-10-03）｜**上位依据**：无——属**工程过程规范**（可逆、单模块、无外部契约，不命中 ADR 判据，见 `spec/Process-03`）。
> **首个实例**：M1 归档，见 `.tao/archive/M1/`（任务书按模块子目录 + `README.md` + 里程碑回顾 `m1-retrospective.md` + 台账快照 `issues-closed.md`）。
> **关键词**：本规范用「**必须**（MUST）／**应当**（SHOULD）／**可以**（MAY）」表达规范性等级。本过程为**一次性历史操作**，无专用机器 checker；验收依赖 §6 的核对命令与 `make check`。

---

## 1. 目的与触发

- **目的**：项目里程碑达成后，把该里程碑的**任务书**与**台账历史**归档，防止 `.tao/tasks/` 无限膨胀、防止历史内容被误读为现行事实。
- **触发时机**：项目里程碑置「达成」后（即该里程碑各模块 `m` 全部置 `里程碑`）。
- **性质**：归档**不删除、不改变历史**——任务书用 `git mv` 保留 rename；台账历史**搬入** archive 的 `README.md`，原文件只留**指针**（内容仍在仓库内，审计链完整）。

## 2. 归档判据（四类，均须**机械可判**）

1. **任务书**：`**项目里程碑**` 字段**恰好等于**该里程碑编号，且状态为终态（`已验证` / `里程碑`）。
   - 过渡期（`M<i>→M<i+1>`）与下一里程碑（`M<i+1>`）的任务**不归档**。
2. **`changelog.md` 条目**：日期 ≤ 该里程碑**达成日**的表行（行首 `| YYYY-MM-DD |`）。
3. **`MEMORY.md` 行**：内容「纯该里程碑」的行（如「M<i> 实现」「M<i> 任务规划」及纯里程碑期的模块状态行）；**混合**了后续里程碑内容的行（如「M1 完成 + M2 过渡」）**不整行归档**，只归档其中纯里程碑部分（必要时人工拆分，不机械切行）。
4. **`issues.yaml` 的 `closed` 项**：`resolved_by` 对应任务**提交日 ≤ 该里程碑达成日**的 `closed` issue（即**里程碑阶段**关闭项）。提取为 archive 的**台账快照**（见 §3/§5）；**达成日之后**（含过渡期 `M<i>→M<i+1>`、由后续任务关闭）的项**不归档**，留在活台账。
   - **判据来源**：`resolved_by` 内嵌任务 ID（如 `QEMU-004t`）；其提交日以 `git log --grep <taskID>` 或该 ID 的侧记日期确定，**不得**凭印象；边界（达成日当天）以「≤ 达成日」为准。
   - **灰区不计**：达成日之后、但属「上一里程碑范围收窄」的关闭项（如 M1 的 `fence` 移出、`rela.si` 删除，均 2026-09-23~30）**不计**里程碑阶段（用户裁定：灰区不算）。

## 3. 落点与结构

```
.tao/archive/<M<i>>/        # 如 M1/、M2/
├── README.md               # 归档说明 + 摘录（见 §4）
├── m<i>-retrospective.md   # 里程碑回顾（如已移入；见 §4/§6）
├── issues-closed.md        # 台账快照：里程碑阶段 closed 项（见 §2.4/§5；可选）
└── <模块>/                 # 任务书按模块子目录（infra/spec/testcases/llvm/qemu/integ/…）
```

- 任务书**必须**用 `git mv` 移动（保留 rename 历史，`git status` 显示 `R` 而非 `A`+`D`）。
- 目录名 `<M<i>>` 与 `.tao/knowledge/milestones.md` 的项目里程碑编号一致。
- archive **可以**承载**台账快照**（如 `issues-closed.md`）与 `README.md` 之外的**补充记录**（如由 `docs/` 移入的 `m<i>-retrospective.md`）——它们与 `README.md` 共同构成该里程碑的完整历史。

## 5. 原台账处理

| 文件 | 动作 |
|---|---|
| `.tao/knowledge/changelog.md` | 移除归档条目；**在表头之上**加一行归档指针（`> **M<i> 归档指针（日期）**：…`）。**不得**放在表内或底部——append-only 下底部会被后续条目埋没，表内会断表 |
| `.tao/knowledge/MEMORY.md` | 移除归档行；在「当前进度」表**内**加一行归档指针（合法表行） |
| `.tao/knowledge/issues.yaml` | 提取「里程碑阶段（≤ 达成日）关闭」的 `closed` 项 → archive 台账快照（如 `issues-closed.md`）；从活台账移除；在文件头注释加指针 |
| `.tao/knowledge/milestones.md` | 里程碑表下方加一行归档注 |
| `.tao/README.md` | 「目录」节补 `archive/<里程碑>/` 约定（**一次性**建立，后续里程碑复用，无需重复改） |

## 6. 验收与纪律

- `make check` **EXIT 0**。
- `git mv` 后 `git status` 显示 `R`（rename）。
- **不误伤并行未提交工作**：只 `git add` 归档相关文件；并行任务书/补丁一律不动（本例曾遇 QEMU FP 并行工作，归档提交只含归档文件）。
- **不与并行任务同树并发**：归档/收尾**应当**避开同一工作树上正在执行的其它任务——并行任务在跑时**暂缓**归档，等其完成/提交后再动。否则**共用文件**的改动（如 `tools/spec/check_scope.py`、`.tao/knowledge/MEMORY.md`）会被**对方的提交**卷走（本例 M1 归档与 `INFRA-032t` 并发，2 处路径修复被卷入 `6e0741b`）。
- 生成的 `README.md` 与改动后的 `changelog.md`/`MEMORY.md`：**无表内空行、无连续空行**——markdown 表格的 `|---|` 后**必须**紧跟数据行；blockquote（`>`）**不得**插在 `|---|` 与数据行之间；文件尾**不得**残留空行。
- 提交**必须**经用户确认（`AGENTS.md`）。

## 7. 教训（M1 归档实录）

1. **表断行**：把归档指针（blockquote）插在 `| --- |` 与数据行之间会**断开表格**；指针须放表头之上（changelog）或做成表内合法行（MEMORY）。
2. **多行 cell**：changelog 存在跨物理行的 cell（行首 `| 2026-` 识别为行首，其余归上一行）；解析/搬运须按「行首正则」分组，勿按物理行切割。
3. **行首/行尾空行**：搬运后须清理每个条目首尾的空行，否则会在表内留下孤立空行。
4. **`\n` 拼接**：用 `"\n".join(段落)` 组装文档时，段落尾的 `\n` 会与 join 的 `\n` 叠加成连续空行；逐行组装（list of lines）更稳。
5. **指针放顶部**：changelog 为 append-only，指针放底部会被后续 `/complete` 追加的条目埋没。
6. **并行同树 → 混提**：归档/收尾若与另一任务在**同一工作树**并发，**共用文件**的改动会被**对方的提交**卷走（本例 `INFRA-032t` 期间 2 处路径修复进了 `6e0741b` / SPEC-089t 的提交）。纪律：并行任务在跑时**暂缓**归档，或等其完成/提交后再动；收尾提交**只 `git add` 本任务文件**（见 §6）。
