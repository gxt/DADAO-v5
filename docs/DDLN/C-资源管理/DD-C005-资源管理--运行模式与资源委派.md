# 资源管理 -- 运行模式与资源委派

**本册要点**

- 4 种模式：`user`/`jail`/`supv`/`hypv`。
- `jail` 是受限用户态，独立 `jmon`。
- `hypv` 用 `cg3`：version/mask/switch/vector/delegation。
- `hypv_cg_reg_deleg`：bit=0 允许 supv；bit3 固定 1。
- 委派 vs cfx mask：两层闸门。
- 嵌套：`hmon`/`smon` 分工。

## 1. 为什么有 `jail` 模式？它和 `user` 的差别是什么？

**答：** `jail` 是“受限应用”模式：和 `user` 一样是用户态，但 cfx 权限更紧、异常进 `jmon` 而不是 `umon`；用来跑不完全可信的代码，而不必为它开一个完整 OS。

- **相同**：`user`/`jail` 都是用户态（两位编码 0/1），都不能直接执行特权操作。
- **不同**：`jail` 有独立的 `jmon`、独立的 mask/switch/vector；默认能触发的 cfx 更少。
- **典型用途**：沙箱、受限服务、第三方代码。
- **代价**：多一套 handler 与 mask；软件要区分“普通应用”和“受限应用”。
- **对比**：x86 用 ring 3 + 页表/权限；ARM 用 EL0 + 页表；RISC-V 用 U-mode + PMP/页表；MIPS kernel/user；SPARC/ PowerPC 没有独立的“受限用户态”，靠 MMU/权限位。

## 2. 为什么 `hypv` 用 `cg3`，而不是另设一组 CSR？

**答：** 因为 `hypv` 只是第四个模式上下文；把它的 version/mask/switch/vector/delegation 放进 `cg3`，可以复用同一套 cfx 寄存器模型，不必为 hypervisor 另造一套 CSR。

- **`cg3` 内容**：`hypv_global_version`、global/instruction masks、`hypv_switch_run_mode`、`hypv_cfx_mask`、`hypv_excp_vector`、`hypv_cg_reg_deleg`。
- **与 `cg0` 对称**：`cg0` 放 `user`/`jail`/`supv` 的同类字段，`cg3` 放 `hypv` 的。
- **好处**：所有 cfx 用同一套 `cg`/`rc` 访问方式；hypervisor 不需要新的指令。
- **对比**：x86 VMX 用 VMCS；ARM EL2 用 `HCR_EL2`/`VTTBR_EL2`；RISC-V H 用 `hstatus`/`hedeleg`；cfx 把这些压进 `cg3`。

## 3. `hypv_cg_reg_deleg` 的位图怎么用？为什么固定 bit3？

**答：** 它是 `cg` 访问授权位图：某位为 0 表示允许 `supv` 访问对应 `cg`；bit3 固定为 1，表示 `cg3`（hypv 自己的组）不向 `supv` 开放。

- **位图**：按 `cg` 编号索引；0=允许、1=禁止；`supv` 访问被禁止的 `cg` → `CFXREG`。
- **bit3 固定 1**：`cg3` 是 hypv 的上下文；不能下放给 supv，否则 supv 能看到/改 hypv 的状态。
- **用途**：hypv 可以把设备类 cfx 的某些 `cg` 下放给 supv，让 guest OS 直接管理设备，而保留 `cg0`/`cg3` 的控制权。
- **对比**：x86 VMCS 的字段授权；ARM `HCR_EL2` 的 trap 位；RISC-V `hedeleg`/`hideleg` 的异常/中断委派。

## 4. 资源委派和 cfx mask 是什么关系？谁先检查？

**答：** 两者是不同层次的闸门：cfx mask 决定“这条 cfx 指令能不能执行”（不通过 → `ILLI`）；委派位图决定“这个 `cg` 能不能被当前模式访问”（不通过 → `CFXREG`）。

- **cfx mask**：global + 指令类型 mask；指令级。
- **委派位图**：`hypv_cg_reg_deleg`；寄存器组级。
- **顺序**：先过 cfx 访问权限，再按委派位图检查 `cg`（具体顺序以实现/规范为准）。
- **为什么分开**：一个管“能不能用这个资源”，一个管“能用资源的哪一部分”。
- **对比**：x86 CPL/IOPL vs VMCS 字段权限；ARM EL vs `HCR_EL2` trap；RISC-V 模式 vs `hedeleg`。

## 5. 嵌套虚拟化时，`hmon` 和 `smon` 怎么分工？

**答：** `hmon` 处理 `hypv` 下的同步异常，`smon` 处理 `supv` 下的同步异常；嵌套时，guest hypervisor 的 trap 进 `hmon`，guest OS 的 trap 进 `smon`，由委派位图决定哪一层看到。

- **hmon**：hypv 的同步异常；只有 hypv 能读写 hmon 的寄存器。
- **smon**：supv 的同步异常；guest OS 的 syscall/缺页等进这里。
- **嵌套**：L0 hypervisor 用 `cg3`/delegation 控制 L1；L1 再用 `smon` 控制 guest OS。
- **代价**：多一层保存/恢复；`excp_prev_*` 只有一级，嵌套要软件保存。
- **对比**：x86 VMX root/non-root + VMCS；ARM EL2/EL1；RISC-V H + S；MIPS/SPARC/PowerPC 的 hypervisor 支持。

## 背景知识

### 术语与概念

- **运行模式**：`user`/`jail`/`supv`/`hypv` 四种权限上下文。
- **资源委派**：把某个 cfx 的某些 `cg` 访问权下放给低一级模式。
- **`hmon`**：hypv 模式下的同步异常处理 cfx。
- **`cg3`**：hypv 模式的通用寄存器组（版本、mask、switch、向量、委派）。
- **嵌套虚拟化**：guest hypervisor 再跑 guest；委派需要多级。

### 对照

**x86-64**：VMX/SVM；root/non-root 模式，VMCS 控制字段与异常注入。

**ARM64**：EL2 hypervisor；`HCR_EL2`、`VTTBR_EL2` 控制 trap 与地址转换。

**RISC-V**：H 扩展；`hstatus`/`hedeleg`/`hideleg` 控制委派。

**MIPS**：kernel/user + 可选 hypervisor 模式；委派靠特权指令。

**SPARC**：trap level + hypervisor 支持；委派靠 trap 表。

**PowerPC**：MSR + hypervisor 位；SPR 委派与 trap。
