# 资源管理 -- TLB 与地址转换维护

**本册要点**

- **没有独立的 TLB 资源**：TLB 属于页表步进 cfx；也没有独立的 TLB 使能位。
- `ptw_enable = 1` 时 TLB 参与查找；`= 0` 时整个转换旁路。
- 匹配键是"虚拟页 + ASID"；全局页跨 ASID 复用。
- 写页表基址、写 ASID、开转换**都不隐含失效 TLB**——必须显式失效。
- A/D 位在 TLB 条目里维护，靠"清/失效/替换"时按位或回写。
- 回写失败报页表错误。
- **I/D 的 TLB 阵列可以分开，但失效命令只有一条、同时作用于两侧**——不引入 I/D 选择位。

## 1. 为什么 TLB 不单独成 cfx？

**答：** 因为 TLB 与页表步进是同一件事的两半：命中就跳过步进，缺失就步进填充；拆成两个 cfx 会让"谁负责异常"变得模糊。

- **归属**：TLB 的失效命令、ASID、地址范围寄存器都在页表 cfx 里。
- **异常归属**：命中与缺失产生的异常都进页表 cfx。
- **没有独立使能**：`ptw_enable` 一个开关同时管转换与 TLB。
- **好处**：软件只需初始化一个 cfx。
- **代价**：页表 cfx 的寄存器表更长。

## 2. 匹配规则是什么？

**答：** 条目的虚拟页必须覆盖访问地址，且全局位为 0 时条目 ASID 要等于当前 ASID；全局位为 1 则跨 ASID 匹配。

- **虚拟页覆盖**：按页大小与对齐比较。
- **ASID 匹配**：全局位为 0 时严格相等。
- **全局页**：软件必须保证它在所有地址空间映射一致。
- **命中**：直接使用条目里的权限与页号，不重读页表。
- **未命中**：走步进；只有全部检查通过才填充。

## 3. 切换进程要做什么？

**答：** 四步：写新 ASID 或新页表基址 → 显式失效 TLB → 打开转换 → 保存/恢复暂存寄存器。

- **写 ASID/基址**：改变地址空间，但不自动失效。
- **显式失效**：否则旧条目仍可能命中。
- **再开转换**：保证失效完成后再启用。
- **暂存寄存器**：进程私有状态，切换时必须存。
- **常见缺陷**：忘了失效，表现为"偶发读到上一个进程的页"。

## 4. A/D 位怎么维护？

**答：** 条目里保存本地 A/D 与挂起位；访问置位；只有在清、失效或替换时才把挂起位按位或回写页表。

- **填充**：拷贝页表的 A/D 到本地，挂起位清零，**不立即回写**。
- **访问**：读/取指置 A，写再置 D，并标记挂起。
- **失败**：缺页或权限失败不更新、不填充。
- **回写**：清/失效/替换时按位或写回，然后清挂起位。
- **失败处理**：回写失败报页表错误。
- **为什么延迟回写**：每次访问都写页表太贵。

## 5. 失效命令有哪些？

**答：** 三种操作（clean / invalid / flush）× 三种范围（全部 / 单地址 / 区间），另有"忽略 ASID"标志。

- **clean**：回写 A/D，保留条目。
- **invalid**：丢弃条目，不回写。
- **flush**：回写后丢弃。
- **范围**：全部、指定虚拟地址、地址区间。
- **忽略 ASID**：让同一操作跨地址空间生效。
- **写即执行**：没有完成状态，软件无法异步等待。

## 6. 回写失败为什么单独报错？

**答：** 因为回写发生在"清理/失效/替换"这类维护动作中，失败意味着页表的 A/D 状态已不可信，必须让软件知道。

- **原因**：页表页不可写、物理地址不可访问。
- **后果**：条目的"是否被访问/修改"信息丢失，换出策略可能出错。
- **处理**：软件收到错误后应修复映射并重做清理。
- **要求**：页表页必须可写。
- **判据**：能否在失败后保证页表状态一致。

## 7. 为什么写基址/ASID/开关不隐含失效？

**答：** 因为"改配置"与"改缓存状态"是两件事：隐含失效会让一次批量配置变成大量隐式操作，代价不可控。

- **显式失效**：软件知道何时需要、失效多大范围。
- **好处**：可批量优化（先改配置，最后一次失效）。
- **代价**：软件漏写就出隐蔽 bug。
- **纪律**：任何地址空间变更都必须跟一次显式失效。
- **判据**：代码里能否指出"这次切换的失效在哪"。

## 8. I/D 的 TLB 要不要分开？失效命令分不分？

**答：阵列分开，接口不分开。**

- **规范依据（先澄清一个常见误解）**：`DADAO-12 §4.5` 与 `contract-tlb` TLB-02 明写「**条目数、组织与替换策略由实现决定**」——规范**没有规定单 TLB**，分 I/D 两表**不构成偏离**。此外规范的 A/D 条目本来就按访问类型区分（「读/取指命中」只置 A，「写命中」置 A/D），与 I/D 分表天然一致。
- **阵列**：每核 I、D 各一张（I 表条目无 D 状态，只维护 A）；这是实现选择，不改变软件看到的语义。
- **接口**：`cfx_ptw_tlb_control` 仍是**一条命令、同时作用于两张表**；**不加 I/D 选择位**。
- **判序**：I 表先、D 表后；跨两表仍按「条目级 + 首错即停、一条指令最多报一处失败」。**这是测试机约定**（规范把组织留给实现，所以顺序也是实现细节；写成约定是为了让 `tests/arch` 的双表矩阵有确定判据）。
- **范围匹配**：`scope=VA` / `range` 对两张表**各自**匹配（同一个 VA 在 I、D 的 PTE 可以不同）。

**为什么不拆接口：**

1. 内核改 PTE 后，I 和 D 都可能缓存旧翻译；**漏清一侧不报错、只留陈旧翻译**，是典型的静默正确性 bug；多清一侧只损失几次重填。
2. 主流 ISA 都是单一失效接口作用于两侧：RISC-V `sfence.vma`（粒度是 VA/ASID）、ARMv8 `TLBI`（VA/ASID/VMID）、x86 `INVLPG`/`INVPCID`、PowerPC `tlbie`。分开的只是**粒度**，不是 I/D。
3. 高性能核普遍有独立 ITLB/DTLB（如 BOOM），但软件仍只有一条失效指令——硬件内部广播即可。

**什么时候才需要"只清一侧"：** 只有在"只改 X 权限、D 侧翻译仍然有效"这类场景才有收益；主流 ISA 都不提供这个粒度。真需要时，在 `tlb_control` 的保留位上加 `side`（`00=两表` 默认、`01=I`、`10=D`）即可，不必新开 cfx/cg。

## 背景知识

### 术语与概念

- **ASID**：地址空间标识，用于区分进程。
- **全局页**：跨 ASID 复用的页。
- **本地 A/D**：TLB 条目里的访问/修改位。
- **挂起位**：待回写到页表的 A/D 标记。
- **失效范围**：全部 / 单地址 / 区间。

### 对照

**TLB 维护**

- **显式失效 + 命令寄存器**：本项目。
- **切换即失效**：简单但代价高。
- **判据**：软件能否控制失效粒度。
