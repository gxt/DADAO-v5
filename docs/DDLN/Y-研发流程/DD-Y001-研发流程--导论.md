# 研发流程 -- 导论

> 状态说明：本册是 Y 系列的**导论**——只讲这套流程在解决什么、六个分册各管哪一段、出问题该查哪里。细则在 Y002–Y007，本册不复述。

**本册要点**

- 主线只有一条：**想法 → 任务 → 实现 → 门控 → 验收 → 沉淀**；每册讲其中一段。
- 规矩不是制度条文：每条都要能回答"没有它会出什么事"。
- 四类根源：**假绿**（看起来通过）、**返工**（做了两遍）、**失控**（不知道在哪一步）、**失忆**（当时为什么这么做查不到）。
- 门控有两半：**何时跑、谁判定** 属本系列；**检查怎么设计才有效** 属测试体系。
- 本系列面向教学团队与维护者，不占正文序号。

## 1. 这套流程在解决什么问题？

**答：** 解决"人多、Agent 多、改动多"时的三件事：**谁在做什么**、**怎么算做完**、**做过的事怎么不丢**。三者缺一，就分别退化成混乱、假绿、失忆。

**主线**（每一段对应一册）：

- 想法 → 任务：把模糊需求变成可验收的任务（Y002）。
- 任务 → 实现：在受控的组件与工区里改（Y004、Y005）。
- 实现 → 证据：门控跑出可复核的结果（Y003）。
- 证据 → 结论：验收判定与状态推进（Y003、Y002）。
- 结论 → 沉淀：文档、决策、归档（Y006、Y007）。

**四个命令对应四个动作**：规划（把想法拆成任务）、下发（把任务交给实现者）、验收（独立复核并收尾）、状态（现在在哪）。除此之外的一切，都是这四步的细节。

**与相邻系列的分工**：

- **测试体系**：管"检查怎么设计"（覆盖、差分、环境）；本系列管"何时跑、谁判定、证据怎么留"。
- **编译工具**：管"怎么构建、补丁怎么写"；本系列管"什么时候必须重装、为什么不能手工拷"。
- **技术各册**：管技术内容；本系列管"改技术内容时要走什么手续"。

## 2. 六个分册各管什么

- **Y002 任务与角色**：任务书自包含、编号与状态机、三角色分离、下发前五项预检、可机械检查的约束。回答"谁做什么、做到哪"。
- **Y003 门控与验收**：三档门控与触发点、可达 FAIL、反例注入、"证据三件套"、独立重跑、模块绿不等于系统对。回答"怎么算做完"。
- **Y004 组件与补丁**：git 基线、补丁树、一文件一补丁、锁 commit、构建树与安装根两个真源、改定义必须重装。回答"改的东西从哪来、改在哪"。
- **Y005 工区与并发**：三类目录、一树一写者、显式路径提交、临时物、长任务脱离、共享文件串行。回答"怎么并行不互相踩"。
- **Y006 文档与知识**：读者三分界、新增文档三问、被引用材料的落点、台账克制、生成物重派生比对。回答"写下来的东西怎么不过期"。
- **Y007 决策与归档**：何时必须记、逐条确认、修订的三种路径、归档只增不改、检查放对层、复盘要产出可执行改动。回答"当时为什么这么做"。

## 3. 实例索引（四类根源）

每个实例在所属册里都是四要素：现象 / 根因 / 规矩 / 机械防。

- **假绿**：验证脚本恒真（Y003）、单模块全绿组合错（Y003）、生成器自检不在门控（Y006）。
- **返工**：子代理异常返回但已落盘（Y002）、验证手段没预检就下发（Y002）、改定义没重装（Y004）、手工拷二进制进安装根（Y004）。
- **失控**：共享树全量暂存（Y005）、长任务会话内等待（Y005）、归档检查放错层被绕过（Y007）。
- **失忆**：引用的材料只在临时区（Y006）、决策未经逐条确认就标已接受（Y007）。

## 4. 出问题该查哪一册

- 门控绿了但缺陷还在 → **Y003**（可达 FAIL、反例注入）。
- 同一个活做了两遍、或验收标准被改软 → **Y002**（预检、状态机）。
- 行为与源码对不上、换机就不对 → **Y004**（两个真源、重装纪律）。
- 改动互相踩、提交带进别人的文件、长任务丢现场 → **Y005**。
- 文档过期、结论查不到依据、生成物悄悄变了 → **Y006**。
- 争议"当初为什么这么定"、归档缺失 → **Y007**。

## 背景知识

### 术语与概念

- **假绿**：门控通过但缺陷未被发现。
- **可达 FAIL**：存在能让断言失败的输入或改动。
- **反例注入**：人为改坏一处，验证检查确实会红，再还原。
- **单一真源**：同一事实只有一处权威落点，其它地方是指针。
- **安装根**：被工具链与门控读取的安装目录，只由安装动作写入。
- **工作树**：一次检出的完整目录；多个工作树可并行不同分支。
- **提交队列**：把待合并改动串行化，先过测试再入主分支。
- **归档**：历史状态的只读快照，只增不改。

### 对照

**协作形态**（各家的差异集中在三处：评审在哪、合并怎么串行、状态谁记录）：

- **Linux 内核**：邮件列表评审，维护者分层并入，状态靠合并结果推断。
- **LLVM**：拉取请求评审，构建机器人把关，状态在 PR 上。
- **Rust**：RFC + 合并队列，状态机明确。
- **Chromium**：提交队列（先测后合），状态由队列系统记录。
- **Apache 系**：评审后提交，状态在邮件与仓库里。
- **企业流水线**：工单 + 预提交检查 + 发布门禁，状态由系统统一记录。
- **共同点**：提交前有独立把关，状态可被别人读到。
