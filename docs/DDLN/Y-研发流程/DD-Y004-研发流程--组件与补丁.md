# 研发流程 -- 组件与补丁

**本册要点**

- 组件源必须是 **git 基线**：能 diff、能定位到行，才能排障与回滚。
- 本地改动做成**补丁树**（一文件一补丁），而不是长期 fork。
- 锁 **commit**，不锁 tag / branch：前者不可变，后两者会移动。
- **两个真源**是万恶之源：构建树与安装根只能有一个写入路径。
- 改了"定义"（描述文件、生成规则）必须**重新安装**，否则门控读的是旧产物。
- 例外操作（手工拷文件）要留理由并对账，否则等于给门控埋雷。

## 1. 为什么组件源必须是 git 基线，而不是 tarball？

**答：** 因为排障时需要"哪一行改了"这一级信息：tarball 只告诉你"是这一版"，git 能给出 diff、作者、时间与上下文。回滚与二分定位也只有在基线可读时才成立。

- **tarball 的用途**：下载原件、校验物；**不能**当组件源（无法 diff、无法二分定位）。
- **裸仓库 + 工作检出**：裸仓库供多源管理，检出目录供构建；两者分离，检出可随时重建。
- **为什么强调"可 diff"**：补丁失效、行为变化、上游改动冲突，都要靠 diff 判断影响面。
- **代价**：目录更大、获取更慢；换来的是可追溯。

**各家做法**：

- **Linux 发行版**：源码包 + 补丁系列，源码包本身来自上游仓库快照。
- **嵌入式构建系统**：拉 git 提交 + 补丁列表，缓存下载件。
- **LLVM / GCC**：上游仓库直接检出，本地改动用补丁或分支。
- **Rust / Go**：以包注册表版本为主，源码级改动少见。
- **商业 EDA**：厂商 tarball + 内部补丁包，可追溯性依赖厂商。

**是统一标准吗**：不是；但"能 diff"是排障的最低要求。

## 2. 为什么用补丁树，而不是长期 fork？

**答：** 因为 fork 一旦分叉，每次上游更新都要人工合并整棵分支；补丁树把改动压成可重放的序列，冲突只落在具体文件上，且能机械校验"每个补丁都还在"。

- **补丁树的形态**：目录结构对应源码树，一文件一补丁，按固定顺序应用。
- **好处**：改动边界清晰、可逐条审查、可逐条丢弃、可机械重放。
- **代价**：上游重构会让补丁失效，需要重新生成；顺序成为隐式依赖。
- **什么时候 fork 更合适**：改动覆盖整个组件、或需要长期偏离上游。
- **判据**：改动面小且要跟上游 ⇒ 补丁；改动面大或长期偏离 ⇒ fork。

**各家做法**：

- **Debian / Ubuntu**：补丁系列 + 顺序文件。
- **RPM 系**：规格文件里的补丁列表。
- **Yocto / Buildroot**：补丁文件 + 配方引用。
- **Apple / Android**：整棵分支 fork。
- **RISC-V 生态**：改动拆小后逐步合入上游。

**是统一标准吗**：不是。

## 3. 为什么"一文件一补丁"？

**答：** 因为冲突与审查都以文件为单位：一个补丁动多个文件时，任一文件的上游变化都会让整个补丁失效；一文件一补丁则把失效范围限制在那一处。

- **审查友好**：补丁标题即文件路径，谁改了什么一目了然。
- **重放稳健**：单个文件失败不会连带整组失败。
- **可校验**：能机械检查"源码树里的每个改动都有对应补丁"（补丁树与工作树对账）。
- **反例**：一个巨型补丁，上游改一行就整体无法应用，最后只能手工重做。
- **代价**：补丁数量多，需要顺序与目录规范。

**各家做法**：

- **发行版**：常按功能或按文件组织，两种都有。
- **嵌入式**：倾向按功能组织，便于裁剪。
- **上游项目**：以提交为单位（一次提交可含多文件），但每个提交有明确边界。
- **本研究仓**：一文件一补丁 + 树形目录，便于机械校验。
- **商业 SDK**：常给整体 diff，可读性差。

**是统一标准吗**：不是。

## 4. 为什么锁 commit，而不是 tag 或 branch？

**答：** 因为 tag 可以移动、branch 会前进：今天构建的和明天构建的可能不是同一份代码。commit 哈希是内容寻址，天然不可变。

- **tag 的风险**：可被删除重打，尤其是预发布标签。
- **branch 的风险**：随时前进，"最新"不是一个可复现的点。
- **commit 的好处**：哈希即身份，可复现、可二分、可存档。
- **配套要求**：锁文件要能一键重建（拉取、检出、应用补丁、校验和）。
- **代价**：升级要显式改哈希并重跑验证，不能"跟着最新走"。

**各家做法**：

- **嵌入式**：配方锁 commit 或带校验和的 tarball。
- **Rust / Go**：锁文件锁版本 + 校验和。
- **LLVM / GCC**：以发布分支与发布号为主，构建系统记录版本串。
- **Linux 发行版**：源码包带校验和，快照由发行版保证。
- **本研究仓**：锁 commit，弃用 tag/branch。

**是统一标准吗**：不是。

## 5. 为什么构建树与安装根必须分开，且只由安装动作写？

**答：** 因为"被读取的那份"和"正在被改的那份"如果是同一份，任何构建中途都会让门控读到半成品；如果安装根能被顺手写入，就会出现"构建树已更新、安装根还是旧的"这种假绿。

- **构建树**：源码 + 中间产物；可删、可重建。
- **安装根**：被工具链与门控读取的最终产物；只由安装动作写入。
- **两个真源的症状**：本机好用、换机不对；门控绿但行为没变；产物与源码对不上。
- **例外操作**：确需手工放置文件时，要记录理由并做哈希对账，事后补跑安装流程。
- **与门控的关系**：门控应当打印并校验安装根版本，版本不符直接红。

**各家做法**：

- **CMake / Meson**：构建目录与安装前缀分离，安装是显式动作。
- **发行版打包**：构建在临时根（staging）里完成，再打包安装。
- **嵌入式 SDK**：安装到独立前缀，工具链自带 sysroot。
- **手工开发**：常直接改安装根，问题最难查。
- **本研究仓**：安装根与构建树分离，安装动作唯一。

**是统一标准吗**：部分统一（构建/安装分离是通用惯例）。

## 6. 为什么改"定义"后必须重装？

**答：** 因为生成物（编码表、匹配器、描述文件）由"定义"生成：定义改了而没重新生成并安装，工具链用的还是旧生成物，门控因此读到旧行为，形成假绿。

- **什么算"定义"**：指令描述、寄存器描述、生成规则、构建配置。
- **为什么容易漏**：只跑"构建"不跑"安装"，或安装到了另一个前缀。
- **正确顺序**：改定义 → 重新生成 → 重新构建 → 重新安装 → 再跑门控。
- **验证方式**：门控记录并比对安装根的时间戳/哈希；与构建树不一致即报警。
- **代价**：每次改定义都要多等一轮构建。

**各家做法**：

- **编译器后端**：改描述后必须重新生成并安装，否则测试读旧表。
- **内核**：改配置后必须重新构建（配置即生成输入）。
- **前端工程**：改 schema 后必须重新生成客户端代码。
- **嵌入式**：改设备树后必须重新编译并烧写，否则跑的是旧描述。
- **一般项目**：常出现"改了没生效"，排查成本高。

**是统一标准吗**：不是。

## 7. 实例：改了定义，没重新安装

**现象**：门控全绿，但实际行为没变；手工验证才发现工具链还是旧的。

**根因**：门控读安装根，而安装根没更新——构建树与安装根成了两个真源。

**规矩**：任何影响生成物的改动，必须走"重新生成 → 构建 → 安装"再跑门控。

**机械防**：
- 门控启动时打印安装根版本（哈希或时间戳），与构建树比对，不一致直接红。
- 安装动作结束后做一次"安装根清单对账"，多出或缺失即报警。
- 变更清单里标注"是否影响生成物"，影响则强制走重装步骤。

## 8. 实例：手工把二进制拷进安装根

**现象**：本机一切正常；换台机器或清理后行为不一致，产物与源码对不上，且无法从提交历史复现。

**根因**：绕过了安装动作，安装根里混入了来源不明的文件；构建树里没有对应输入。

**规矩**：安装根只由安装动作写入；确需例外时记录理由、做哈希对账，并事后补跑安装。

**机械防**：
- 安装根清单（路径 + 哈希）与实际文件比对，出现未登记文件即报警。
- 手工操作必须留下记录，并在下一次安装时被覆盖而非累加。
- 清理与重建流程能一键复现安装根，复现不出来即说明有未登记输入。

## 背景知识

### 术语与概念

- **组件基线**：上游仓库 + 精确 commit，作为构建输入。
- **补丁树**：按源码目录组织、一文件一补丁的改动集合。
- **锁文件**：记录每个组件的精确版本与来源。
- **构建树**：源码与中间产物所在的目录，可删可重建。
- **安装根**：被工具链与门控读取的最终产物目录，只由安装动作写入。
- **生成物**：由描述文件或规则生成的源码/表，改定义必须重生成。
- **重放**：按顺序应用补丁，得到与工作树一致的结果。
- **对账**：用清单或哈希比对"应有什么"与"实际有什么"。

### 对照

**组件源形态**

- **git 基线**：可 diff、可二分、可重放。
- **tarball**：只可校验、不可 diff，适合做下载原件。
- **包注册表**：版本 + 校验和，源码级改动能力弱。

**改动承载**

- **补丁树**：改动面小、需跟上游。
- **fork**：改动面大、长期偏离。
- **上游合入**：改动可公开、追求长期维护。

**版本锁定**

- **commit**：不可变。
- **tag**：可移动。
- **branch**：会前进。
- **发布号**：对应区间，需额外记录构建输入。

**构建与安装**

- **分离**：构建树 + 安装前缀（主流做法）。
- **合一**：直接在安装位置构建，问题最难查。
- **多前缀**：交叉编译与多版本并存时常见。
