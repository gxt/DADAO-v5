# 研发流程 -- 决策与归档

**本册要点**

- 决策记录保存的是**被否方案与代价**，这正是重做时最想知道的东西。
- 何时必须记：代价高、跨模块、多方案、涉外部契约、结论要固化、定位性决策。
- 决策条目要**逐条确认**；文档里写的只是提案，未确认不得标"已接受"。
- 已接受的决策要改，走"新增 / 标记被取代 / 经授权就地修订"，不静默改。
- 归档**只增不改**；归档检查放里程碑级，不放秒级门控。
- 复盘回答"哪里判断错了、下次怎么提前发现"，不是写总结报告。

## 1. 什么情况下必须留决策记录？

**答：** 当"选错了代价很大"或"半年后会有人问为什么"时。判据不是"重不重要"，而是"这个选择是否需要向未来解释"。

- **代价高**：返工成本大、影响面广。
- **跨模块**：多个模块要按同一决定对齐。
- **多方案**：存在被否的合理方案，需要说明为什么没选。
- **外部契约**：接口、格式、兼容性承诺，改动会影响别人。
- **结论要固化**：一旦定下就要长期遵守（编码约定、命名、目录结构）。
- **定位性决策**：决定了后续所有设计的方向。
- **不必记**：可逆的小选择、个人实现细节、随手能改的东西。

**各家做法**：

- **Rust / Python**：有明确的自述式流程（RFC、PEP），重要变更必须走。
- **IETF**：标准文档固化为不可变编号。
- **LLVM**：重要设计有专门文档，但无统一编号制度。
- **Linux 内核**：以邮件与提交信息承载，追溯靠归档。
- **硬件团队**：规格变更单 + 影响分析，逐条签核。

**是统一标准吗**：不是；但"高代价 + 多方案"是共同的触发条件。

## 2. 为什么决策要逐条确认？

**答：** 因为一份决策文档里往往混着"已经拍板"和"还在讨论"两类内容；不逐条确认就整体标"已接受"，等于让未定事项借道变成定论。

- **逐条的含义**：每一条独立确认，可以"接受 / 修改 / 拒绝"，不打包。
- **状态区分**：提案 / 已接受 / 被取代 / 已废弃；未确认只能是提案。
- **为什么容易出事**：文档写得很完整时，读者默认"这就是决定"。
- **代价**：逐条确认慢；换来的是"已接受"这三个字可信。
- **配套**：确认记录要能追溯（谁确认、在哪次、原话摘要）。

**各家做法**：

- **RFC / PEP**：有明确的"最终评论期"与接受/拒绝标记。
- **标准组织**：投票与异议记录在案。
- **企业架构评审**：逐条决议 + 责任人。
- **一般团队**：文档写完即当定论，事后争议无裁决依据。
- **本研究仓**：逐条确认后才标"已接受"。

**是统一标准吗**：不是。

## 3. 已接受的决策怎么改？

**答：** 不静默改。三种正规路径：新增一则（并存并说明取代关系）、把旧的标记为"被取代"、或经授权就地修订并留下修订原因。

- **新增**：新决策独立成篇，指向被取代者，历史保留。
- **标记被取代**：旧文档保留正文，状态改为"被取代"，指向新文档。
- **就地修订**：仅在授权下进行，必须写清"改了什么、为什么、谁授权"。
- **为什么不能直接改**：直接改会让"当时的决策依据"消失，后来的读者无法理解历史行为。
- **代价**：文档数量增加；换来的是历史可读。

**各家做法**：

- **IETF**：RFC 不可变，靠新文档更新旧文档。
- **Python**：PEP 有"被取代"状态，编号不复用。
- **Rust**：RFC 状态机包含"被取代"。
- **企业**：版本化文档 + 变更记录。
- **一般项目**：直接改正文，历史丢失。

**是统一标准吗**：不是。

## 4. 为什么归档只增不改？

**答：** 因为归档的用途是"证明当时是什么样"：一旦可改，它就不再是证据，只是另一份会漂移的文档。

- **只增不改**：新快照进新目录，旧快照保持原样。
- **配套**：每个快照带来源与校验信息，保证可核对。
- **为什么不"就地更新"**：更新后无法回答"当时到底是什么样"。
- **代价**：体积增长；换来的是可追溯。
- **例外**：发现快照本身有误（如漏了文件），只能"补一份新快照并注明"，不改旧的。

**各家做法**：

- **标准组织**：发布版本不可变，勘误单独发布。
- **包管理**：版本一旦发布不可覆盖（只能撤回）。
- **企业**：审计日志只追加。
- **一般项目**：直接覆盖，历史不可回溯。
- **本研究仓**：归档快照只读、只增。

**是统一标准吗**：部分统一（"已发布不可变"是软件发布领域的共识）。

## 5. 为什么归档检查要放里程碑级？

**答：** 因为归档检查"低频且重"：每次小改都跑，会让秒级门控变慢，最终被人绕过；而它对应的风险（归档缺失）只在里程碑收口时才要紧。

- **判据**：检查的代价与失效后果决定它该在哪一层。
- **分层**：秒级放结构与冒烟；分钟级放代表集；小时级放全量与归档。
- **被绕过的机制**：门控一慢，人就学会跳过；跳过之后所有门控都失去约束力。
- **配套**：新增检查必须声明层级与依据，否则默认进最慢一层。
- **代价**：问题发现得晚；可接受，因为归档不是每日动作。

**各家做法**：

- **CI 系统**：分层流水线（提交 / 合并 / 夜间 / 发布）。
- **发布工程**：发布前检查清单，平时不跑。
- **审计场景**：季度/年度审计，不逐次。
- **一般项目**：所有检查堆在提交时，最后被整体跳过。
- **本研究仓**：归档检查移到里程碑触发。

**是统一标准吗**：不是。

## 6. 复盘要回答什么？

**答：** 三个问题：判断错在哪一步、当时的信号是什么、下次用什么检查提前发现。写成"经验总结"而没有可执行改动，等于没复盘。

- **判断错在哪**：是信息不足、还是信息足够但被忽略。
- **当时的信号**：哪一个可观测现象其实已经提示了问题。
- **下次的检查**：新增/修改哪条门控或流程，能更早发现。
- **产物**：一条判据（写进教训台账）+ 一条机械检查（进对应层）才算闭环。
- **不写什么**：不写"大家要更仔细"这类无法执行的话。

**各家做法**：

- **SRE 文化**：事后复盘聚焦机制改进，不追责个人。
- **航空/医疗**：事件报告 + 流程修订，强制闭环。
- **制造业**：根因分析 + 标准作业更新。
- **一般团队**：复盘会开完就结束，无落地项。
- **本研究仓**：复盘落判据 + 门控。

**是统一标准吗**：不是；但"复盘必须产出可执行改动"是共同要求。

## 7. 实例：决策未经确认就标"已接受"

**现象**：实现按文档做了，事后负责人说"那一条我没同意"；返工时争议无法裁决，因为文档状态写的是"已接受"。

**根因**：把"写进文档"当成"已决定"；文档里混着提案与定论，却整体标了接受。

**规矩**：每个决策条目逐条确认；未确认只能标"提案"，收尾检查"已接受"必须有确认记录。

**机械防**：
- 决策文件里"已接受"条目必须带确认记录（时间 + 确认人 + 原话摘要）。
- 状态检查：无确认记录的"已接受"直接判为不合规。
- 决策新增时同步登记"哪一条是提案、哪一条已定"。

## 8. 实例：归档检查放进秒级门控

**现象**：每次小改都要等归档检查；为了提速有人开始跳过门控，最后所有检查都被当作"可跳过"。

**根因**：把"低频、重"的检查放进了"高频、轻"的层，代价与触发频率不匹配。

**规矩**：检查按代价分层，低频重检查放里程碑级；新增检查必须声明层级与依据。

**机械防**：
- 门控分层清单记录每个检查的代价级别与触发点。
- 秒级门控有耗时上限，超限即报警（强制迁移）。
- 检查迁移时同步更新触发点文档，避免"两层都跑"或"两层都不跑"。

## 背景知识

### 术语与概念

- **决策记录**：记录选择、理由、被否方案与代价的文档。
- **逐条确认**：每个决策条目独立确认，不打包。
- **被取代**：旧决策失效但保留，指向新决策。
- **归档快照**：某一时刻的只读副本，只增不改。
- **门控分层**：按代价与触发频率划分的检查层级。
- **复盘**：事后分析判断与信号，产出可执行改进。
- **闭环**：判据 + 机械检查同时落地，才算改进完成。

### 对照

**决策载体**

- **RFC / PEP**：编号 + 状态机 + 最终评论期。
- **邮件 + 提交信息**：可检索但无状态。
- **变更单 + 签核**：逐条签核，适合安全关键领域。
- **一般文档**：无状态，易被当定论。

**历史保留**

- **不可变发布**：IETF、包管理、标准组织。
- **可覆盖文档**：多数 wiki 与内部文档。
- **折中**：版本化 + 变更记录。

**复盘落地**

- **强**：事件报告 + 流程修订 + 跟踪验证。
- **中**：复盘会议 + 行动项（常不了了之）。
- **弱**：只写总结。
