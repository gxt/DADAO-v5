# 研发流程 -- 工区与并发

**本册要点**

- 三类目录各司其职：**缓存区**可重建、**工作区**可删、**安装根**受控写入。
- 同一工作树同一时间**只能有一个写者**；要并行就开**独立工作树**。
- 提交必须**显式列路径**，禁"全量暂存"。
- 临时物一律进指定临时目录，**绝不留在仓库**里。
- 长任务**脱离会话**运行，落日志与退出码；不以"看起来跑完了"判定完成。
- 共享文件（构建脚本、清单、共享数据）必须**串行改**。

## 1. 为什么三类目录要分开？

**答：** 因为三类内容的"可删性"与"可信度"不同：缓存区删了能重建，工作区删了只影响当前进度，安装根删了会让门控失效。混在一起时，清理会误删证据，重建会污染读数。

- **缓存区**：裸仓库、下载原件、只读引用；可重建，删了不心疼。
- **工作区**：源码检出、构建产物、日志与证据；可删，但要能重建。
- **安装根**：被工具链与门控读取的最终产物；受控写入，删除要显式。
- **判据**："删掉它，多久能恢复？谁依赖它？"答案不同，目录就不同。
- **反例**：把构建产物放进缓存区 ⇒ 清理缓存时顺手删掉构建状态；把证据放工作区 ⇒ 一次清理丢掉全部留痕。

**各家做法**：

- **LLVM / CMake**：源码树只读，构建目录独立，安装前缀独立。
- **QEMU / Meson**：构建目录完全独立，支持多配置并行。
- **Rust / Cargo**：缓存目录（下载与编译缓存）与目标目录分离。
- **嵌入式构建系统**：下载缓存、构建目录、安装根三处分离。
- **一般项目**：全部堆在源码树里，清理靠人工记忆。

**是统一标准吗**：不是；但"可删性分级"是共同思路。

## 2. 为什么"一个工作树只能一个写者"？

**答：** 因为一次切分支或一次全量暂存会把别人的改动一起带走；而独立工作树让两个写者各自拥有独立的分支、暂存区与工作区，互不干扰。

- **工作树隔离的部分**：当前分支、暂存区、工作区文件。
- **共享的部分**：仓库对象库、钩子、部分配置；所以仍要避免同分支两处检出（版本控制会拒绝）。
- **不可跟踪文件的陷阱**：被忽略的草稿/产物**不会**跟着新工作树过去；若草稿是唯一副本，就必须留在原树。
- **代价**：磁盘与构建缓存翻倍；换环境时容易"两边各跑一半"。

**各家做法**：

- **多工作树**：主流版本控制都支持，适合并行任务与长时间构建。
- **多检出（clone）**：隔离更彻底，代价是同步靠推送/拉取。
- **单一工作树**：靠提交频率与人肉协调，规模一大就冲突。
- **CI 环境**：每次构建全新检出，天然隔离。
- **嵌入式团队**：共享只读缓存 + 每人独立检出。

**是统一标准吗**：不是。

## 3. 为什么提交要显式列路径？

**答：** 因为"全量暂存"会把别人正在改的文件、以及不该入库的产物一起带上；显式列路径等于在提交前做一次"范围声明"，可核对、可审查。

- **纪律**：只暂存本次任务声明的文件；提交前把清单与任务书的"修改文件"逐条对账。
- **差集检查**：暂存列表与声明清单的差集必须为空；非空就停。
- **为什么在共享树上更要紧**：别人的改动一旦被带进你的提交，撤回会牵连他的工作。
- **代价**：每次提交多一步核对；换来的是提交内容与意图一致。

**各家做法**：

- **评审型项目**：提交粒度小、范围明确，评审者按范围核对。
- **单仓大项目**：提交前检查工具会提示"是否包含无关文件"。
- **企业流水线**：按变更集提交，范围由工具推导。
- **个人项目**：常见全量提交，出问题时难以拆分。
- **本研究仓**：显式路径 + 与完成区对账。

**是统一标准吗**：不是。

## 4. 为什么临时物不能留在仓库里？

**答：** 因为仓库的"干净"是很多流程判断的前提：快照对账、残留检查、提交范围核对都假设"多余文件 = 异常"。临时物一多，判断就失真，最后没人再相信 `status`。

- **定义**：临时物 = 过程产物（中间文件、调试输出、一次性脚本）。
- **后果**：对账噪声、误提交风险、清理时误删真实产物的概率上升。
- **正确做法**：统一进指定临时目录，任务结束可整目录清理。
- **例外**：需要长期保留的生成器/脚本，必须落到非易失位置并入库。
- **判据**："换个人拿到仓库，是否需要它？"不需要 ⇒ 不能留在仓库。

**各家做法**：

- **主流项目**：忽略规则覆盖构建产物与编辑器临时文件。
- **严格项目**：提交前检查未跟踪文件，非白名单即拒。
- **企业流水线**：构建在隔离容器内，仓库本身保持干净。
- **一般团队**：靠 `.gitignore` 兜底，偶有漏网。
- **本研究仓**：临时目录固定在仓库外，收尾检查残留。

**是统一标准吗**：不是。

## 5. 为什么长任务要脱离会话？

**答：** 因为等待本身没有价值，而且脆弱：会话可能超时、被中断、被别的操作打断。脱离运行 + 落日志与退出码，能让"完成"变成可离线判定的事实。

- **做法**：后台启动、脱离会话、写日志、结束写退出码文件。
- **判据**：完成 = 退出码文件存在且为 0（或按约定判定），不是"终端里看起来跑完了"。
- **申报**：启动前说明预计耗时与产物位置，避免别人空等。
- **失败处置**：保留日志与退出码，记录重试次数，不以重试掩盖根因。
- **代价**：需要主动查看状态，不能"盯着屏幕等"。

**各家做法**：

- **CI 系统**：任务天然异步，状态由系统记录。
- **集群调度**：作业提交后由调度器管理，日志落盘。
- **嵌入式实验室**：长仿真挂后台，产物落共享目录。
- **个人开发**：常在终端里等，超时后重跑。
- **本研究仓**：脱离会话 + 退出码文件。

**是统一标准吗**：不是；但"异步 + 可离线判定"是共同方向。

## 6. 为什么共享文件必须串行改？

**答：** 因为共享文件（构建脚本、清单、共享数据）是"所有任务的交汇点"：两个任务同时改，冲突不仅难合，而且会导致"其中一方的验证结果对应的是另一方改过的文件"。

- **识别**：被多个任务引用、或被门控读取的文件。
- **纪律**：同一时刻只允许一个任务改；改完先跑受影响的门控。
- **代价**：并行度下降；换来的是验证结果可信。
- **替代**：若必须并行，先做"接口冻结"（约定期望形态），各自改各自的部分。
- **反例**：两人同时改构建脚本，合并后门控通过，但通过的是"混合体"，谁都不敢回滚。

**各家做法**：

- **单仓大项目**：代码所有者制度，共享文件需审批。
- **多仓项目**：把共享部分抽成独立组件，版本化消费。
- **企业流水线**：共享配置由平台团队统一维护。
- **小团队**：靠沟通，冲突频繁。
- **本研究仓**：共享文件串行改 + 变更后重跑门控。

**是统一标准吗**：不是。

## 7. 实例：共享树里全量暂存

**现象**：提交里出现了别人正在改的文件，或出现了不应入库的产物；回滚时牵连他人工作。

**根因**：暂存范围用了"全部"，而不是"本次声明"。

**规矩**：提交前显式列路径，并与任务书"修改文件"清单逐条对账。

**机械防**：
- 提交前生成"暂存清单 vs 声明清单"差集，非空即停。
- 收尾检查确认工作树无残留（未跟踪文件、临时命名模式）。
- 提交信息里写明改动范围，便于事后核对。

## 8. 实例：长任务在会话里等

**现象**：构建或仿真跑了一个多小时，会话超时/被打断，日志与退出码丢失，只能重跑；重跑又撞上别人的构建。

**根因**：把"等待"当成流程的一部分，完成判据依赖"屏幕上看到"。

**规矩**：超阈值的任务脱离会话运行，落日志与退出码；完成判据读取这些文件。

**机械防**：
- 启动前申报预计耗时与产物路径；启动后立即返回。
- 结束写退出码文件；收尾只认该文件。
- 与门控互斥：同一工作树的写操作与长任务不并发。

## 9. 为什么资源水位也要当门控？

**答：** 因为"跑得动"和"存得下"是两件事，而磁盘/内存的耗尽往往发生在**任务收尾之后**——人已经走了，产物还在长。等下一次派任务时才发现盘满，停的是整条队列。

**实测（2026-11-10，本仓主控机）**：

- 仓库所在文件系统 `/mnt/tao` 达 **92%**（424G / 492G）。
- 其中 **8 个已归档任务**的逐例运行目录（`runtime/`、`review/`）合计 **≈250G**：每例都留了 ELF、`libtest.a`、`m5out/`。
- `.work/build/` 下三份**一次性 gem5 构建副本**（`*-103t*`、`104t-*`）合计 **72G**：每个跑批任务各建了一份完整构建。
- 单看二进制：`gem5.opt` **702 MB**，而 `size` 实测代码+数据只有 **34 MB**——**662 MB 是调试符号**。

**为什么会这样**：

- 证据目录按"任务 + 轮次"累积（基线轮、复核轮、注入轮各留一份），没人删。
- 构建目录按任务派生，名字里带任务号，天然不会被复用。
- 逐指令轨迹（`--debug-flags=Exec`）**一例就能到 GB 级**；反过来，不开轨迹时每例 `m5out` 只有 **280 KB**——大头从来不是统计信息，是重复的运行目录。

**怎么防**：

- **收尾即清理**：任务置"已验证"后，证据目录只留 `run.sh` + 汇总 JSON/Markdown + 日志（合计 **≤10 MB**），逐例目录必须删（可重跑再生）。
- **构建目录只允许规范名**（`gem5`/`qemu`/`llvm`）；派生构建随任务删除；`gem5.debug` 只在需要源码级调试时临时建。
- **常规跑批不开轨迹**；确实要查某条错误，用起止窗口卡住范围，用完即删。
- **水位门控**：主控机 `make check-disk`、节点 `remote.py status` 的 `disk_use_pct`/`disk_alert`；**任一 > 90% 先报警并清理，再派评测/长跑任务**。

**内存为什么也要看**：

- 并发度是"核数 × 单例峰值"的乘积，不是核数本身：48 路 gem5 同时跑，单例多占 1 GB 就是 48 GB。
- **临时目录可能挂在 tmpfs 上**（本仓主控机 `/tmp` 为 16 GB tmpfs）——写满会直接中断任务链，所以节点间中转文件禁止放 `/tmp`。
- guest 的地址空间要**上限封顶**（如 QEMU `-R 4G`），否则一个"不断申请"的测试程序能耗尽宿主内存，把机器变成不可判定状态。

**判据**：一条产物如果"换台机器重跑就能重建"，它就不该长期占盘；只有**结论与最小证据**需要留下来。

**各家做法**：

- **个人机**：盘满了再删，常见"删错东西"。
- **CI 流水线**：产物按保留期自动过期，超期即删。
- **大型集群**：配额（quota）+ 定时巡检 + 告警。
- **本研究仓**：收尾清理规约 + 水位门控 + 派单前预检。

**是统一标准吗**：不是；但"上限 + 告警 + 清理责任到任务"三者缺一，都会退化成事后救火。

## 背景知识

### 术语与概念

- **缓存区**：可重建的下载件与裸仓库，删除代价低。
- **工作区**：源码检出与构建产物，可删但需能重建。
- **安装根**：被读取的最终产物，受控写入。
- **工作树**：一次检出的完整目录，含独立分支与暂存区。
- **暂存区**：本次提交将包含的改动集合。
- **临时物**：过程产物，任务结束即清理。
- **退出码文件**：长任务结束时写入的结果凭据。
- **互斥**：同一资源同一时刻只允许一个写者。

### 对照

**目录分层**

- **CMake / Meson**：源码 / 构建 / 安装三处分离。
- **Cargo**：缓存与目标目录分离。
- **嵌入式**：下载缓存 / 构建 / 安装根分离。
- **一般项目**：合并在一处，靠约定区分。

**并行方式**

- **多工作树**：独立分支与暂存区，共享对象库。
- **多克隆**：完全隔离，靠推送同步。
- **单树**：靠提交频率协调。
- **CI**：每次全新检出。

**长任务管理**

- **集群/CI**：异步 + 日志 + 状态。
- **实验室**：后台 + 共享产物目录。
- **个人**：终端等待，最脆弱。
- **共同点**：完成判定要能离线进行。
