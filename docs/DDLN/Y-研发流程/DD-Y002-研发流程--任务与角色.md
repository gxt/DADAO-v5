# 研发流程 -- 任务与角色

**本册要点**

- 任务书必须**自包含**：执行所需的事实、格式、模板都在里面，不依赖"去看另一个文件"。
- 任务要有**编号与状态机**，状态由收尾动作改，不由实现者自报。
- 三个角色：实现、审查、协调；**提交权只在一处**。
- **下发前五项预检**是防返工最便宜的投入：任务书自洽、验证手段可用、验收可跑、与合约一致、不碰只读区。
- 给执行者的约束要**可机械检查**，不写"请注意"。
- 并行有上限，共享文件必须串行。

## 1. 为什么任务书必须"自包含"？

**答：** 因为执行者可能是一个没有上下文的新会话：它看不到你和别人之前的讨论。凡是执行需要的事实、格式、模板，都必须写进任务书，否则它会猜——猜出来的东西与你的意图不一致时，返工成本比多写几行高得多。

- **自包含的三项内容**：做什么（可验收的目标）、怎么算做完（具体判据）、依据什么（格式、模板、关键事实）。
- **为什么不写"见某文件"**：被引用的文件可能变、可能被删、可能在另一个工作树里不存在。
- **为什么模板要抄进来**：模板是"格式的事实来源"，让执行者去别处找模板，等于把一致性交给了运气。
- **代价**：任务书写得长；换来的是"不需要来回澄清"。

**各家做法**：

- **Linux 内核**：补丁说明要自带"为什么改、改了什么、怎么验证"，评审者不查历史邮件。
- **LLVM**：拉取请求描述要能独立读懂改动动机与影响。
- **Rust RFC**：RFC 模板固定章节（动机、指南、缺点、替代方案），提交即自包含。
- **企业工单系统**：字段化（复现步骤、期望、实际），本质是把"自包含"做成表单。
- **IETF 草案**：状态与变更都写在文档内，不依赖讨论记录。

**是统一标准吗**：不是；但"读者不追问也能动手"是所有成熟流程的共同要求。

## 2. 为什么任务要有编号与状态机？

**答：** 因为并行时"现在到哪一步"必须能从盘上读出来，而不是靠谁记得。编号让引用稳定，状态机让推进可判定。

- **编号**：模块前缀 + 序号 + 后缀；只增不复用，引用永不歧义。
- **状态**：待开始 → 待验收 → 已验证，另有阻塞与返工分支；**只有收尾动作能改状态**。
- **为什么不让实现者自报"完成"**：自报的"完成"没有证据，等于把验收权交给了被验收者。
- **状态落点**：状态写在任务本体里，进度表只做索引——避免两处状态打架。
- **副作用**：状态机逼着流程定义"什么叫进入下一态"，也就定义了证据。

**各家做法**：

- **GitHub / GitLab**：议题状态 + 拉取请求关联，合并即关闭。
- **Jira 类**：状态机可配置，但常被简化成"进行中/完成"。
- **Linux 内核**：无编号状态机，靠邮件与合并状态推断。
- **Rust**：RFC 有明确状态（提案/最终评论/接受/实施）。
- **IETF**：草案有标准状态序列（个人草案 → 工作组草案 → RFC）。

**是统一标准吗**：不是；共同点是"状态可被别人读到"。

## 3. 为什么角色要分实现、审查、协调三种？

**答：** 因为三种动作的目标互相冲突：实现者想"尽快通过"，审查者要"证明它不通过"，协调者要"保证顺序与边界"。同一个人兼三种角色时，最容易发生的是"自己给自己放行"。

- **实现**：写代码或写文档，填完成区，但不改状态为"已验证"。
- **审查**：独立重跑验收、注入反例、核对完成区与真实输出。
- **协调**：决定顺序、处理跨模块影响、执行提交；**唯一有提交权**。
- **为什么提交权只在一处**：提交是"把改动固化"的动作，多处可提交必然出现"谁先谁后"的竞争与漏检。
- **代价**：多一次交接；换来的是"放行"这个动作有第二双眼睛。

**各家做法**：

- **Linux 内核**：作者 / 评审 / 维护者三层，维护者决定并入。
- **LLVM**：作者 + 评审者 + 构建机器人（机器充当"第二双眼睛"）。
- **Rust**：作者 + 评审 + 合并队列（队列串行化）。
- **Apache 系**：评审后提交，提交者与评审者分离。
- **企业流水线**：开发 / 测试 / 发布三角色，发布权集中。

**是统一标准吗**：不是。

## 4. 下发前五项预检，各防什么？

**答：** 五项分别防五类最常见的返工：任务书自相矛盾、验证手段还不存在、验收项跑不了、与既有约定冲突、改到不该改的地方。

- **① 任务书内部一致**：目标、判据、修改范围互不矛盾（否则执行者必然二选一，选错就返工）。
- **② 验证手段的全部前置实际可用**：门控、工具、数据现在就位（不是"应该会有"）。
- **③ 验收逐条标"现在可跑 / 被阻塞（原因 + 替代证据）"**：把"跑不了"提前暴露。
- **④ 与合约、向量一致**：避免"实现对了但契约没过"。
- **⑤ 拟改文件与只读区冲突检查**：命中只读区且无授权 ⇒ 直接停，别做。
- **为什么放在下发前**：这五项在下发后发现的成本是下发前的十倍（要改任务书、要重排、要解释）。

**各家做法**：

- **Linux 内核**：补丁进队列前有自动构建与检查脚本（相当于②③）。
- **LLVM**：预提交 CI 覆盖构建与测试（②③），风格检查（④）。
- **Rust**：合并队列先跑全量测试再入主分支（③）。
- **航空/汽车**：需求可追溯性检查（④⑤ 的强形式）。
- **一般团队**：常只做①，其余靠运气。

**是统一标准吗**：不是。

## 5. 为什么给执行者的约束要"可机械检查"？

**答：** 因为"请注意不要越界"这类话在压力下必然失效；能机械检查的约束（路径白名单、命令白名单、提交前清单比对）才在没人看着时仍然有效。

- **可检查的例子**：临时目录固定在指定位置（可扫描仓库有无残留）；提交前列清单并与任务书对账（可 diff）；只允许写指定目录（权限层面拦截）。
- **不可检查的例子**："尽量少改""注意风格""不要顺手优化"——只能靠自觉。
- **为什么执行者需要约束**：并行时没人盯着每一步；约束是"没人看着时的护栏"。
- **代价**：约束会拖慢"顺手改一下"的爽感；换来的是可预测。

**各家做法**：

- **LLVM**：格式化与静态检查进 CI，格式不合成硬伤。
- **Rust**：`rustfmt`/`clippy` 作为门控，风格争议变成工具判定。
- **Google**：预提交检查 + 代码所有者规则。
- **Linux 内核**：检查脚本 + 维护者人工把关（工具覆盖较松）。
- **航空/医疗**：编码规范由静态分析强制。

**是统一标准吗**：不是。

## 6. 实例：子代理异常返回，但工作已经落盘

**现象**：收到"任务取消 / 空结果"的通知，于是重派同一任务；两份产出先后落盘，后一份覆盖了前一份的完成区，审阅记录丢失。

**根因**：把"通知"当成"事实"。通知只是信号，盘上的任务状态、证据目录、提交记录才是事实。

**规矩**：收到任何"完成 / 失败 / 取消"通知，先核盘上事实，再决定续链；未落盘才重试，且重试要有次数上限。

**机械防**：
- 收尾判定只读盘上文件（状态字段、证据目录、提交记录），通知仅作触发。
- 重试前检查"是否已有产出"，有产出则转入审查而非重派。
- 同一任务的重试次数写进任务书，超过即停并上报。

## 7. 实例：验证手段没预检就下发

**现象**：任务做到一半才发现"验收要用的门控还没接上"；为了赶进度，把验收标准改成"人工看一眼"，于是这一册永远无法被独立复核。

**根因**：预检只检查了任务书"写得对不对"，没检查"验证手段现在能不能跑"。

**规矩**：下发前逐条标注验收项的状态——"现在可跑"或"被阻塞（原因 + 替代证据）"；被阻塞项必须在任务书里写清解锁条件。

**机械防**：
- 预检清单作为任务书固定章节，五项逐条填写。
- 收尾时把"当时标注"和"实际跑出的输出"逐条对齐；不一致即视为任务书失真。
- 被阻塞项若在收尾时仍未解锁，只能以"部分验收"结案并显式登记遗留。

## 背景知识

### 术语与概念

- **自包含任务书**：执行所需事实全在文档内，不依赖外部上下文。
- **状态机**：状态与允许的迁移，只有特定动作能触发迁移。
- **角色分离**：实现、审查、协调由不同主体承担。
- **预检**：下发前的机械核对清单。
- **完成区**：任务书里记录"实际改了什么、跑出了什么"的固定章节。
- **提交权**：把改动固化进主分支的权限，只授予一个角色。
- **越界**：改动了任务书范围之外的文件。

### 对照

**任务载体**

- **Linux 内核 / LLVM / Rust**：补丁或 PR 自带说明与验证信息。
- **Jira 类**：字段化工单，适合状态追踪，弱于技术叙述。
- **IETF**：草案文档自带状态与变更。
- **企业流水线**：工单 + 流水线记录分离。

**角色分离程度**

- **Linux 内核**：作者 / 评审 / 维护者三层。
- **LLVM**：作者 + 评审 + 机器。
- **Rust**：作者 + 评审 + 合并队列。
- **Apache**：评审与提交分离。
- **小团队**：常一人多角色，冲突时无裁决者。

**约束的机械化**

- **强**：格式工具、静态分析、权限白名单、提交清单比对。
- **中**：CI 检查 + 人工评审。
- **弱**：口头约定与"请注意"。
- **趋势**：越靠近生产与安全关键，越倾向机械化。
