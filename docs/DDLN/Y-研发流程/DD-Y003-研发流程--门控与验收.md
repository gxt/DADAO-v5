# 研发流程 -- 门控与验收

**本册要点**

- 门控分三档：**秒级**（完整性 + 冒烟）、**分钟级**（模块代表集）、**小时级**（全量）；触发点固定，不靠人记得。
- 门控的价值不在"覆盖多"，而在**能失败**：没有可达失败路径的检查不是证据。
- **反例注入**是验证门控本身的手段，注入后必须**保留现场再还原**。
- 证据 = 一键脚本 + 真实输出 + **被检命令自己的退出码**，三者缺一不可。
- 验收由**不写实现的人**独立重跑；自报"我测过了"不算。
- 模块门控全绿只能证明"模块内没退化"，不能证明"组合正确"。

## 1. 为什么门控要分三档？

**答：** 因为检查代价差两三个数量级，而反馈时机比完备性更重要：秒级检查每次改都跑，分钟级收尾跑，小时级里程碑跑。只留最全的一档，结果是没人跑。

- **秒级**：结构完整性（清单闭包、编号唯一、路径存在、覆盖投影一致）+ 工具自测；不跑被测语义。
- **分钟级**：模块代表集（按层机械派生，不手挑）。
- **小时级**：全量语义 + 大套件；只在里程碑或显式要求时跑。
- **触发点固定**：收尾跑分钟级，里程碑跑小时级；"看情况跑"等于不跑。
- **并发保护**：同一工作树内的门控与写操作互斥（用锁串行化），否则门控会读到半成品。
- **为什么分层而不是"按需"**：按需意味着每次都要判断"这次要不要跑"，判断本身就会走样。

**各家做法**：

- **LLVM**：`lit` 按目录与特性标签分组，日常跑子集、合并前跑全量。
- **Rust**：本地测试 → 合并队列 → 夜间全量，三级推进。
- **Linux 内核**：子系统自测 + 定期全量构建（不同配置矩阵）。
- **Chromium**：提交队列跑代表集，夜间跑完整矩阵。
- **航空/汽车**：按审查节点分层，节点间只跑增量检查。

**是统一标准吗**：不是；但"快速反馈 + 慢速兜底"是所有成熟流程的共性。

## 2. 为什么"能失败"比"覆盖全"更重要？

**答：** 因为一条永远不会失败的检查，覆盖再全也只是装饰；它带来的是"假绿"——比没有检查更危险，因为它会让人停止怀疑。

- **可达失败路径**：每条断言都要能指出"改哪里会让它红"；指不出来就说明断言无效。
- **常见恒真形态**：两支写同一结果；断言"跑完没崩"而不是"值对不对"；把异常吞掉后判通过；比较对象是自己。
- **覆盖与有效性的关系**：覆盖决定"能发现多少类问题"，可达失败决定"发现了会不会报"；后者是前提。
- **代价**：写"能失败"的检查要比写"看起来在检查"的检查多花时间。

**各家做法**：

- **编译器测试**：`RUN`/`CHECK` 必须能因输出变化而失败。
- **合规套件**：签名比对，签名不同必然失败，不存在"恒真"空间。
- **内核自测**：断言 + TAP 输出，失败可定位。
- **企业流水线**：常见"只检查构建成功"的伪门控。
- **研究原型**：常以"能跑通"代替断言，可复现性最弱。

**是统一标准吗**：不是。

## 3. 反例注入怎么做才不破坏现场？

**答：** 先备份、再注入、确认变红、然后**用备份还原并核对哈希**；全程不碰版本控制命令。破坏现场的还原方式（如强制检出）会把别人未提交的改动一起清掉。

- **注入对象**：被检对象本体（值、字段、行），以及检查脚本自身（防止"脚本永远返回真"）。
- **注入粒度**：一次只动一处，确保"变红"可归因到这一处。
- **还原纪律**：用文件备份 + 哈希对账；**不用**任何会清理工作树的命令。
- **记录要求**：保留"注入前 → 注入后变红 → 还原后复绿"的三段真实输出。
- **为什么审查者要独立注入一次**：实现者自测通过不代表检查有效；第二个人注入是"检查的检查"。

**各家做法**：

- **LLVM**：用"改预期输出"验证测试会红（属于注入的一种）。
- **Rust**：合并队列本身是"反例"——任何回归都会阻止入队。
- **内核自测**：以故意失败的用例验证框架。
- **硬件验证**：注入故障（错误值、时序偏移）验证检查器。
- **一般团队**：很少做，导致门控有效性无人验证。

**是统一标准吗**：不是。

## 4. 证据为什么必须是"脚本 + 输出 + 退出码"？

**答：** 因为三样各缺一角：脚本让证据可重放，输出让人能读，**退出码**让机器能判。用管道把命令输出转存时如果吞掉了退出码，失败会被记成成功。

- **一键脚本**：一条命令重跑全部验收，避免"靠记忆复现"。
- **真实输出**：原始文本，不做美化与截断（截断会藏掉关键行）。
- **退出码**：必须抓**被检命令自身**的退出码；经过管道/包装后要单独记录，否则拿到的可能是包装器的码。
- **落点**：证据放非易失位置，按任务归档；临时目录只放过程产物。
- **失败处置**：保留现场（命令、输出、退出码、日志路径），然后自行处置并记录次数，不以重试掩盖根因。

**各家做法**：

- **CI 系统**：天然记录退出码与日志，证据完整。
- **LLVM**：`lit` 输出逐用例结果，失败带日志。
- **内核自测**：TAP + 退出码。
- **企业流水线**：日志留存但常被清理策略覆盖。
- **口头验收**："我看过了"——无任何可复核证据。

**是统一标准吗**：部分统一（退出码是 POSIX 通用约定），证据形态各家自定。

## 5. 为什么验收必须由不写实现的人重跑？

**答：** 因为实现者的自测会不自觉地"围绕已知能过的路径"设计；独立重跑能暴露"只有作者知道的跑法"和"环境依赖"。

- **重跑而非看报告**：报告可以是选择性摘录；重跑看到的是同一份代码在当前环境下的真实行为。
- **核对范围**：完成区声明的修改文件与实际改动是否一致；验收项与真实输出是否逐条对齐。
- **独立注入**：审查者至少注入一次反例，确认检查有效。
- **收尾前置**：门控全绿、仓库无残留、证据在非易失位置、无未提交结果——任一条不过就停。
- **代价**：多一个人时；换来的是"放行"有第二双眼睛。

**各家做法**：

- **Linux 内核**：维护者重跑或依赖自动化农场。
- **LLVM**：构建机器人重跑，评审者看差异。
- **Rust**：合并队列在干净环境重跑。
- **Apache**：提交前至少一位评审者复核。
- **航空/汽车**：独立验证团队重跑并签核。

**是统一标准吗**：不是；但"验证者不等于实现者"是共同底线。

## 6. "单模块全绿"为什么不能推出"系统正确"？

**答：** 因为模块之间的约定不在任何单个模块的门控里：同一份接口文档，两个模块可以各自"正确"地理解成不同意思。组合错误只有跨模块检查才能发现。

- **典型裂缝**：寄存器保存约定、参数顺序、结构体布局、状态机迁移、错误码语义。
- **为什么模块门控看不见**：每个模块的用例都按自己的理解写期望值，两边都自洽。
- **补法**：设"整体收敛"检查（跨模块用例、接口契约扫描、端到端场景），并规定"跨模块影响未处置不得宣告完成"。
- **代价**：跨模块用例写起来慢、定位难；但它是唯一能发现"理解分歧"的手段。

**各家做法**：

- **Linux 内核**：集成测试 + 全量构建矩阵，跨子系统问题在集成阶段暴露。
- **LLVM**：全量测试套件与端到端编译链测试。
- **Rust**：合并队列里跑的是全仓测试，不是单 crate。
- **Chromium**：提交队列跑跨模块的完整测试集。
- **硬件验证**：系统级仿真 + 硅后验证兜底。

**是统一标准吗**：不是。

## 7. 实例：验证脚本恒真

**现象**：门控长期全绿；人为把一处关键值改错，门控仍然全绿。

**根因**：断言两支写的是同一个结果（或断言的是"进程正常退出"而不是"值正确"），失败路径根本不存在。

**规矩**：每条断言必须能指出"改哪里会让它红"；验收脚本本身要被注入验证。

**机械防**：
- 审查环节独立注入一次反例，记录"注入 → 变红 → 还原（备份 + 哈希）→ 复绿"三段输出。
- 断言清单里逐条标注"对应的可注入点"，指不出来的断言一律重写。
- 门控汇总里区分"通过"与"未判定"，防止把跳过当通过。

## 8. 实例：单模块全绿，组合起来错

**现象**：每个模块的门控都过，集成后行为不对；定位时发现两个模块对同一条约定的理解相反。

**根因**：门控按模块切分，跨模块约定没有对应检查；两边各自的期望值都按自己的理解写，所以都"通过"。

**规矩**：存在未处置的跨模块影响时，不得宣告模块完成；接口约定必须有跨模块用例。

**机械防**：
- 设"整体收敛"任务，专门跑跨模块场景与接口一致性检查。
- 接口变更触发对应跨模块用例；未触发即视为遗漏。
- 收尾检查里加一条：本次改动是否触及跨模块约定；触及则必须列出对应的跨模块证据。

## 背景知识

### 术语与概念

- **门控**：可自动判定、且能失败的检查。
- **可达 FAIL**：存在能让断言变红的输入或改动。
- **反例注入**：人为改坏一处，验证检查确实会红。
- **证据三件套**：重跑脚本、真实输出、被检命令的退出码。
- **假绿**：检查通过但缺陷仍存在。
- **收敛点**：专门做跨模块检查的任务或阶段。
- **互斥锁**：保证同一工作树内门控与写操作不并发。
- **未判定**：环境或工具不支持，结果既非通过也非失败。

### 对照

**门控分层**

- **LLVM**：目录/标签分组 + 合并前全量。
- **Rust**：本地 → 合并队列 → 夜间。
- **Linux**：子系统自测 + 构建矩阵。
- **Chromium**：提交队列代表集 + 夜间全量。
- **航空/汽车**：按审查节点分层。

**证据形态**

- **CI 系统**：日志 + 退出码 + 制品。
- **测试框架**：逐用例结果 + 失败详情。
- **内核自测**：TAP 文本。
- **口头/截图**：不可复核，最弱。

**跨模块检查**

- **强**：全仓测试、端到端链、接口一致性扫描。
- **弱**：仅模块自测，靠人盯。
- **趋势**：模块越多，越需要独立的"收敛点"。
