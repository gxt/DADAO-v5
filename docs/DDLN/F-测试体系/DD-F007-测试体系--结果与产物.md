# 测试体系 -- 结果与产物

**本册要点**

- 每次运行一个独立目录，内含三件套：结构化结果、原始日志、元数据。
- 全量跑与夜跑都要写**只读报告**，由里程碑消费；缺报告即失败。
- 夜跑目录名用**本地日期**，元数据里记 **UTC**；两者不可混。
- 驱动不得有固定默认输出目录，输出路径必须显式传参。
- 结果分通过 / 失败 / 未判定三列，并带平台与版本。
- 清理与复现都要有目标：产物可删、结论可重建。

## 1. 为什么运行产物要单独成目录？

**答：** 因为"跑过一次"必须可追溯：跑了什么、结果如何、用了哪版工具链；散落在仓库里的输出既不可追溯，也会污染工作树。

- **目录名**：时间戳 + 套件 + 模式，可排序、可去重。
- **三件套**：结构化结果（机器读）、日志（人读）、元数据（命令与版本）。
- **隔离**：与源码树分离。
- **保留**：权威跑与报告长期保留，其余按策略清理。

## 2. 全量报告与夜跑报告各是什么？

**答：** 全量跑逐成员执行并写报告（成员清单、每项返回码、日志指针）；夜跑跑长套件并写同样格式的报告；两者都由里程碑验证存在性、结构与结果。

- **全量报告**：按时间戳目录存放，覆盖四个范围的成员清单。
- **夜跑报告**：按本地日期（小时粒度）目录存放，覆盖外部套件与长资源场景。
- **消费方式**：里程碑读报告，不重跑长套件。
- **缺失即失败**：没跑不等于通过，报告缺失必须判失败。
- **结构检查**：表头、数据行、列数、返回码字段都要校验。

## 3. 本地时间与 UTC 怎么处理？

**答：** 目录名可用本地日期便于人找，但元数据必须记 UTC，便于跨机器比对与排序。

- **目录**：本地日期（小时粒度），一眼能看出"哪天的跑"。
- **元数据**：统一 UTC 时间戳。
- **一致性**：报告内部所有时间字段用同一时区约定，并在元数据里注明。
- **陷阱**：跨时区协作时，本地时间目录会"看起来乱序"。

## 4. 驱动为什么要禁止默认输出目录？

**答：** 因为默认目录会让"忘了传参"变成"覆盖上一次结果"：历史消失，比对失效。

- **要求**：输出路径必填，由调用方指定。
- **好处**：结果可并存、可比对。
- **检查**：静态检查驱动是否含固定默认目录。
- **配套**：运行目录命名规则统一。

## 5. 统计口径怎么定？

**答：** 三列状态 + 四类归因 + 三个维度（范围、平台、版本）；单列未判定，禁止并入通过。

- **状态**：通过 / 失败 / 未判定（含跳过、环境不支持）。
- **归因**：编码 / 语义 / 工具链 / 环境或套件自身。
- **维度**：按范围、按平台、按版本。
- **趋势**：只有版本可比的两次运行才能比趋势。
- **反模式**：只报通过率；未判定算通过；跨版本直接比数量。

## 6. 清理与复现怎么做？

**答：** 清理按清单删、保留权威与报告；复现从干净状态重建并比对，验证"结论可重建"。

- **清理目标**：按产物清单删除，白名单保留权威跑与报告。
- **复现目标**：干净环境下重跑关键套件，比对结果与版本。
- **判据**：换机器能否得到同一结论。
- **留痕**：清理与复现都要记录时间、命令与结果。

## 背景知识

### 术语与概念

- **三件套**：结果、日志、元数据。
- **全量报告**：逐成员执行的结构化记录。
- **夜跑报告**：长套件的结构化记录。
- **报告消费**：里程碑读报告而不重跑。
- **未判定**：非通过非失败的状态。
- **复现**：从干净状态重建并比对。

### 对照

**产物组织**

- **强**：独立目录 + 三件套 + 报告。
- **弱**：输出散落仓库或临时目录。
- **判据**：换个人能否复现同一结论。

**时间处理**

- **目录本地 + 元数据 UTC**：兼顾可读与可排序。
- **全本地**：跨时区易乱。
- **全 UTC**：人读不直观。
