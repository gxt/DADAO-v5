# 测试体系 -- 模块自测

**本册要点**

- unit 测各模块自身功能：编译器、链接器、模拟器、C 库、仓库工具。
- 工具链的端到端用例（编译/链接/运行）也归 unit，不再单列一个"端到端"范围。
- 跑在宿主/工具链上，不依赖整机模拟。
- smoke 与全量是**两个不同目标**：全量版内部会带上 smoke，但只在全量层直接列出。
- 模块全绿不能推出系统正确——跨模块约定要单独测。

## 1. unit 覆盖哪些模块？

**答：** 每个可独立验证的组件各成一组：编译器的编码与代码生成、链接器的产物与重定位、模拟器的译码与执行、C 库的接口、仓库自有工具，以及工具链的端到端用例。

- **编译器**：汇编/反汇编往返、编码字节、代码生成结构、执行结果。
- **链接器**：重定位、符号解析、链接脚本、产物格式。
- **模拟器**：译码覆盖、异常路径、设备模型。
- **C 库**：自测套件（只在库自身构建下跑）。
- **仓库工具**：门控脚本、生成器、校验器的自测。
- **端到端**：编译→链接→运行的小程序（原先单列的范围已并入本处）。

## 2. 为什么模块全绿不等于系统正确？

**答：** 因为模块之间的约定不在任何模块的测试里：参数顺序、寄存器保存、结构布局、错误码，两边各自正确却不兼容。

- **典型裂缝**：编译器与模拟器对同一编码理解不同；库与内核参数约定不一致。
- **补法**：跨模块用例（inst/arch/tset）与接口一致性检查（静态层）。
- **判据**：模块全绿只说明没退化，不说明组合正确。
- **成本**：跨模块用例慢，但能发现"理解分歧"。

## 3. smoke 与全量为什么要分成两个目标？

**答：** 因为"一层一列"要求同一目标只在一个层直接列出；全量层用"全量版"目标，它内部把 smoke 当前置依赖，从而既跑到又不重复计层。

- **smoke 目标**：代表集，快速层直接列出。
- **全量目标**：等于 smoke + 全量用例；只在全量层列出。
- **好处**：层归属唯一，耗时统计可解释。
- **代价**：多维护一个"全量版"入口。

## 4. 代表集怎么派生？

**答：** 机械规则：按用例粒度取固定比例或固定规则（每个格式类一条、每个模块入口一条），规则写入文档，不手挑。

- **可复现**：换人得到同一集合。
- **稳定**：文件增删时变化可解释。
- **计数**：现场统计，不写死。
- **覆盖**：代表集要包含每类"最容易坏"的用例。

## 5. 上游套件与自建用例怎么划界？

**答：** 上游/组件自带的测试优先用上游的；我们只补"上游没覆盖的架构特性"与"我们的胶水"。

- **用上游**：编码往返、优化器回归、库自测。
- **自建**：本架构特有的边界、异常、扩展指令。
- **胶水**：启动、链接脚本、桩代码，属测试基础设施。
- **禁止**：复制上游用例后改期望值来"通过"。

## 6. 版本与回归怎么管？

**答：** 组件版本锁定；升级先跑全量再合；差异要区分"上游行为变化"与"我们引入的回归"。

- **锁定**：精确版本或提交，不用浮动标签。
- **升级流程**：全量跑 → 分类差异 → 需要时更新期望并说明理由。
- **基线**：保留上次全量结果便于比对。
- **归因**：集中某模块 ⇒ 该模块变更；分散 ⇒ 工具链或环境。

## 背景知识

### 术语与概念

- **unit**：模块自身功能的测试范围。
- **代表集**：按规则抽取的子集。
- **全量版目标**：带 smoke 前置依赖的全量入口。
- **胶水**：把上游组件接到本架构的非用例代码。
- **回归基线**：用于比对的历史结果。
- **端到端用例**：编译、链接、运行一条链。

### 对照

**模块测试**

- **编译器**：编码断言 + 代码生成结构 + 执行结果。
- **链接器**：产物结构 + 重定位结果。
- **模拟器**：译码覆盖 + 异常路径。
- **本设计**：按模块分组，smoke 与全量分目标。
