# 测试体系 -- 模块自测

**本册要点**

- unit 测的是**模块自身功能**：编译器、链接器、模拟器、C 库、仓库工具。
- 跑在宿主/工具链上，不依赖整机模拟。
- 组件自带的测试套件归本范围；不自建重复套件。
- 代表集由机械规则派生；全量进 L3。
- 模块全绿**不能**推出系统正确——跨模块约定要单独测。

## 1. unit 覆盖哪些模块？

**答：** 每个可独立验证的组件各成一组：编译器的编码与代码生成、链接器的产物与重定位、模拟器的译码与执行、C 库的接口、以及仓库自有工具。

- **编译器**：汇编/反汇编往返、编码字节、代码生成结构、执行结果。
- **链接器**：重定位、符号解析、链接脚本、产物格式。
- **模拟器**：译码覆盖、异常路径、设备模型。
- **C 库**：自测套件（在库自身构建下跑）。
- **仓库工具**：门控脚本、生成器、校验器的自测。

## 2. 为什么模块自测不能替代系统测试？

**答：** 因为模块之间的约定不在任何模块的测试里：参数顺序、寄存器保存、结构布局、错误码，两边各自"正确"却互相不兼容。

- **典型裂缝**：编译器与模拟器对同一编码理解不同；库与内核的参数约定不一致。
- **补法**：跨模块用例（inst/arch/tset 层）与接口一致性检查。
- **判据**：模块全绿只说明"模块没退化"，不说明"组合正确"。
- **成本**：跨模块用例写起来慢，但它是唯一能发现"理解分歧"的手段。

## 3. 代表集怎么派生？

**答：** 机械规则：按测试文件/用例粒度取固定比例或固定规则（如每个格式类一条、每个模块入口一条），不手挑，且规则写入文档。

- **机械派生**：规则可复现，换人得到同一集合。
- **稳定**：文件增删时集合变化可解释。
- **计数现场统计**：不写死"应有 N 条"。
- **全量**：进 L3；代表集进 L2。

## 4. 上游套件与自建用例的边界？

**答：** 上游/组件自带的测试优先用上游的（省维护、覆盖真实），我们只补"上游没有覆盖的架构特性"与"我们的胶水"。

- **用上游**：编码往返、优化器回归、库自测。
- **自建**：本架构特有的边界、异常、扩展指令。
- **胶水**：启动、链接脚本、桩代码，属测试基础设施，不属上游。
- **禁止**：复制上游用例后改期望值来"通过"。

## 5. 版本与回归怎么管？

**答：** 组件版本锁定；升级时先跑全量再合；失败要区分"上游行为变化"与"我们引入的回归"。

- **锁定**：精确版本或提交，不用浮动标签。
- **升级流程**：全量跑 → 分类差异 → 更新期望（需说明理由）。
- **回归基线**：保留上次全量结果，便于比对。
- **归因**：差异集中在某模块 ⇒ 该模块变更；分散 ⇒ 可能是工具链或环境。

## 背景知识

### 术语与概念

- **unit**：模块自身功能的测试范围。
- **代表集**：按规则抽取的子集，进快速门控。
- **胶水**：把上游组件接到本架构的非用例代码。
- **回归基线**：用于比对的历史结果。
- **跨模块约定**：模块之间必须一致的接口细节。

### 对照

**模块测试**

- **编译器**：编码断言 + 代码生成结构 + 执行结果。
- **链接器**：产物结构 + 重定位结果。
- **模拟器**：译码覆盖 + 异常路径。
- **本设计**：按模块分组，代表集进 L2、全量进 L3。
