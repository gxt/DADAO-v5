# 测试体系 -- 外部套件

**本册要点**

- tset 跑的是**第三方套件**在成品系统上的行为：C 库测试、编译器测试套件、基准程序。
- 跑在 `user` 平台（成品系统），测不到特权态——那属 arch。
- 套件**不改上游源码**；接入靠胶水（链接脚本、启动代码、接口桩），胶水分共享与套件独有。
- smoke 跑代表集，full 进夜跑（小时级），结果只产只读报告。
- 失败归因要落在"工具链 / C 库 / 系统接口"三者之一，否则无法处置。

## 1. 为什么需要外部套件？

**答：** 因为自建用例覆盖的是"我们想到的语义点"，外部套件覆盖的是"真实程序的用法"：库函数、编译器优化、长循环、浮点、字符串处理，这些组合出的缺陷自建用例很难穷举。

- **覆盖面**：真实代码路径远多于手工用例。
- **回归价值**：工具链或库升级后，外部套件是最灵敏的探测器。
- **代价**：启动慢、依赖多、失败定位难。
- **定位**：它不是"更全的单元测试"，而是"系统级体检"。

## 2. 为什么跑在 `user` 平台？

**答：** 因为外部套件假定有完整的 C 运行环境与系统调用：它们需要 libc、文件 I/O、进程与内存管理；只有成品系统才能提供，裸机会直接缺接口。

- **前提**：成品系统 + C 库 + 系统调用接口。
- **测不到**：特权态、页表、异常现场（这些归 arch/inst）。
- **环境差异**：宿主与目标端序、`long double` 宽度、`fenv` 支持度不同，比对前要排除。
- **未判定**：缺某个接口导致套件无法运行时，记未判定而非失败。

## 3. 胶水怎么归属？

**答：** 胶水是"把上游套件接到本架构"的非用例代码，按复用范围分三处：共享（链接/启动/运行时/桩）、套件独有、组件补丁。**改上游源码只能走组件补丁，不能塞进测试目录。**

- **共享胶水**：链接脚本、启动代码、运行时、公共宏与期望。
- **套件独有胶水**：只有这个套件需要的适配（如基准的板级支持）。
- **组件补丁**：必须改上游源码时才用，走组件补丁流程。
- **判据**：被两个以上套件复用 ⇒ 共享；只服务一个 ⇒ 套件独有。
- **反例**：把补丁混进测试目录，导致"上游干净"的假象。

## 4. smoke 与 full 怎么分？

**答：** smoke 取每个套件的代表子集（机械规则），几分钟内可跑完；full 跑全量，放进夜跑，小时级，结果只读。

- **smoke**：进 L2，任务收尾跑；保证"没把系统整体搞坏"。
- **full**：进夜跑；覆盖长尾与性能相关路径。
- **报告**：夜跑产出汇总表（范围/套件/返回码/日志），里程碑消费。
- **禁止**：把 full 塞进提交前门控（会被绕过）。

## 5. 失败怎么归因？

**答：** 按"工具链 / C 库 / 系统接口 / 套件自身"四类归因：先看是否普遍失败（工具链或库），再看是否集中在某类调用（接口），最后才怀疑套件适配。

- **普遍失败**：工具链或库整体不可用。
- **集中在某类调用**：系统接口语义或 ABI 问题。
- **集中在某个测试文件**：胶水或该文件依赖的特性。
- **偶发**：并发、时序、资源不足——需要复跑并记录次数。
- **处置**：归因后落到对应模块任务，不在测试体系里"改期望值"。

## 背景知识

### 术语与概念

- **tset**：外部套件范围。
- **胶水**：把上游套件接到本架构的非用例代码。
- **成品系统**：能跑用户态程序、带 C 库与系统调用的环境。
- **未判定**：缺接口或环境导致无法运行。
- **夜跑**：低频长跑，产物只读。

### 对照

**外部套件形态**

- **C 库测试**：逐接口断言 + 边界。
- **编译器测试套件**：编译并运行大量程序，比对输出。
- **基准程序**：以运行正确性 + 性能为主。
- **共同点**：都依赖完整运行环境。
