# 测试体系 -- 外部套件

**本册要点**

- tset 跑第三方套件在成品系统上的行为：C 库测试、编译器测试套件、基准程序。
- 跑在用户态平台，测不到特权态——那属资源与权限范围。
- 套件不改上游源码；接入靠胶水，胶水分共享与套件独有。
- **smoke 只在快速层；全量只在夜跑**；全量层不直接列 tset。
- 失败归因落在"工具链 / C 库 / 系统接口 / 套件自身"四类。

## 1. 为什么需要外部套件？

**答：** 因为自建用例覆盖的是我们想到的语义点，外部套件覆盖真实程序的用法：库函数、优化器、长循环、浮点、字符串处理。

- **覆盖面**：真实代码路径远多于手工用例。
- **回归价值**：工具链或库升级后最灵敏的探测器。
- **代价**：启动慢、依赖多、定位难。
- **定位**：不是"更全的单元测试"，而是系统级体检。

## 2. 为什么跑在用户态平台？

**答：** 因为外部套件假定有完整 C 运行环境与系统调用：需要库、文件 I/O、进程与内存管理，只有成品系统能提供。

- **前提**：成品系统 + C 库 + 系统调用接口。
- **可行性看平台能力**：有没有"系统调用代答"、时序是否精确——缺代答就要替代通道或最小内核。
- **测不到**：特权态、页表、异常现场。
- **环境差异**：端序、`long double` 宽度、浮点环境支持度不同，比对前要排除。
- **未判定**：缺接口导致无法运行时，记未判定而非失败。

## 3. 胶水怎么归属？

**答：** 胶水是"把上游套件接到本架构"的非用例代码，按复用范围分三处：共享、套件独有、组件补丁；改上游源码只能走组件补丁。

- **共享**：链接脚本、启动代码、运行时、公共宏与桩。
- **套件独有**：只有该套件需要的适配。
- **组件补丁**：必须改上游源码时使用，走组件补丁流程。
- **判据**：被两个以上套件复用 ⇒ 共享。
- **反例**：把补丁混进测试目录，制造"上游干净"的假象。

## 4. smoke 与全量怎么分？

**答：** smoke 取每个套件的代表子集，进快速层；全量放夜跑（静态与动态各一遍），结果只读，按需诊断（观测，不阻断收口）。

- **smoke**：几分钟内完成，保证"系统整体没坏"。
- **全量**：小时级，覆盖长尾与性能相关路径。
- **不进全量层**：全量层的定位是"四范围之外的语义与集成"，tset 全量不在此列。
- **报告**：夜跑产出汇总表，按需 `make check-night-report` 验证其存在与结果（观测）。
- **禁止**：把全量塞进提交前门控。

## 5. 失败怎么归因？

**答：** 四类：普遍失败看工具链或库；集中在某类调用看系统接口；集中在某个文件看胶水；偶发看并发与时序。

- **普遍失败**：工具链或库整体不可用。
- **集中某类调用**：系统接口语义或 ABI 问题。
- **集中某文件**：胶水或该文件依赖的特性。
- **偶发**：并发、时序、资源不足；复跑并记录次数。
- **处置**：归因后落到对应模块，不在测试体系里改期望值。

## 6. 三条套件各自测什么？

**答：** C 库测试看接口与边界；编译器测试套件看编译正确性与运行结果；基准程序看正确性加性能。

- **C 库**：逐接口断言与边界，最能暴露 ABI 与系统调用问题。
- **编译器套件**：大量程序编译并运行，比对输出；暴露优化与代码生成缺陷。
- **基准**：正确性 + 性能；性能数据只作参考，不作判据。
- **组合**：三者互补，不能只留一个。

## 背景知识

### 术语与概念

- **tset**：外部套件范围。
- **胶水**：把上游套件接到本架构的非用例代码。
- **成品系统**：能跑用户态程序、带库与系统调用的环境。
- **未判定**：缺接口或环境导致无法运行。
- **夜跑**：低频长跑，报告只读。

### 对照

**套件形态**

- **C 库测试**：逐接口断言 + 边界。
- **编译器测试套件**：编译并运行大量程序。
- **基准程序**：正确性 + 性能。
- **共同点**：都依赖完整运行环境。
