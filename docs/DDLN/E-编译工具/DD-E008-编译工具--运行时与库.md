# 编译工具 -- 运行时与库

**本册要点**

- **builtins 是工具链的一部分**：没有硬件指令覆盖的运算，必须由运行时库提供，编译器不能凭空生成。
- builtins 归 `compiler-rt`（或 libgcc），**不归 C 库**：它服务的是"代码生成",不是"应用编程接口"。
- **启动代码 `crt0`** 负责"把 C 运行环境搭起来"，只能由工具链/环境提供。
- 链接顺序（`crt1` → `crti` → `crtbegin` → 用户 → 库 → `crtend` → `crtn`）影响符号解析与初始化，不能乱。
- 静态 PIE 需要**位置无关的 C 库**，否则重定位在启动时无法自解。
- **库的选型归运行平台，库的链接机制归工具链，系统调用契约归 OS** —— 三段不重叠。
- 裸机没有内核，I/O 只能走 **semihosting** 或自备驱动。
- `freestanding` 必须显式声明，否则编译器会假定有完整 C 库。

## 1. 为什么工具链必须自带"运行时支持库"（builtins），编译器不能凭空生成全部指令？

**答：** 因为有些运算在目标 ISA 上没有对应指令（64 位除法、128 位乘除、位计数、软浮点），编译器只能发一次**函数调用**；被调用的实现就是 builtins，它必须由工具链提供。

- **触发条件**：目标缺少该宽度的运算指令，或选择"库调用比展开序列更省"。
- **典型成员**：`__divdi3`/`__udivdi3`（64 位除法）、`__divti3`（128 位除法）、`__clzdi2`、`__popcountdi2`、软浮点运算。
- **为什么不能内联展开一切**：128 位除法的展开序列上百条指令，代码体积与 I-cache 代价都不可接受。
- **命名约定**：`__<op><mode><type>` 是事实标准，跨编译器互通；改名会让目标文件无法互相链接。

**各家做法**：

- **x86-64**：64 位除法有硬件指令，builtins 主要覆盖 128 位运算与部分位操作。
- **ARM64**：有 64 位除法与多数位操作；128 位除法仍需库调用。
- **RISC-V**：M 扩展提供乘除，未配置时全部走库调用；128 位运算在任何配置下都走库。
- **MIPS**：有 64 位除法（`ddiv`），128 位与位计数需库。
- **SPARC**：V9 有 64 位乘除；位计数需库或扩展指令。
- **PowerPC**：有 64 位乘除，`popcount` 依赖较新实现。

**是统一标准吗**：不是。builtins 的名字有事实约定，**是否触发库调用**由目标能力决定。

## 2. 为什么 builtins 归 `compiler-rt`（或 libgcc），而不归 C 库？

**答：** 因为 builtins 服务的是"编译器生成的代码"，不是"应用程序的编程接口"：它在 `-ffreestanding`、没有 C 库的环境里也必须存在，否则连一条 64 位除法都执行不了。

- **依赖关系**：编译器生成的代码依赖 builtins；C 库依赖编译器与 builtins。层次不能倒置。
- **裸机场景**：没有 libc，也要能算 64 位除法 —— builtins 必须独立可用。
- **实现形态**：通常是一个静态库，按需拉取成员（不用的不被链接进来）。
- **命名来源**：`compiler-rt` 是 LLVM 的实现，`libgcc` 是 GCC 的实现；两者提供同名符号。

**各家做法**：

- **GCC**：`libgcc`（含 builtins、异常展开、软浮点）。
- **LLVM**：`compiler-rt`（builtins + 部分 sanitizer/性能运行时）。
- **MSVC**：运行库与 CRT 合并（`vcruntime` + `ucrt`），builtins 由编译器运行时提供。
- **ARM 32 位**：`__aeabi_*` 一族 ABI 规定的辅助函数，由各工具链实现。
- **RISC-V**：libgcc 与 compiler-rt 都可用，取决于发行配置。
- **嵌入式厂商**：自带运行时库，命名可能不同但对齐 `__aeabi_*` 风格。

**是统一标准吗**：部分统一。符号命名有事实约定（`__aeabi_*`、`__<op>di2`），**由哪家库提供**没有标准。

## 3. 为什么启动代码（`crt0`）必须由工具链/环境提供？

**答：** 因为"把 C 运行环境搭起来"需要知道目标的内存布局与入口约定：设栈指针、清 `.bss`、搬 `.data`、初始化 `gp`/TOC、再调 `main` —— 这些信息只有工具链与平台约定掌握，C 库自己拿不到。

- **必须做的事**：设栈、清 `.bss`、搬 `.data`、调用构造器（`init_array`）、传 `argc/argv`、结束时调用退出路径。
- **为什么不能在 `main` 里做**：`main` 运行时 C 语义已经要求 `.data` 就绪、栈可用。
- **裸机与托管的差异**：裸机还要初始化时钟/串口/异常向量；托管环境由内核完成装载。
- **常见缺陷**：漏清 `.bss` 表现为"全局变量初值随机"；漏搬 `.data` 表现为"初始化值丢失"。

**各家做法**：

- **Linux/glibc**：`Scrt1.o`/`crt1.o` 的 `_start` 调 `__libc_start_main`。
- **musl**：`crt1.o` 的 `_start` 更直接，自己完成大部分环境搭建。
- **裸机/newlib**：`crt0.o` 直接设栈、清 bss、调 `main`，无参数或从固定地址取参数。
- **Windows**：CRT 启动代码（`mainCRTStartup`）初始化堆、运行库与 TLS。
- **RTOS**：由启动文件（汇编 `startup_*.s`）完成向量表与栈设置，再进 `main`。

**是统一标准吗**：不是。入口符号名、初始化顺序、参数来源都由平台约定。

## 4. 为什么链接顺序不能随意改？

**答：** 因为静态库按"从左到右、一次扫描"解析符号：库放在使用者之前，符号还没被引用就不会被拉进来；`crtbegin`/`crtend` 提供构造器表的边界，位置错了初始化就丢。

- **典型顺序**：`crt1` → `crti` → `crtbegin` → 用户目标文件 → 库 → `crtend` → `crtn`。
- **`crti`/`crtn`**：提供 `_init`/`_fini` 的段边界，让构造器能串起来。
- **`crtbegin`/`crtend`**：夹住构造器/析构器表；顺序颠倒会让表被截断。
- **静态库的一次扫描**：`-lfoo -lbar` 与 `-lbar -lfoo` 可能结果不同；循环依赖要用 `--start-group`。
- **为什么链接器不自动重排**：重排会改变符号解析结果，违背"命令行即语义"的原则。

**各家做法**：

- **GNU ld**：严格从左到右扫描静态库，顺序敏感。
- **lld（ELF）**：与 GNU ld 兼容，同样顺序敏感；循环依赖用 `--start-group`。
- **macOS ld64**：顺序敏感，但提供 `-all_load`/`-force_load` 解决"未被引用"问题。
- **MSVC link**：库顺序敏感度较低（默认会多轮解析），但仍建议按依赖顺序。
- **裸机链接**：常显式列出 `crt0.o`、库与链接脚本，顺序即初始化顺序。

**是统一标准吗**：不是。扫描策略是链接器实现，ELF 生态以 GNU 语义为事实标准。

## 5. 为什么静态 PIE 需要"位置无关的 C 库"？

**答：** 因为静态 PIE 的装载基址在运行期才确定，库里任何绝对地址假设都要在启动时被重定位；若库编译时没有生成位置无关代码，重定位项不足以修正它。

- **PIE 的要求**：代码用 PC 相对或 GOT 间接，数据用相对重定位。
- **静态 PIE 的特殊性**：没有 `ld.so`，重定位必须由启动代码自己应用 —— 因此库必须以**可重定位**的形态提供。
- **为什么普通 `libc.a` 不行**：它是按固定地址编译的，绝对寻址指令无法在运行期改。
- **产物形态**：`libc_pic.a`（位置无关的静态库）+ 启动代码自动选择 `-static-pie`。

**各家做法**：

- **glibc**：提供静态 PIE 支持（`rcrt1.o` 一类启动文件）。
- **musl**：支持 `-static-pie`，要求库以 PIC 编译。
- **x86-64 / ARM64 / RISC-V**：工具链普遍支持 `-static-pie`，前提是库为 PIC。
- **MIPS**：GOT/`$gp` 约定使静态 PIE 实现更复杂，支持度较弱。
- **SPARC / PowerPC**：传统上偏向非 PIE，静态 PIE 场景少见。

**是统一标准吗**：不是。ELF 规定重定位机制，**是否支持静态 PIE** 由 C 库与工具链决定。

## 6. 为什么"库的选型"归运行平台，"库的链接"归工具链？

**答：** 因为这是两个不同的问题："用哪个库"取决于环境（裸机没有 glibc，用户态模拟不能跑裸机库）；"库怎么被链接进来"取决于工具链（`crt0`、`sysroot`、链接顺序、PIC 形态）。

- **选型问题**：裸机 → newlib/picolibc；用户态 → musl/glibc；完整系统 → musl/glibc + 动态链接。
- **链接问题**：`-lc` 找哪个目录、`crt0` 从哪来、静态还是动态、要不要 PIC。
- **为什么必须分开写**：合成一册会让"环境差异"和"工具机制"互相打断，读者分不清"是环境限制还是工具限制"。
- **第三段**：库与内核的**接口契约**（syscall 编号、errno、退出方式）归 OS 册。

**各家做法**：

- **裸机**：newlib/picolibc + semihosting 或自备驱动。
- **Linux 用户态**：glibc（功能全、体积大）或 musl（体积小、静态友好）。
- **Android**：bionic（自有 libc，与 glibc 不兼容）。
- **Windows**：ucrt + vcruntime。
- **RTOS**：newlib-nano 或厂商自带精简库。
- **RISC-V 裸机**：picolibc 常见，配 semihosting 做 I/O。

**是统一标准吗**：不是。库的选择是平台决策，链接机制是工具链实现。

## 7. 为什么裸机环境只能走 semihosting（或自备驱动）？

**答：** 因为裸机没有内核：`write`/`open`/`exit` 这些系统调用无处可去；semihosting 让 guest 通过一条特殊陷入把请求交给**宿主调试器/模拟器**，这是唯一不需要写驱动的 I/O 通道。

- **semihosting 的形态**：一条特殊指令（或带 tag 的陷入）+ 约定的参数块，宿主侧实现文件/控制台/退出。
- **为什么不用普通系统调用**：没有内核，`ecall`/`syscall` 没有处理者。
- **替代方案**：直接操作 UART 寄存器（要写驱动），或用内存环形缓冲 + 宿主轮询。
- **退出方式**：`SYS_EXIT` 把退出码传回宿主，构建脚本据此判成败。
- **代价**：semihosting 依赖宿主，脱离调试器就跑不起来；因此只用于测试与开发。

**各家做法**：

- **Arm**：semihosting 用 `SVC` 加固定立即数，服务号表由 Arm 规定。
- **RISC-V**：semihosting 用 `ebreak` + 寄存器约定。
- **本项目**：用 `trap` 的立即数高位做 tag 区分 semihosting 与一般陷入，不进入异常向量。
- **x86**：无 semihosting 传统，裸机多用串口或 `out` 指令。
- **MIPS / SPARC / PowerPC**：裸机多用串口或厂商调试桩。
- **嵌入式 IDE**：厂商调试器常自带 semihosting 实现。

**是统一标准吗**：不是。Arm 与 RISC-V 各有约定，本项目另行定义 tag；**服务号值**部分借用 Arm 的表。

## 8. 为什么 `freestanding` 必须显式声明？

**答：** 因为编译器默认按"有完整 C 库"的托管环境优化：可以假定 `main` 的签名、可以生成对 `memcpy`/`memset` 的调用、可以假定有启动代码；`-ffreestanding` 明确告诉它"这些都不成立"。

- **关闭的假设**：不假定标准库存在、不假定程序入口是 `main`、不把某些循环识别为库调用（或反之保留库调用）。
- **为什么重要**：裸机若不声明，编译器可能生成对 `memcpy` 的调用，而链接时没有 libc → 未定义符号。
- **反向要求**：声明 freestanding 后，标准头里的某些函数不可用，需要自己提供。
- **与 builtins 的关系**：freestanding 仍可用 builtins（那是工具链的一部分），但不能假定 C 库。

**各家做法**：

- **GCC**：`-ffreestanding`。
- **Clang/LLVM**：`-ffreestanding`，语义与 GCC 对齐。
- **MSVC**：无同名开关，用 `/kernel` 或自定义入口近似。
- **嵌入式工具链**：默认接近 freestanding（无托管启动代码）。
- **RTOS 工程**：普遍显式开启，避免隐式库依赖。

**是统一标准吗**：部分统一。`-ffreestanding` 是 GCC/Clang 的共同约定，MSVC 世界没有等价物。

## 背景知识

### 术语与概念

- **builtins**：编译器生成的代码所依赖的辅助函数（`__divdi3` 一类）。
- **compiler-rt / libgcc**：LLVM / GCC 各自的运行时库实现。
- **`crt0`**：启动代码，负责搭 C 运行环境（栈、`.bss`、`.data`、构造器）。
- **`crtbegin`/`crtend`**：构造器表的边界目标文件。
- **sysroot**：交叉编译时目标头文件与库的根目录。
- **静态 PIE**：位置无关的可执行文件，无动态链接器，自行应用重定位。
- **semihosting**：guest 通过特殊陷入把 I/O 请求交给宿主。
- **freestanding**：不假定存在完整 C 库的编译环境。

### 对照

**运行时库归属**

- **GCC**：libgcc。
- **LLVM**：compiler-rt。
- **MSVC**：vcruntime + ucrt。
- **ARM 32 位**：`__aeabi_*` 一族，由各工具链实现。
- **RISC-V**：libgcc 或 compiler-rt（发行配置决定）。

**启动代码**

- **glibc**：`Scrt1.o`/`crt1.o` + `__libc_start_main`。
- **musl**：`crt1.o`，启动逻辑更自包含。
- **newlib/picolibc**：`crt0.o`，裸机直接设栈清 bss。
- **Windows**：`mainCRTStartup`。
- **RTOS**：汇编启动文件 + 向量表。

**库顺序敏感度**

- **GNU ld / lld**：严格从左到右，循环依赖需 `--start-group`。
- **ld64（macOS）**：顺序敏感，`-force_load` 处理未引用成员。
- **MSVC link**：敏感度较低，默认多轮解析。

**裸机 I/O**

- **Arm**：semihosting（`SVC` + 固定立即数）。
- **RISC-V**：semihosting（`ebreak` + 寄存器约定）。
- **本项目**：带 tag 的 `trap`，不进异常向量，直接 `IP += 4` 返回。
- **x86 / MIPS / SPARC / PowerPC**：裸机多用串口或调试桩。
