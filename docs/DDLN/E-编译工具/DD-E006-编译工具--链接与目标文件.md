# 编译工具 -- 链接与目标文件

**本册要点**

- 新 ISA 必须实现自己的目标文件后端：`e_machine`、`e_flags`、重定位语义三者都无法复用。
- 用 **RELA**（显式加数）而非 REL（就地加数），避免"加数藏在被改写的字节里"。
- **重定位类型编号必须冻结**：链接器、目标文件、调试信息都依赖它。
- 链接脚本是内核式构建的必需品：`KEEP`/`PROVIDE`/`ALIGN`/`LONG`/`QUAD`/`ASSERT` 各有其位。
- 去掉 `FILEHDR`/`PHDR` 是为了让映像从段起点开始，与页对齐和引导加载方式一致。
- 动态链接要有 **`.dynamic`/`.dynsym`/`.rela.dyn`/GOT/PLT** 一整套；静态 PIE 只留自解部分。
- 大对象需要 **DWARF64**：32 位偏移放不下时，调试信息无法被工具读取。
- **修正记录的端序与编号**必须与目标一致，否则链接器读到的是错值。

## 1. 为什么面向新 ISA 要实现自己的目标文件后端，而不是复用"通用 ELF 后端"？

**答：** 因为 ELF 只规定了容器格式，真正决定链接行为的是三样东西：`e_machine`（机器标识）、`e_flags`（ABI/特性位）、重定位类型语义；这三样都是每个 ISA 独有的，通用后端无法猜。

- **`e_machine`**：ELF 文件头里的机器编号，链接器据此选择重定位解释规则。
- **`e_flags`**：承载 ABI 版本、指令集扩展、浮点调用约定等；填错会让链接器/加载器按错误假设处理。
- **重定位语义**：同一个"填 32 位"的写法，在不同 ISA 上可能是绝对、PC 相对或 GOT 相对。
- **为什么不能"先借用别的机器号"**：工具链会按借用者的规则解释，调试信息、链接脚本、段属性全部错位。

**各家做法**：

- **x86-64**：`EM_X86_64`，`e_flags` 基本不用。
- **ARM64**：`EM_AARCH64`，`e_flags` 记录 ABI 变体与特性位。
- **RISC-V**：`EM_RISCV`，`e_flags` 记录 RVC（压缩指令）与浮点 ABI。
- **MIPS**：`EM_MIPS`，`e_flags` 承载架构级别与 ABI（信息量最大的一家）。
- **SPARC**：`EM_SPARCV9`，`e_flags` 记录 ABI 与内存模型选项。
- **PowerPC64**：`EM_PPC64`，`e_flags` 记录 ABI 版本（ELFv1/ELFv2）。
- **非 ELF 世界**：Windows 用 COFF/PE，macOS 用 Mach-O —— 容器不同，重定位语义同样各自定义。

**是统一标准吗**：部分统一。ELF 容器格式由 System V gABI 规定；`e_machine` 编号有注册表；**重定位语义与 `e_flags` 位定义由各 ABI 自定**。

## 2. 为什么用 RELA（显式加数），而不是 REL（就地加数）？

**答：** 因为 REL 把加数藏在"被改写的字段"里：链接前必须先把原值读出来加到符号值上，字段宽度不够时就会丢信息；RELA 把加数单独放在重定位项里，计算与检查都干净。

- **REL 的工作方式**：`结果 = 符号值 + 字段原值`，字段既存数据又存加数。
- **RELA 的工作方式**：`结果 = 符号值 + r_addend`，字段只被写、不被读。
- **64 位目标的现实**：字段常放不下完整加数（如 HI/LO 拆分），REL 的"就地读"会截断。
- **对链接器的意义**：RELA 可以并行处理、可以重复应用而不改变语义；REL 需要原地累积。

**各家做法**：

- **x86-64**：RELA（`R_X86_64_*` + `r_addend`）。
- **ARM64**：RELA。
- **RISC-V**：RELA。
- **MIPS**：传统用 **REL**（SGI ABI），加数放在字段里 —— 与其余几家相反。
- **SPARC**：RELA。
- **PowerPC64**：RELA。
- **32 位 x86**：REL，是"REL 仍被使用"的现实例证。

**是统一标准吗**：不是。ELF 同时定义 REL 与 RELA 两种记录，选哪种由 ABI 定。

## 3. 为什么重定位类型的编号必须冻结？

**答：** 因为编号是跨组件的契约：编译器按编号发射、汇编器按编号编码、链接器按编号解释、调试器/反汇编器按编号还原；一旦重排，历史上所有目标文件立刻变成"用错规则解释"。

- **冻结的含义**：已分配的编号永不复用、永不改语义；新类型往后追加。
- **破坏后果**：旧 `.o` 与新链接器混用时，字段被按错误公式填充，错误往往只在特定优化级暴露。
- **为什么不能"按 ISA 版本重排"**：目标文件是**可分发的产物**，会与旧链接器、旧库混用。
- **配套要求**：类型表要有单一真源，机器可读，生成文档与代码。

**各家做法**：

- **x86-64**：编号由 psABI 维护，只增不改。
- **ARM64**：AAELF64 文档固定编号，新增走新号。
- **RISC-V**：psABI 有明确的编号分配流程，社区讨论后冻结。
- **MIPS**：SGI ABI 的编号沿用数十年，新增极少。
- **SPARC**：编号写在 ABI 文档里，长期稳定。
- **PowerPC64**：ELFv1/ELFv2 各自固定一套编号。

**是统一标准吗**：部分统一。ELF 只要求"编号在 ABI 内唯一且稳定"，具体分配由各 ABI 负责。

## 4. 为什么内核式构建离不开链接脚本？

**答：** 因为内核要控制**段的绝对位置与顺序**：入口必须落在约定地址、某些段不能被回收、符号要在链接期生成、对齐与填充要精确到字节 —— 这些都不是默认布局能保证的。

- **`KEEP`**：阻止垃圾回收删掉"没有引用但必须存在"的段（如异常向量表）。
- **`PROVIDE`**：定义链接期符号（如 `__bss_start`），供启动代码引用。
- **`ALIGN`/`LONG`/`QUAD`/`ASSERT`**：控制对齐、写常量表、在布局不满足时直接报错。
- **为什么不用默认脚本**：默认脚本面向用户态可执行文件，段的顺序、对齐、入口都不是内核要的。
- **为什么 `ASSERT` 重要**：布局约束（如"内核映像不超过某大小"）应在链接期失败，而不是运行期暴雷。

**各家做法**：

- **GNU ld / lld**：都实现 GNU 链接脚本语法；内核构建依赖它。
- **x86-64 / ARM64 / RISC-V / MIPS / SPARC / PowerPC 内核**：各有自己的脚本，但用的都是同一套指令集。
- **Windows**：没有链接脚本，用段属性 + `.def` + 链接器选项表达同类约束。
- **macOS**：用段/节顺序与 `-segaddr` 一类选项，能力比脚本弱。
- **裸机项目**：脚本通常只有几十行，但入口、向量表位置、栈段都靠它。

**是统一标准吗**：不是。脚本语法是 GNU 工具链的事实标准，非 ELF 平台各有替代机制。

## 5. 为什么去掉 `FILEHDR`/`PHDR` 会影响加载？

**答：** 因为 ELF 文件头与程序头默认占据映像起始处；引导加载器若按"从段起点开始拷贝"处理，头部会挤占第一个段的位置，导致入口偏移与页对齐全部错位。

- **默认布局**：文件头 + 程序头 + 第一个段，加载器通常按程序头描述搬运，头部不进入内存。
- **去头部的场景**：引导加载器直接把"文件从偏移 0 开始"当作映像，此时头部必须不占位。
- **页大小的作用**：段对齐按页取整；页大小填错会让段之间出现"不该有的间隙"或"重叠"。
- **副作用**：去掉头部后，某些工具无法再把它当普通 ELF 解析 —— 调试与反汇编要用原始二进制模式。

**各家做法**：

- **x86-64 / ARM64 / RISC-V**：常规内核映像保留 ELF 头，由引导加载器解析程序头。
- **MIPS**：常见"裸二进制 + 固定装载地址"的用法，头部处理更敏感。
- **SPARC**：引导格式与 ELF 的对应关系由固件约定。
- **PowerPC**：部分固件要求特定头部（如 PReP/FCH）而非标准 ELF。
- **本项目**：链接脚本显式去掉文件头/程序头，使映像从段起点对齐到页。

**是统一标准吗**：不是。加载方式由固件/引导加载器决定，ELF 只是容器。

## 6. 动态链接需要哪些段与表？

**答：** 需要一整套协作结构：`.dynamic` 说明"有哪些表、在哪"，`.dynsym`/`.dynstr` 提供符号名，`.rela.dyn`/`.rela.plt` 提供重定位，GOT/PLT 提供间接访问与跳板。

- **`.dynamic`**：动态链接的目录，指向符号表、字符串表、重定位表、依赖库列表。
- **`.dynsym` + `.dynstr`**：导出的/需要导入的符号及其名字。
- **`.rela.dyn`**：数据类重定位（全局变量地址、相对重定位）。
- **`.rela.plt` + PLT + GOT**：函数调用的跳板与表项。
- **初始化顺序**：先加载依赖 → 应用重定位 → 再调用初始化函数；顺序错了会用到未填的 GOT。
- **静态 PIE 的差别**：没有 `ld.so`，只保留 `.rela.dyn` 一类自解重定位。

**各家做法**：

- **x86-64**：上述结构齐备；`DT_JMPREL`/`DT_PLTGOT` 分别指向 PLT 重定位与 GOT。
- **ARM64**：结构相同，PLT 桩形态与重定位类型不同。
- **RISC-V**：结构相同，PLT 依赖 `auipc`+`jalr` 序列。
- **MIPS**：GOT 由 `$gp` 常驻指向，动态链接对寄存器约定更敏感。
- **SPARC**：GOT 经 `%l7` 基址，PLT 形态与延迟绑定相关。
- **PowerPC**：TOC 与 GOT 合一，`r2` 常驻，重定位类型分 TOC 相对。

**是统一标准吗**：部分统一。ELF 规定各段的结构与 `DT_*` 标签；**PLT/GOT 的指令序列与寄存器约定由各 ABI 自定**。

## 7. 为什么大对象要用 DWARF64？

**答：** 因为 DWARF32 的段内偏移只有 32 位：调试信息一旦超过 4 GiB（大工程、模板展开、宏展开），偏移就溢出，工具读不出任何调试信息；DWARF64 把偏移扩到 64 位。

- **32 位的硬上限**：`.debug_info` 等段内的引用用 32 位偏移，超限即不可表示。
- **代价**：每个引用变 8 字节，调试信息体积明显增大。
- **何时必须**：单段超过 4 GiB，或工具链整体按 64 位偏移约定生成。
- **与地址宽度的区别**：DWARF64 解决的是"段内偏移"，不是"地址宽度"；64 位地址在 DWARF32 里也能表达，限制在偏移。

**各家做法**：

- **x86-64**：默认 DWARF32，超大工程显式开 DWARF64。
- **ARM64**：同上，DWARF64 按需开启。
- **RISC-V**：同上；部分工具默认仍为 DWARF32。
- **MIPS / SPARC / PowerPC**：DWARF32 为主，超大工程才切 DWARF64。
- **本项目**：默认 DWARF64，属"宁可体积大也不让偏移溢出"的取舍。

**是统一标准吗**：是。DWARF 标准同时定义 32/64 两种格式与切换标记；**默认用哪种是实现选择**。

## 8. 为什么修正记录（fixup）的端序与编号必须与目标一致？

**答：** 因为目标文件里的多字节字段按**目标端序**解释：大端目标若按小端写出，链接器读到的是字节颠倒的值；编号体系若与后端不一致，链接器会按错的公式计算。

- **端序的来源**：目标文件的所有多字节字段（含重定位项、符号值、段头）都遵循 ELF 数据的端序标记。
- **编号的来源**：汇编器在目标文件里写的是"重定位类型编号"，必须与链接器认的表一致。
- **典型症状**：数值"看起来差了一个字节序"（如 `0x1234` 变 `0x3412`），或偏移整体错位。
- **为什么容易漏**：小端机器上开发、大端目标上运行时才暴露；单测若只在小端跑就发现不了。

**各家做法**：

- **x86-64 / RISC-V（小端）/ ARM64（可双端）/ MIPS（可双端）**：端序由 ELF 头标记，工具必须双向支持。
- **SPARC / PowerPC**：历史上以大端为主，端序处理是常态。
- **ELF 规范**：`EI_DATA` 字段显式标记端序，工具应据此解释而非假定宿主端序。
- **LLVM 的教训**：目标描述里若把端序写死在生成物中，跨端构建才会暴露。
- **本项目的取舍**：目标为大端，因此端序相关代码路径必须显式测试。

**是统一标准吗**：是。ELF 规定端序标记字段与"按标记解释"的规则；**实现是否真的遵守**才是缺陷来源。

## 背景知识

### 术语与概念

- **ELF**：可执行与可链接格式，规定文件头、段/节、符号表、重定位记录的容器结构。
- **`e_machine` / `e_flags`**：机器编号与 ABI/特性标志位。
- **REL / RELA**：就地加数 / 显式加数的重定位记录。
- **链接脚本**：描述段布局、符号定义与布局断言的脚本语言。
- **`FILEHDR`/`PHDR`**：文件头与程序头；决定映像起始偏移。
- **`.dynamic` / `.dynsym`**：动态链接目录与动态符号表。
- **GOT / PLT**：全局偏移表 / 过程链接表。
- **DWARF32 / DWARF64**：调试信息的两种偏移宽度格式。
- **fixup**：汇编阶段记录的"待修正字段"，最终转化为重定位。

### 对照

**加数模型**

- **x86-64 / ARM64 / RISC-V / SPARC / PowerPC64**：RELA。
- **MIPS / 32 位 x86**：REL。
- **取舍**：RELA 干净、可重复应用；REL 依赖字段原位，宽度受限。

**重定位编号的稳定性**

- **x86-64 / ARM64 / RISC-V**：psABI/AAELF 固定编号，只增不改。
- **MIPS**：SGI ABI 编号沿用数十年。
- **SPARC / PowerPC64**：ABI 文档固定，ELFv1/v2 各一套。
- **共同点**：编号是跨组件契约，破坏即不兼容。

**布局控制手段**

- **ELF 平台**：GNU 链接脚本（`KEEP`/`PROVIDE`/`ALIGN`/`ASSERT`）。
- **Windows**：段属性 + `.def` + 链接器选项。
- **macOS**：段/节顺序与 `-segaddr` 一类选项。
- **裸机**：脚本控制入口、向量表、栈段。

**调试信息宽度**

- **x86-64 / ARM64 / RISC-V**：默认 DWARF32，超大工程切 DWARF64。
- **MIPS / SPARC / PowerPC**：以 DWARF32 为主。
- **本项目**：默认 DWARF64。
- **判据**：单段是否可能超过 4 GiB。

**端序**

- **小端为主**：x86-64、RISC-V（常见配置）、ARM64（常见配置）。
- **大端为主**：SPARC、PowerPC（历史上）。
- **双端支持**：ARM64、MIPS 的多种实现。
- **规则**：一律按 ELF 头的端序标记解释，不假定宿主端序。
