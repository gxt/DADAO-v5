# 编译工具 -- 编译器后端

**本册要点**

- 后端先立**骨架**：值类型 + 寄存器类 + 指令描述，再谈优化；骨架错了，选择规则无处落。
- **窄整数要有 canonical 形式**，否则每次使用都要重新判断高位是否有效。
- **合法化**把"目标不支持的类型/操作"拆成支持的序列，选择器只面对规范形态。
- `setcc` 与 `select_cc` 是两种模式：产生布尔 vs 融合成条件写回。
- **跳转表**是"只读数据 + 间接跳转"，必须单独 lowering。
- 内联汇编的核心是**约束绑定**与它对寄存器分配的约束。
- `asm goto` 把控制流边界带进后端，难度在"建图时就要知道多个后继"。
- TLS 与原子要按**模型/粒度**选实现，选错会退化成库调用或静默不原子。
- 浮点与位操作接线要处理"特殊值寄存器"（如 `rf0`）与"无原生指令时拆序列"。

## 1. 为什么后端要先立"值类型 + 寄存器类"的骨架，而不是直接写指令选择？

**答：** 因为指令选择规则的作用对象是"某个值类型 × 某个寄存器类"的组合；类型与类别没定，规则就没有落点，写出来的选择器只能靠字符串匹配助记符。

- **寄存器类的意义**：同类寄存器可互换，跨类不可直接互换（需要搬运指令）；类分得越粗，分配越自由但合法化越重。
- **本项目的两类整数寄存器**：`rd`（数据）与 `rb`（基址）分离 —— 访存只能用 `rb`，算术结果在 `rd`，跨类搬运是显式指令。
- **值类型的意义**：i1/i8/i16/i32/i64/f32/f64/f128 各自可用的寄存器类与合法操作不同。
- **为什么不能"按指令助记符选"**：同一助记符在不同操作数形态下结果类型不同，按名字匹配无法表达约束。

**各家做法**：

- **x86-64**：GR8/GR16/GR32/GR64 与 XMM/MMX 等类；部分寄存器写会引入合并问题。
- **ARM64**：`W`/`X` 是同一寄存器的两种视图，写 `W` 自动清零高位。
- **RISC-V**：整数 `X` 与浮点 `F` 分离，无窄寄存器视图（值恒在 XLEN 宽）。
- **MIPS**：GPR 与 FPR 分离，32/64 位由指令后缀区分。
- **SPARC**：整数寄存器窗口（`%g/%o/%l/%i`）+ 浮点寄存器，窗口切换影响可见性。
- **PowerPC**：GPR/FPR/VR 分离，条件寄存器 CR 单独成类。

**是统一标准吗**：不是。寄存器分类与"是否有窄视图"由各 ISA 决定，标准只管编码。

## 2. 为什么窄整数要有 canonical 扩展形式？

**答：** 因为同一位宽的值会在多处被使用，如果每次使用都临时判断"高位是否有意义"，优化与寄存器分配都无法稳定；定一个 canonical 形式（把窄值扩展到一个确定的宽度并记录语义），后续只需在边界处转换。

- **为什么需要**：i8 的加法在 64 位寄存器里算，高位是垃圾还是符号扩展，决定了后续比较与移位是否正确。
- **canonical 化的代价**：扩展指令可能变多；但换来"同一值只有一种表示"，CSE 与 RA 才有意义。
- **边界处的转换**：load 时按符号/零扩展定形；store 时按位宽截断。
- **缺陷形态**：缺 canonical 化时典型 bug 是"某条路径高位没清"，表现为 O1 对、O2 错。

**各家做法**：

- **x86-64**：部分寄存器写（`al`/`ax`）不自动清高位，需显式 `movzx`/`movsx`，历史上产生部分寄存器合并停顿。
- **ARM64**：写 `W` 寄存器自动零扩展到 64 位，canonical 形式天然成立。
- **RISC-V**：没有窄寄存器，窄值靠 `slli`/`srai` 成对做符号扩展。
- **MIPS**：load 自带符号/零扩展；64 位下的 32 位算术（`ADDW` 一类）结果按符号扩展定形。
- **SPARC**：32 位运算在 64 位寄存器中的高位处理**待核手册**（不同实现与指令变体写法不一）。
- **PowerPC**：32 位结果写 GPR 时高位未定义（架构允许），需显式扩展。

**是统一标准吗**：不是。是否"写窄即清高位"由各架构规定，直接决定 canonical 化的工作量。

## 3. 为什么需要"合法化"阶段，而不是让选择器直接面对所有类型与操作？

**答：** 因为目标只支持有限的类型与操作组合；合法化先把不支持的东西拆成支持的（i128 拆两条 i64、f16 升 f32、除法换库调用），选择器只需处理规范形态。

- **合法化做三件事**：类型合法化（拆/升）、操作合法化（换序列或库调用）、调用约定合法化（参数拆分与重排）。
- **为什么必须在校验之前**：选择器面对的类型集合越小，规则越少，越不容易漏。
- **代价**：拆分可能引入额外寄存器压力与栈流量，需要后续优化回收。
- **缺陷形态**：漏合法化时表现为"某类型在某个优化级下崩溃/错译"。

**各家做法**：

- **LLVM**：`LegalizeTypes` + `LegalizeDAG` 两级，之后才进指令选择。
- **GCC**：`expand` 阶段把 GIMPLE 降到 RTL，靠 `optabs` 查"目标是否支持该操作"。
- **x86-64**：i128 拆成两条 i64；x87 与 SSE 混合时还需类型提升。
- **ARM64**：i128 拆对；无硬件 f16 时提升为 f32。
- **RISC-V**：无硬件浮点或原子时降为库调用。
- **MIPS**：软浮点与硬浮点两套 ABI，合法化结果不同。

**是统一标准吗**：不是，纯实现结构；标准只规定"结果必须正确"。

## 4. 为什么 `setcc` 与 `select_cc` 要分开处理？

**答：** 因为"比较产生布尔"与"比较后选值"是两种使用模式：前者结果要能被分支或逻辑运算消费，后者希望融合成条件移动/条件写回；融合是否可行取决于 ISA 有没有条件寄存器或条件指令。

- **`setcc`**：产生 0/1 或标志位，供后续分支/位运算使用。
- **`select_cc`**：比较 + 选值一步完成；没有条件移动的 ISA 上会退化成"分支 + 两个块"。
- **为什么不能总是融合**：融合要求两个候选值都能无副作用地求值，否则必须保留分支。
- **本项目的特点**：有"条件写回"形态（指令带条件标记），`select_cc` 可以落到单条指令；纯分支 ISA 则必须走分支。

**各家做法**：

- **x86-64**：`setcc` 产生字节 0/1；`cmovcc` 做条件移动（要求两值已就绪）。
- **ARM64**：`cset`/`csel`/`csinc` 一族，条件选择是一等指令。
- **RISC-V**：只有分支与 `slt` 系列，没有条件移动（`select` 需分支）。
- **MIPS**：只有分支与 `slt`，无通用条件移动。
- **SPARC**：条件码 + 条件移动（v9 的 `movcc` 一族）。
- **PowerPC**：条件寄存器 CR + `isel`（较新实现）或分支。

**是统一标准吗**：不是。是否提供条件移动/条件写回，直接改变 `select_cc` 的代价模型。

## 5. 为什么跳转表（`br_jt`）要单独 lowering？

**答：** 因为它是"只读数据 + 间接跳转"的组合：表要在数据段生成、条目宽度与重定位要处理、跳转前还要算出目标地址，这些都不是普通分支指令能表达的。

- **表的内容**：目标块地址（绝对或相对）；相对表更利于位置无关代码。
- **条目宽度**：与指针宽度、重定位类型绑定；宽度选错会让重定位越界。
- **间接跳转的前置计算**：先取表项，再跳到表项内容；位置无关时还要加基址。
- **为什么不能展开成 if 链**：分支数多时 if 链的指令数与分支预测代价都不可接受。

**各家做法**：

- **x86-64**：`jmp *table(,%rax,8)`，表项为绝对地址或相对偏移。
- **ARM64**：`adr` 取表基址 + `ldr` 取项 + `br` 跳转；PIC 下用相对项。
- **RISC-V**：`auipc` + `ldr`/`lw` 取相对项 + `jalr`，天然位置无关。
- **MIPS**：`jr` + 表项；PIC 下需 `gp` 相对或绝对重定位。
- **SPARC**：`jmp %g1 + offset`，表项为偏移。
- **PowerPC**：`bctr` 间接跳转 + 表项偏移。

**是统一标准吗**：不是。表项格式与重定位方式由各平台 ABI 与目标文件格式决定。

## 6. 为什么内联汇编的核心是"约束绑定"？

**答：** 因为内联汇编不是"嵌进一段文本"那么简单：编译器必须知道哪个 C 变量进哪个寄存器/内存、哪些寄存器被改写、能否与前后的代码重排；这些都由约束字符与 clobber 列表表达，错误绑定会静默改错值。

- **约束字符的含义**：`r` 通用寄存器、`m` 内存、`i` 立即数、`n` 常量；每种都影响寄存器分配与指令选择。
- **clobber 列表**：声明"这段汇编破坏了哪些寄存器"，后端据此避免把它们分给活跃值。
- **为什么 `m` 最难**：内存操作数要保证地址可用，且不能与同块内的其它内存访问重排。
- **本项目现状**：约束仅支持 `r/m/i/n` 四类；`m` 约束曾有崩溃缺陷，属已知缺口。

**各家做法**：

- **GCC**：约束最丰富（含修饰符 `=`/`+`/`&`、多候选约束），且允许机器相关约束。
- **LLVM（clang）**：约束集由目标定义，x86 与 ARM 覆盖较全，新目标常只实现少数几类。
- **MSVC**：`__asm` 块（x86）与约束语法差异大，ARM64 不支持内联汇编块。
- **RISC-V**：GCC 与 LLVM 都只支持有限约束集，扩展约束需两边同步。
- **ARM64**：标准约束 + `Q`（内存）等修饰，LLVM 与 GCC 口径需对齐。

**是统一标准吗**：不是。约束字符是编译器扩展，各编译器与各目标自行定义。

## 7. 为什么 `asm goto` 比普通内联汇编难？

**答：** 因为它把"控制流出口"带进了后端：普通内联汇编只有一个出口（顺序往下），`asm goto` 有多个后继块；后端必须在**建图阶段**就知道这些边，还要处理"内联块里的输出在跳转后是否有效"。

- **多后继的代价**：SelectionDAG 是基本块内结构，跨块边要在建图时显式登记，否则调度与寄存器分配会按"无后继"处理。
- **带输出的额外难点**：输出值要在跳转前写回指定位置，而跳转目标可能有多个，写回语义必须对所有后继一致。
- **已知缺陷形态**：带输出的 `asm goto` 在部分实现上直接断言失败，编译器探针因此判定"不支持"。
- **本项目现状**：`asm goto` 无输出的情形可用；带输出的情形是已知缺口。

**各家做法**：

- **GCC**：`asm goto` 支持较早，带输出支持较晚（需要额外的标签与写回约定）。
- **LLVM**：`asm goto` 支持多年，但"带输出"的支持按目标推进，新目标常滞后。
- **MSVC**：无 `asm goto` 等价物。
- **RISC-V / ARM64**：GCC 与 LLVM 两组实现的支持程度不完全一致，需分别核对。
- **内核场景**：内核大量使用 `asm goto` 做静态分支键（static key），"带输出不支持"会直接让探针失败。

**是统一标准吗**：不是，是编译器扩展，且各实现的支持边界不同。

## 8. 为什么 TLS 与原子要按"模型/粒度"选实现？

**答：** 因为两者都不是单一指令能覆盖的：TLS 有四种访问模型（代价从一条指令到一次函数调用），原子有一组指令与一组库调用，选错就会静默退化。

- **TLS 模型**：local-exec（最省）、initial-exec、general-dynamic（要调 `__tls_get_addr`）、local-dynamic。
- **选择依据**：模块是主程序还是共享库、能否假定加载时已知偏移。
- **原子的两条路**：有原生 LR/SC 或原子指令时内联；否则生成 `__atomic_*` 库调用（语义相同，代价不同）。
- **为什么粒度重要**：同一段代码里的原子操作若一部分内联、一部分库调用，会在混用锁与无锁时出现语义裂缝。
- **本项目现状**：原子按 LR/SC + `fence` 实现；动态 TLS 与 `dlopen` 场景需要 general-dynamic 路径。

**各家做法**：

- **x86-64**：TLS 用 `fs` 段基址，模型差异体现在偏移量与是否调用；原子有 `lock` 前缀。
- **ARM64**：TLS 用 `tpidr_el0` + `mrs`；原子用 `ldaxr/stlxr`（LSE 扩展另有 `ldadd` 等）。
- **RISC-V**：TLS 用 `tp` 寄存器；原子用 `lr/sc` 或 `amo*`（A 扩展）。
- **MIPS**：TLS 通过 `$28`（gp）与专用序列；原子用 `ll/sc`。
- **SPARC**：TLS 用 `%g7`；原子用 `cas`/`swap`（v9）。
- **PowerPC**：TLS 用 `r13`；原子用 `lwarx/stwcx`。

**是统一标准吗**：不是。TLS 模型与原子指令集都是各架构自定，只有内存模型的语义受语言标准约束。

## 9. 为什么浮点与位操作的"接线"也要专门处理？

**答：** 因为这类指令常带"架构专有的特殊约定"：特殊值寄存器（`rf0` 同时是 qNaN 与状态寄存器）、无原生指令时要拆序列、以及操作数顺序/舍入模式的位置。

- **特殊值寄存器**：`rf0` 既是"读作 qNaN 的常量零位"，又承载浮点状态位（异常标志、舍入模式），读写语义必须分开。
- **无原生指令时**：`ctlz`/`cttz`/`ctpop` 在无对应指令的 ISA 上要拆成位运算序列或查表。
- **位操作的"半宽"问题**：`clmul` 只在 64 位上定义时，窄位宽要做扩展与截断。
- **接线错误的典型形态**：操作数顺序颠倒（浮点比较/减法）、舍入模式未随指令走、特殊值被当普通寄存器分配。

**各家做法**：

- **x86-64**：浮点状态在 `MXCSR`/`x87` 状态字，与数据寄存器分离；`popcnt`/`lzcnt`/`tzcnt` 有原生指令。
- **ARM64**：`FPCR` 管舍入与异常；`clz`/`rbit` 原生；`clmul` 需 crypto 扩展。
- **RISC-V**：`fcsr` 管舍入与标志；`clz`/`ctz`/`cpop` 在 Zbb 扩展；`clmul` 在 Zbc。
- **MIPS**：FCSR 管状态；位计数需软件序列（无原生指令）。
- **SPARC**：浮点状态寄存器 FSR；`popc` 在 v9 可用。
- **PowerPC**：FPSCR 管状态；`cntlz` 原生，`popcnt` 较新实现才有。

**是统一标准吗**：部分统一。浮点异常标志与舍入模式由 IEEE 754 规定语义，但**寄存器组织与指令形式**各家自定。

## 背景知识

### 术语与概念

- **指令选择（ISel）**：把中间表示的模式映射成目标指令。
- **合法化（Legalize）**：把目标不支持的类型/操作转换成支持的形态。
- **寄存器类**：可互换的寄存器集合；跨类需要显式搬运。
- **canonical 形式**：同一语义值的唯一表示（如窄值统一扩展到某宽度）。
- **`setcc` / `select_cc`**：比较产生布尔 / 比较并选值。
- **跳转表**：以数据表存目标地址或偏移，配合间接跳转。
- **约束（constraint）**：内联汇编里声明操作数位置与类型的字符。
- **clobber**：内联汇编声明会被破坏的寄存器/内存。
- **TLS 模型**：线程局部存储的访问方式（local-exec / initial-exec / general-dynamic / local-dynamic）。
- **LR/SC**：加载保留 / 条件存储，构成原子读改写对。

### 对照

**寄存器分类与窄视图**

- **x86-64**：GR8/16/32/64 + XMM；窄写不自动清高位。
- **ARM64**：W/X 同寄存器双视图，窄写自动零扩展。
- **RISC-V**：X/F 分离，无窄视图。
- **MIPS**：GPR/FPR 分离。
- **SPARC**：整数窗口寄存器 + 浮点寄存器。
- **PowerPC**：GPR/FPR/VR + 条件寄存器 CR。

**条件选择能力**

- **x86-64**：`setcc` + `cmovcc`。
- **ARM64**：`cset`/`csel` 一族。
- **RISC-V**：仅分支 + `slt`。
- **MIPS**：仅分支 + `slt`。
- **SPARC**：条件码 + `movcc`。
- **PowerPC**：CR + `isel` 或分支。

**64 位常量与高位运算**

- **x86-64**：`movabs`；`mul` 产出 `rdx:rax`。
- **ARM64**：`movz`+`movk`；`umulh`/`smulh` 取高半。
- **RISC-V**：`lui`+`addi`；`mulh*` 取高半。
- **MIPS**：`lui`+`ori`；`multu` + `mfhi`。
- **SPARC**：`sethi`+`or`；`mulx`。
- **PowerPC**：`lis`+`ori`；`mulld`+`mulhd`。

**TLS 与原子**

- **x86-64**：`fs` 段 + `lock` 前缀。
- **ARM64**：`tpidr_el0` + `ldaxr/stlxr`。
- **RISC-V**：`tp` + `lr/sc`、`amo*`。
- **MIPS**：`$28` + `ll/sc`。
- **SPARC**：`%g7` + `cas`。
- **PowerPC**：`r13` + `lwarx/stwcx`。

**内联汇编支持面**

- **GCC**：约束集最全，`asm goto` 带输出支持较早。
- **LLVM**：按目标推进，新目标常只实现少数约束。
- **MSVC**：无 `asm goto`；ARM64 不支持内联汇编块。
- **RISC-V / ARM64**：两套实现的支持边界需分别核对。
- **本项目**：约束仅 `r/m/i/n`；`asm goto` 带输出为已知缺口。
