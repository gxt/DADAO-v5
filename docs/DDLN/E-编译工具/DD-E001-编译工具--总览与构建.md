# 编译工具 -- 总览与构建

**本册要点**

- 工具链的第一问题是**可复现**：组件按 commit 锁定，不按 tag/branch。
- `triple` 决定数据布局、默认调用约定与目标特性，是新目标的入口。
- 四类工具（编译 / 汇编 / 链接 / 二进制工具）按**输入输出边界**划分，可分段验证。
- **安装根**（prefix / sysroot）把"构建产物"与"查找路径"分开，多版本才能并存。
- 本地改动用**补丁树**（一文件一补丁）而非 fork，才能跟上上游。
- 选 LLVM 而不是 GCC，换来统一描述与库化结构，代价是工具覆盖与边角特性要自己补。
- 构建门控分层（快 / 中 / 全），代价与覆盖面匹配。

## 1. 为什么工具链要先谈"组件基线锁定"，而不是先讲编译器算法？

**答：** 因为工具链里最大的不可控量不是算法，而是"你用的到底是哪一版组件"：同一个源文件、同一组选项，如果编译器/汇编器/链接器换了版本，产物与行为就可能不同。锁定到 commit 才能让"缺陷—产物—源码"三者一一对应。

- **锁 commit 而不是 tag**：tag 可以被移动、可以重打；branch 会随上游前进。commit 哈希是内容寻址，天然不可变。
- **为什么不是"发版号"**：发版号（如 20.1.0）对应一个区间内的多次提交，发行包还带厂商补丁，无法定位"到底哪次改动改了行为"。
- **为什么要多源**：编译器、汇编器/链接器、模拟器、C 库分属不同上游，"统一版本号"不存在，只能各自锁。
- **代价**：升级从"改一行版本号"变成"读 diff、重放本地补丁、重跑全套向量"；换来"任意一次历史构建都能重来"。

**各家做法**：

- **GCC / 发行版**：以 release tarball 为单元，发行版再叠补丁集（Debian `debian/patches`、RHEL 补丁包）——版本以发版号为准。
- **LLVM 上游**：monorepo 单仓多项目，可按 commit 锁定；发行包另有 release tag。
- **Apple clang**：整棵分支 fork，随 Xcode 版本发布，内部 commit 不外露。
- **Android NDK**：同样按 NDK 版本锁定 fork，工具集随版本整体替换。
- **RISC-V**：GCC 与 LLVM 双线并行，改动倾向拆小后合入上游，而不是长期分叉。
- **MSVC**：随 Visual Studio 版本发布，不提供 commit 粒度。

**是统一标准吗**：不是，各家不同。共同点只有"可复现构建"这一目标。

## 2. 为什么 target 注册（`triple`）是独立的一步？

**答：** 因为一个编译器二进制要同时服务多个目标，`triple` 是"用哪套数据布局、哪套默认调用约定、开哪些目标特性"的唯一开关；没有它，后端无法在编译期选对代码生成规则。

- **triple 的形态**：`arch-vendor-os-env`；它决定字长与端序（写进数据布局）、指针宽度、默认 code model、可用寄存器与 ABI 变体、可执行格式（ELF/Mach-O/COFF）。
- **为什么不能用一个"开关集合"代替**：目标差异是**编译期生成**的（指令选择表、寄存器类、调用约定 lowering 都是生成的代码），不是一个运行时布尔量。
- **为什么"新目标"往往先卡在这一步**：triple 注册不上，`-target` 直接报未知目标，后面所有工作都跑不起来。

**各家做法**（六家 triple 形态）：

- **x86-64**：`x86_64-unknown-linux-gnu`；同架构还有 `-pc-windows-msvc` 等变体。
- **ARM64**：`aarch64-unknown-linux-gnu`；裸机环境常用 `aarch64-none-elf`。
- **RISC-V**：`riscv64-unknown-elf`（裸机）或 `riscv64-unknown-linux-gnu`。
- **MIPS**：`mips64el-linux-gnuabi64`——`el` 表示小端，`abi64` 表示 64 位 ABI 变体。
- **SPARC**：`sparc64-unknown-linux-gnu`。
- **PowerPC**：`powerpc64le-unknown-linux-gnu`——`le` 直接写进 arch 字段。
- **MSVC**：没有 triple 概念，用 `/arch` + 平台 SDK 组合。

**是统一标准吗**：不是。triple 字符串本身无标准（GNU 惯例）；ELF 的 `e_machine` 有标准（System V gABI），两者需人工对齐。

## 3. 为什么把工具分成"编译 / 汇编 / 链接 / 二进制工具"四类？

**答：** 因为四类的**输入输出边界**不同：源码 → 汇编文本 → 目标文件 → 可执行/共享对象 → 检查与改写。边界清楚，才能分段验证、单独替换。

- **编译器**：C/C++ → 汇编或目标文件；负责优化与寄存器分配。
- **汇编器**：汇编文本 → 目标文件；负责编码、重定位记录。
- **链接器**：多个目标文件 + 库 → 可执行/共享对象；负责符号解析、重定位应用、段布局。
- **二进制工具**：`objdump`/`readelf`（看）、`objcopy`（改）、`ar`/`ranlib`（归档）、`strip`（去符号）。
- **为什么汇编器与反汇编器必须共享描述**：编码表只应有一份真源；描述一致，"汇编→反汇编→汇编"才可能逐字节相同。这是把 MC 层做成独立组件的根本理由。
- **为什么这层划分对教学有价值**："编译错"和"编码错"是两类完全不同的缺陷，分段才能定位。
- **后端与汇编器共用一套数据指示符集合**：后端只准发射、汇编器必须受理同一套写法（命名与宽度取舍见「汇编语言」册）。

**各家做法**：

- **GNU binutils**：`as`/`ld`/`objdump`/`ar` 一组独立程序，各自命令行。
- **LLVM**：MC 层做成库，`llvm-mc`/`llvm-objdump`/`lld` 只是其外壳；汇编器与反汇编器同源。
- **MSVC**：`cl`/`ml`/`link`/`lib`/`dumpbin` 分工，`cl` 可直调链接器。
- **嵌入式厂商**：IAR/Keil 等把编译-汇编-链接封在 IDE 里，命令行工具仍存在但很少单独使用。

**是统一标准吗**：划分本身通用（各家都有四类），**集成度**各家不同。

## 4. 为什么有"安装根"（prefix / sysroot）约定？

**答：** 因为驱动必须按**固定布局**去找头文件、库与子工具；安装根把"产物放哪"与"运行时去哪找"分开，才能让多个工具链版本在同一台机器上并存。

- **典型布局**：`bin/`（编译器、汇编器、链接器）、`include/`（C 头）、`lib/`（运行库、内置头目录）、`share/`（脚本与描述）。
- **`sysroot` 的作用**：交叉编译时目标系统的头文件与库从这里找，而不是沿用宿主 `/usr/include` —— 否则会把宿主的 glibc 头混进目标构建。
- **为什么不能只靠 `PATH`**：`PATH` 决定"调哪个程序"，不决定"头与库从哪来"；混用会出现"用 A 版编译器 + B 版头文件"的静默错配。
- **为什么强调"只有安装动作写安装根"**：手工往安装根里拷二进制，会出现"构建树已更新、安装根还是旧的"，门控读到旧产物而假绿。

**各家做法**：

- **GCC**：`--prefix` + 交叉前缀命名（`aarch64-linux-gnu-gcc`），布局随 prefix。
- **LLVM**：`--prefix` 或安装前缀变量；`bin/`/`lib/clang/<ver>/include` 结构固定。
- **Linux 发行版**：交叉工具链常放 `/usr/<triple>/`，宿主工具在 `/usr/bin`。
- **嵌入式 SDK**：自带 `sysroot/` 子目录，整个目录可整体搬移。
- **MSVC**：无 `sysroot` 概念，靠 Windows SDK 的注册路径。

**是统一标准吗**：不是。`bin/ lib/ include/` 只是 FHS 的惯例，交叉布局各发行版仍有差异。

## 5. 为什么本地改动用"补丁树"，而不是维护一个 fork 分支？

**答：** 因为 fork 一旦分叉，每次上游更新都要人工合并整棵分支；补丁树把改动压成"一文件一补丁"，既能机械重放，也能逐条审查与丢弃。

- **一文件一补丁的好处**：改动边界与文件边界一致，冲突时只影响那一个文件；补丁能进版本库、能被门控校验"每个补丁都还在"。
- **代价**：上游重构会让补丁失效，需要重新生成；补丁数一多，重放顺序成为隐式依赖。
- **什么时候 fork 更合适**：改动面覆盖整个组件（如换后端架构）、或需要长期偏离上游（厂商私有扩展）时，fork 的维护成本反而低。

**各家做法**：

- **Debian / Ubuntu**：`debian/patches` 系列 + `series` 文件决定顺序。
- **RPM 系（Fedora/RHEL）**：spec 里的 `%patch` 列表。
- **Yocto / Buildroot**：`.patch` 文件 + 构建配方引用。
- **Apple / Android**：直接维护 fork，不与上游逐补丁同步。
- **RISC-V**：改动拆小后逐步合入上游，减少长期分叉。
- **Debian 内核**：补丁集 + 单一源码包，属"补丁树"的极端规模化用法。

**是统一标准吗**：不是，纯工程约定。

## 6. 为什么选 LLVM 而不是 GCC？

**答：** 因为 LLVM 把"指令描述、汇编/反汇编、目标注册"统一在 TableGen 与库化结构里，改一处描述就能同步影响编码器、汇编器与反汇编器；代价是工具覆盖与边角特性不如 GCC 成熟，缺的东西要自己补。

- **单一描述真源**：格式类、寄存器类、指令语义都在 TableGen 里，改编码位域不用同步改三份代码。
- **库化**：编译器、汇编器、链接器、反汇编器都是库的上层外壳，便于在同一进程里复用与做工具（如自定义检查器）。
- **许可**：Apache-2.0 with LLVM exception，对链接与再分发约束小；GCC 为 GPLv3，带传染性。
- **诊断与工程性**：错误信息定位、增量构建、模块化测试（`lit`）更友好。
- **代价一：工具清单不全**。`ar`/`ranlib`/`strip` 的 LLVM 版本需要单独就位，否则静态库归档与去符号仍要靠 GNU 工具临时顶。
- **代价二：边角特性晚到**。内联汇编约束种类、`asm goto` 带输出的支持、内核式 `-mcmodel` 变体，往往落后于 GCC。
- **代价三：社区口径差异**。某些平台的 ABI 细节以 GCC 实现为事实标准，LLVM 需对齐。

**各家做法**：

- **GNU / GCC**：工具覆盖最全（编译器 + binutils + libstdc++ + 完整内联汇编约束），GPLv3。
- **Apple**：Xcode 全面转向 clang，Objective-C/Swift 生态绑定 LLVM。
- **Android**：NDK 已移除 GCC，默认 clang；工具集随 NDK 版本替换。
- **FreeBSD**：基础系统默认 clang/LLVM，GCC 作为可选包。
- **RISC-V**：GCC 与 LLVM 双线，ABI 以规范为准，两边都必须过同一套测试。
- **PowerPC / MIPS / SPARC**：GCC 仍是主流，且部分老平台只有 GCC 能完整覆盖。

**是统一标准吗**：不是，各家不同。ABI 与目标文件格式有标准（gABI、ABI 规范），而"用哪套编译器"是工程选择。

## 7. 为什么构建门控要分层（快 / 中 / 全）？

**答：** 因为检查代价差两三个数量级，而缺陷的发现时机比检查的完备性更重要：秒级检查每次改都跑，分钟级检查收尾跑，全量检查里程碑跑。

- **三层的定位**：完整性 + 冒烟（秒级）→ 模块代表集（分钟级）→ 较完整/全量（小时级）。
- **为什么必须"能在改动后立刻跑"**：工具链回归常是"一个编码位错导致全表错"，慢门控跑不动就等于没有。
- **为什么不能只留最全的一层**：全量检查的反馈周期比一次改动还长，开发者会绕过它。

**各家做法**：

- **LLVM**：`lit` 按目录与 feature 标签分组（MC / CodeGen / 回归用例），可只跑子集。
- **GCC**：DejaGnu 按 `dg-do run` / 编译期检查分档，另有 torture 集。
- **Linux 内核**：`selftests` 有快速子集，全量按子系统单独跑。
- **Rust**：`cargo test` 分单元 / 集成 / doc 测试。
- **CMake 项目**：`ctest -L` 按标签分层。

**是统一标准吗**：不是，纯工程方法；共同点只有"多级粒度 + 明确触发点"。

## 背景知识

### 术语与概念

- **工具链（toolchain）**：把源码变成可运行产物的工具集合（编译器、汇编器、链接器、二进制工具、运行库）。
- **triple**：目标描述串 `arch-vendor-os-env`，编译器据此选数据布局与目标实现。
- **sysroot**：交叉编译时目标系统头文件与库的根目录。
- **安装根（prefix）**：工具链自身的安装位置（`bin/`、`lib/`、`include/`）。
- **补丁树 / patch series**：把本地改动拆成按文件排列的补丁集合，可机械重放。
- **MC 层**：汇编器/反汇编器共享的编码描述层；编码表是唯一真源。
- **归档（archive）**：多个目标文件打成的库文件（`ar` 格式），`ranlib` 为其建符号索引。
- **数据指示符（directive）**：汇编里"往目标文件放数据"的伪操作，如 `.dd.o64`。
- **门控（gate）**：可自动判定的检查，分快/中/全三层。

### 对照

**四类工具的划分**

- **GNU binutils**：`as`/`ld`/`objdump`/`ar` 一组独立程序。
- **LLVM**：MC 层为库，`llvm-*` 一族为外壳，汇编与反汇编同源。
- **MSVC**：`cl`/`ml`/`link`/`lib`/`dumpbin` 分工。
- **嵌入式厂商**：封进 IDE，命令行工具存在但不常用。

**triple 与目标标识**

- **x86-64**：`x86_64-unknown-linux-gnu`。
- **ARM64**：`aarch64-unknown-linux-gnu`。
- **RISC-V**：`riscv64-unknown-elf`。
- **MIPS**：`mips64el-linux-gnuabi64`。
- **SPARC**：`sparc64-unknown-linux-gnu`。
- **PowerPC**：`powerpc64le-unknown-linux-gnu`。
- **共同点**：triple 字符串无标准，ELF `e_machine` 有标准（gABI）。

**安装布局**

- **GCC**：`--prefix` + 交叉前缀命名。
- **LLVM**：`--prefix` + 固定的 `lib/clang/<ver>/include`。
- **发行版**：交叉工具进 `/usr/<triple>/`。
- **嵌入式 SDK**：自带可搬移的 `sysroot/`。
- **MSVC**：无 sysroot，靠 Windows SDK 路径。

**本地改动的承载方式**

- **Debian / RPM / Yocto**：补丁集（`debian/patches`、`%patch`、`.bbappend`）。
- **Apple / Android**：整棵 fork。
- **RISC-V**：拆小合入上游。
- **取舍判据**：改动面小、需跟上游 → 补丁；改动面大或长期偏离 → fork。

**门控分层**

- **LLVM**：`lit` 分组 + feature 标签。
- **GCC**：DejaGnu 分档 + torture 集。
- **Linux**：`selftests` 快速子集 / 全量。
- **Rust**：单元 / 集成 / doc 三档。
- **共同点**：多级粒度 + 明确触发点，层数与命名无统一标准。
