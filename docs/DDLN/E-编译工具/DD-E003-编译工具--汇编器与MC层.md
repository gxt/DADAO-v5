# 编译工具 -- 汇编器与 MC 层

**本册要点**

- 汇编器建在**描述生成**上：格式类、操作数、寄存器类来自同一份声明，编码器与汇编匹配器由它生成。
- **格式类**是 MC 层的核心单元：一条指令只属于一个格式类，操作数如何摆放由格式类决定。
- 汇编器与反汇编器**共用描述**，但规范化逻辑各自保留（否则往返不成立）。
- `rwii` 的 **wyde-position** 必须在解析期确定，且拒绝"裸数字"。
- 同一助记符可能需要**变体选择**（寄存器形态 vs 相对形态）。
- 越界诊断发生在**编码前**，不是链接期。
- `-multiple-to-single` 是"改写形态、保持助记符"的合法降级手段。
- MC 层测试以**字节 oracle** 为主：文本可规范化，字节不可。

## 1. 为什么汇编器要建在"描述生成"之上，而不是手写解析与编码？

**答：** 因为同一条指令的信息要在四个地方用到（解析、编码、打印、反汇编），手写四份必然漂移；把"格式类 / 操作数 / 寄存器类"写成一份声明，再由它生成匹配表与编码器，漂移就没有发生的机会。

- **一份声明生成什么**：指令名与操作数约束 → 解析匹配表；字段位域 → 编码器与解码器；寄存器类 → 合法性检查。
- **为什么必须是生成而不是"共享宏"**：位域与操作数序在编码上是强耦合的，宏只能共享文本，生成才能共享结构。
- **代价**：构建依赖生成步骤（改了声明必须重新生成并重新安装），否则会出现"源码已改、二进制没变"的假绿。
- **收益**：新增一条同格式类的指令，通常只加一行声明，不必碰解析与打印代码。

**各家做法**：

- **LLVM**：TableGen 声明 + 生成匹配器/编码器，MC 层是库。
- **GNU binutils**：每个后端手写 `tc-*.c`（解析）+ 编码表（`opcodes/*`），解析与反汇编各写一遍。
- **ARM 官方汇编器**：闭源，按体系结构手册实现，不对外暴露描述格式。
- **RISC-V**：GAS 后端手写；LLVM 侧走 TableGen，两边各自维护。
- **MIPS / SPARC / PowerPC**：GAS 后端均为手写解析 + 独立反汇编器。

**是统一标准吗**：不是。这是实现结构的选择；标准只规定编码，不规定汇编器怎么写。

## 2. 为什么"格式类"是 MC 层的核心单元？

**答：** 因为编码只取决于"这条指令属于哪个格式类"：操作数个数、字段位置、立即数宽度全由格式类决定；同格式类的指令共享同一套编码与解码逻辑。

- **本项目的 11 个格式类**：`rrrr`、`rrri`、`rrii`、`riii`、`iiii`、`rwii`、`orrr`、`orri`、`oiii`、`crrr`、`ciii`（`crii` 已撤销）。
- **格式类决定什么**：几个寄存器操作数、是否有立即数、立即数在哪些位、是否有 `rd` 写回。
- **为什么不是"一条指令一个编码函数"**：几十条指令会产生几十份几乎相同的代码，任何位域调整都要改几十处。
- **为什么格式类要少而规整**：格式类越少，解码树的深度与分支越少，反汇编越容易写成表驱动。

**各家做法**：

- **x86-64**：没有统一格式类，靠 ModR/M + SIB + 前缀组合，编码空间是"可变长拼装"。
- **ARM64**：按指令组定义固定 32 位布局（数据处理/访存/分支各一套），与"格式类"思路相近。
- **RISC-V**：R/I/S/B/U/J 六种基本格式，概念上与格式类最接近。
- **MIPS**：R/I/J 三种格式，同样固定字段位置。
- **SPARC**：固定 32 位、三种基本格式（格式 1/2/3）。
- **PowerPC**：固定 32 位、按 opcode 主表分组的多种格式（D/X/XO 等）。

**是统一标准吗**：不是。字段位置由各 ISA 规定，但"用少数格式类覆盖全部指令"是共同的设计手法。

## 3. 为什么汇编器与反汇编器共用描述，却仍要各自保留规范化逻辑？

**答：** 因为两者目标相反：汇编器要把**多种合法写法**收成一个编码，反汇编器要把一个编码**收成一种规范写法**；共用描述保证"合法集合"一致，规范化策略必须各自实现。

- **汇编器侧**：接受别名、接受省略写法、接受两种拼写，最后编码唯一。
- **反汇编器侧**：只输出一种规范形式（如单寄存器组不带冒号），保证"反汇编→汇编"逐字节一致。
- **共用部分**：字段位置、操作数类型、寄存器编号映射 —— 这些错了，两边一起错，所以必须同源。
- **不共用的部分**：可接受的写法集合与输出挑哪一种 —— 这是策略，不是结构。

**各家做法**：

- **LLVM**：`AsmMatcher` 与 `AsmWriter` 都由同一份声明生成，但匹配与打印的代码路径分开。
- **GNU binutils**：`tc-*.c`（汇编）与 `*.dis`（反汇编）是两套独立实现，靠测试对齐。
- **ARM 官方工具**：汇编与反汇编同一产品内实现，规范化口径由厂商定义。
- **RISC-V**：GAS 与 objdump 分属两个程序，别名输出策略经常成为争议点。
- **MIPS / SPARC**：反汇编器倾向输出"可再汇编"的最简形式。

**是统一标准吗**：不是。规范化策略没有标准，只有"往返测试"这一工程约束。

## 4. 为什么 `rwii` 的 wyde-position 必须在解析期确定，且要拒绝"裸数字"？

**答：** 因为 64 位常量是分片拼出来的，每片要写进哪个 16 位槽（`wp0`–`wp3`）必须由书写者显式指定；如果允许裸数字，汇编器只能猜位置，猜错就得到"值对、位置错"的编码。

- **片与位置**：一条 `rwii` 指令承载一个 16 位片 + 一个位置字段；位置决定这一片落在 64 位的哪一段。
- **为什么位置不能推导**：同一个常量可以按不同片序拼装，位置是编码的一部分，不是值的函数。
- **为什么拒绝裸数字**：裸数字会让"位置"变成隐式默认值，反汇编时无法还原书写意图，往返判定失效。
- **实践后果**：常量装载由伪指令承担（`set.rd` 等按值选最少片数），手写多片指令时必须显式给位置。

**各家做法**：

- **x86-64**：`movabs` 一条指令装 64 位立即数，不存在分片。
- **ARM64**：`movz`/`movk` 组合，`movk` 用 `lsl #16/#32/#48` 显式指定位置 —— 与本项目"显式位置"同理。
- **RISC-V**：`lui` + `addi` 两段，位置由指令本身固定（高 20 位 / 低 12 位）。
- **MIPS**：`lui` + `ori` 两段，位置固定。
- **SPARC**：`sethi` 装高 22 位，低位靠 `or`，位置固定。
- **PowerPC**：`lis` + `ori`，位置固定。

**是统一标准吗**：不是。分片方式与"位置是否显式"由 ISA 与汇编语法各自决定。

## 5. 为什么同一助记符需要"变体选择"？

**答：** 因为书写层常常用一个名字覆盖多种操作数形态（寄存器-寄存器、寄存器-立即数、相对目标），汇编器必须按操作数类型挑出真正的那条指令；挑错就是"能汇编但语义不同"的静默错误。

- **典型冲突**：同一分支助记符既能接"寄存器基址"又能接"相对偏移"，两者编码不同。
- **判定依据**：操作数的**类**（寄存器组/立即数/标签）优先于字面值；能解析成标签的就不该当立即数。
- **错误形态**：静默选错变体比报错更危险 —— 程序能跑，但跳到了别处。
- **测试方式**：对每个助记符列出"操作数组合 → 期望编码"的矩阵，逐格断言。

**各家做法**：

- **x86-64**：`mov` 覆盖寄存器/内存/立即数数十种组合，由汇编器按操作数形态选编码。
- **ARM64**：`ldr` 分字/字节/立即数偏移/寄存器偏移多种形态，靠操作数语法区分。
- **RISC-V**：`jal`（相对）与 `jalr`（寄存器）分成两条指令，避免同名词歧义。
- **MIPS**：`lw` 只有一种形态（`offset(base)`），歧义面小。
- **SPARC**：`ld`/`lda` 按寻址方式区分，不靠操作数类型猜。
- **PowerPC**：`addi`/`addis` 用不同助记符承担不同位宽，避免同名。

**是统一标准吗**：不是。有的 ISA 用"一词多形"（x86、ARM64、本项目），有的用"多词一义"（RISC-V、PowerPC）。

## 6. 为什么越界诊断必须在编码前完成？

**答：** 因为编码一旦发生，溢出位就丢了：越界检查放在编码后只能看到截断后的值，无法判断原始意图；放在编码前，才能带着"原始值 + 字段范围"一起报错。

- **必须检查的字段**：立即数位宽、偏移对齐、寄存器序号、位置字段取值（`wp0`–`wp3`）。
- **为什么"静默环绕"是缺陷**：截断后的编码看起来合法，错误被推到运行期，定位成本剧增。
- **诊断内容**：合法范围、实际值、以及"是否对齐"这类附加约束。
- **与链接期的分工**：符号未解析属于链接期问题；**字段放不下**属于汇编期问题，两者不能混。

**各家做法**：

- **LLVM 集成汇编器**：多数越界为 error，带源位置。
- **x86 GAS**：部分越界 warning 后截断，退出码仍 0。
- **ARM64 汇编器**：立即数越界通常直接报错。
- **RISC-V GAS**：多数情形报错，个别为 warning（**待核手册**）。
- **MIPS / SPARC / PowerPC**：口径不一（**待核手册**）。

**是统一标准吗**：不是。"warning 还是 error"没有统一规定，属于各工具的严格度选择。

## 7. 为什么需要"多寄存器 → 单寄存器"的 `-multiple-to-single` 改写？

**答：** 因为目标是"同一份汇编能在不支持多寄存器指令的实现上跑"：把一条多寄存器指令拆成一串单寄存器指令，**助记符保持不变**，从而不改源码、只改产物。

- **改写边界**：只做"展开"，不做优化；顺序与写回语义保持与多寄存器指令一致。
- **为什么保持助记符**：若同时改助记符，源码与目标实现的差异就被固化进汇编文件，失去可移植性。
- **代价**：指令数变多、代码变大；原本原子写回的多寄存器语义需要逐条复现。
- **当前状态**：本项目的这一选项尚未实现，属已知缺口。

**各家做法**：

- **x86-64**：无对应需求（没有多寄存器指令），靠编译器自行展开。
- **ARM64**：`ldp`/`stp` 在旧核上由编译器拆成两条 `ldr`/`str`，不是汇编器选项。
- **RISC-V**：无多寄存器指令，无此问题。
- **MIPS**：无多寄存器指令。
- **SPARC**：无多寄存器指令。
- **PowerPC**：`lmw`/`stmw` 有对应"逐条展开"的实现差异，由编译器或内核自行处理。

**是统一标准吗**：不是，是本项目为"多寄存器指令 + 兼容实现"这一组合专设的开关。

## 8. 为什么 MC 层测试以"字节 oracle"为主，而不是只比反汇编文本？

**答：** 因为文本可以被规范化掩盖差异：空白、别名、寄存器写法都能让两份文本"看起来对"，而字节是唯一不可协商的事实。

- **字节 oracle 的做法**：对每条指令固定"汇编文本 → 期望字节序列"，逐字节比对。
- **再叠一层往返**：反汇编回来的文本重新汇编，必须回到同一字节序列。
- **为什么不能只比文本**：反汇编输出的别名/规范化会让"文本相同、编码不同"的情况漏过。
- **覆盖面**：每个格式类至少一条样例，另加边界值（最大/最小立即数、越界附近）。

**各家做法**：

- **LLVM**：`lit` + `llvm-mc --show-encoding` 的字节断言。
- **GCC / binutils**：`gas` 测试套用 objdump 反汇编输出比对，间接比对字节。
- **ARM 官方工具**：厂商自带一致性套件，按手册编码表逐条比对。
- **RISC-V**：上游一致性测试（arch-test）以行为为主，编码由各家测试补。
- **MIPS / SPARC / PowerPC**：多以反汇编文本回溯编码，字节级断言较少。

**是统一标准吗**：不是。测试方法属工程实践，没有标准规定必须字节级。

## 背景知识

### 术语与概念

- **MC 层**：机器码层，包含汇编匹配、编码、打印、反汇编，是编译器与目标文件之间的公共层。
- **格式类（format）**：决定操作数个数与字段位置的编码模板。
- **wyde**：16 位半字；64 位常量由若干 wyde 拼成。
- **wyde-position**：指定某个 wyde 落在 64 位中的哪一段（`wp0`–`wp3`）。
- **变体选择（variant selection）**：同一助记符按操作数类型挑出具体指令。
- **字节 oracle**：以期望字节序列为断言基准的测试方式。
- **规范化**：反汇编输出统一形态（空白、别名、单寄存器组写法）的过程。
- **编码器 / 解码器**：值 → 字节、字节 → 值的两个方向。

### 对照

**汇编器的实现结构**

- **LLVM**：TableGen 生成匹配器与编码器，MC 层为库。
- **GNU binutils**：每后端手写解析 + 独立反汇编器。
- **ARM 官方**：闭源，按手册实现。
- **RISC-V**：GAS 手写 + LLVM TableGen 双线。
- **MIPS / SPARC / PowerPC**：GAS 手写。

**固定字段布局的程度**

- **x86-64**：可变长，ModR/M + SIB + 前缀组合。
- **ARM64**：固定 32 位，按指令组划分。
- **RISC-V**：六种基本格式，最接近"格式类"。
- **MIPS / SPARC / PowerPC**：固定 32 位，三种到多种格式。

**64 位常量的装法**

- **x86-64**：`movabs` 一条指令。
- **ARM64**：`movz` + `movk`（位置用移位显式给出）。
- **RISC-V**：`lui` + `addi`（位置固定）。
- **MIPS / SPARC / PowerPC**：高位指令 + 低位或运算（位置固定）。
- **本项目**：`rwii` 片 + 显式 wyde-position。

**同名多形态 vs 多名一义**

- **同名多形态**：x86-64（`mov`）、ARM64（`ldr`）、本项目（分支的寄存器/相对形态）。
- **多名一义**：RISC-V（`jal`/`jalr`）、PowerPC（`addi`/`addis`）、SPARC（`ld`/`lda`）。
- **取舍**：同名多形态书写省事、歧义风险高；多名一义书写啰嗦、判定简单。

**测试基准**

- **LLVM**：`--show-encoding` 字节断言 + 往返。
- **binutils**：反汇编文本比对。
- **ARM 官方**：厂商一致性套件。
- **RISC-V**：arch-test 以行为为主。
- **共同点**：字节级断言最可靠，但工作量最大。
