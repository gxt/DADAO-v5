# 风险管控 -- 导论

> 状态说明：本册是 X 系列的**导论**——讲这套东西在压什么风险、与研发流程怎么分工、各分册查哪里。细论证在 X002–X006，本册不复述。
> 术语约定：本系列的"风险"指**交付风险**，不是"安全/合规风险"。

**本册要点**

- 流程回答"下一步做什么"，风险管控回答"这一步可能怎么错、错了谁来兜"。
- 四类交付风险：**方向**（做了不该做的）、**质量**（做坏了）、**成本**（做贵了）、**保证失效**（流程变仪式）。
- 四道闸各压一类风险：方案闸压方向、契约闸压接口分歧、证据闸压质量、承诺闸压对外失真。
- 每条规矩都要能回答两件事：**它压住哪类风险、它压不住什么**。
- 风险处置只有四种策略：避免、减轻、转移、接受——大多数规矩是"减轻"，"接受"必须写清代价。
- **元风险**：整套保证自己会退化，必须有抽审与度量。

## 1. 为什么"流程走完"不等于"风险可控"？

**答：** 因为流程规定的是动作，不是效果：方案评审可以变成签字，代码审核可以变成看 diff，门控可以变成跑一遍。动作完成了，风险可能一点没动。

- **流程与风险的错位**：流程按阶段切（任务/实现/验收），风险按性质分（方向/质量/成本/失效）——两套坐标不重合。
- **症状**：门控全绿但方向错了；审核记录齐全但没人真跑；每条都"符合流程"却没人能说出防住了什么。
- **判据**：随便抽一条规矩，问"它压住哪类风险"，答不出来就是仪式。
- **代价**：把风险显式化需要一次梳理；但梳理之后，删规矩和加规矩都有依据。
- **边界**：本系列不设计测试（那是测试体系），不安排任务（那是研发流程），只管"判断与兜底"。

**各家做法**：

- **硬件团队**：投产前检查清单，每条对应一类已知失效。
- **航空/医疗**：失效模式与影响分析（FMEA），按严重度 × 概率排序。
- **互联网运维**：错误预算（error budget）把可靠性风险量化成可消耗的额度。
- **安全领域**：威胁建模，先列攻击面再定对策。
- **一般软件项目**：有评审动作，但没有风险清单，说不清防住了什么。

**是统一标准吗**：不是；共同点是"先列风险，再定动作"。

## 2. 四类交付风险

**答：** 方向、质量、成本、元风险。四类的信号不同、处置手段不同，混在一起谈就会变成"什么都重要"。

- **方向风险**：需求理解错、方案选错、范围漂移、对外承诺过度。信号：做完之后发现"不是要这个"。
- **质量风险**：语义错、边界漏、判据不独立、配置错误。信号：合并后才发现，或换环境才复现。
- **成本风险**：审核跟不上产出、门控慢到被跳过、返工率上升。信号：周期变长、大家都在等。
- **元风险（保证失效）**：评审变签字、门控变仪式、凑绿、绕过。信号：记录齐全但没人能复述结论依据。
- **为什么分四类**：因为处置手段不同——方向靠"做之前停下来问"，质量靠"独立判据"，成本靠"分层与抽样"，元风险靠"抽审与度量"。

**各家做法**：

- **制造业**：把缺陷按"设计/工艺/来料"分类，因为处置责任不同。
- **软件工程**：缺陷按"需求/设计/编码/测试"分类，对应不同阶段。
- **运维**：故障按"变更/容量/依赖/人为"分类。
- **安全**：按攻击面分类（网络/主机/供应链/人员）。
- **共同点**：分类的目的是"让处置有主"。

**是统一标准吗**：不是。

## 3. 四道闸与风险的映射

**答：** 方案闸压方向，契约闸压接口分歧（方向与质量的交界），证据闸压质量，承诺闸压对外失真；四道闸之外还有两道元审压"保证失效"。

- **方案闸（做之前）**：一页方案，回答改什么、选哪个、否了哪个、怎么验证、边界在哪。压方向风险。
- **契约闸（写之前）**：验收标准能否命令判定；跨模块约定谁审。压"两边理解不同"。
- **证据闸（做完）**：代码/数据/配置/依赖/权限审核 + 独立重跑 + 反例注入。压质量风险。
- **承诺闸（发布前）**：文档与对外口径不得把设计写成现状。压"读者被误导"。
- **元审 A（周期性）**：抽几个已完成任务，回看预检/门控/证据是否真实存在。
- **元审 B（周期性）**：回滚与复现演练——出事能不能退、产物能不能重建。
- **为什么按闸组织**：每道闸对应一个"可以停下来的时刻"，比按角色组织更可执行。

**各家做法**：

- **硬件**：设计评审 → 投产评审 → 硅后验证，三道闸。
- **航空**：初步设计评审 → 关键设计评审 → 飞行准备评审。
- **互联网**：设计评审 → 代码评审 → 灰度发布 → 事后复盘。
- **出版**：选题评审 → 审稿 → 校对。
- **共同点**：闸的位置由"此时停下最便宜"决定。

**是统一标准吗**：不是。

## 4. 与研发流程（Y）的分工

**答：** Y 按**阶段**讲（任务 → 实现 → 门控 → 验收 → 沉淀），X 按**风险**讲（方向/质量/成本/失效）。两者正交：同一阶段可能压多种风险，同一风险也可能横跨多个阶段。

- **Y 的问题**："下一步做什么、谁做、做到哪一步"。
- **X 的问题**："这一步凭什么算对、算值；错了谁兜"。
- **重叠处**：门控与验收（Y003）是流程环节；X004 讲"门控本身能不能压住风险"。
- **写法差异**：Y 讲规矩怎么落地；X 讲规矩防的是什么、防不住什么。
- **避免重复**：X 不复述流程步骤，只引用"哪一道闸"。

## 5. 六个分册各管什么

- **X002 方向风险**：方案评审、任务书与验收标准审核、契约与范围控制、对外承诺管理。
- **X003 质量风险（产物）**：代码审核五查、独立重跑、反例注入与还原；数据/配置/依赖/权限审核。
- **X004 质量风险（判据）**：判据独立性、门控有效性（可达 FAIL、恒真、幂等、并发）、弃权与覆盖口径。
- **X005 成本风险**：审核预算、分层抽样、自动化前置、AI 时代瓶颈（产出快于阅读）、返工率与逃逸缺陷。
- **X006 元风险**：过程合规抽审、绕过与凑绿、回滚与复现、体系自身的度量与修订。

## 6. 每条规矩都要回答两个问题

**答：** "它压住哪类风险"和"它压不住什么"。前一个防止仪式化，后一个防止过度信任。

- **压住什么**：对应风险类别 + 一个可观察的信号（没有它会看到什么）。
- **压不住什么**：边界（例如代码审核压不住"方向错"，门控压不住"判据错"）。
- **处置策略**：避免（不做的）、减轻（降低概率/影响）、转移（交给别的环节/工具）、接受（写清代价）。
- **"接受"要显式**：接受的风险必须有记录与复核时点，不能默认它不存在。
- **反例**：一条规矩若说不出压住什么，它大概率只是"看起来严谨"。

**各家做法**：

- **FMEA**：每条失效模式都有严重度、概率、探测度与对策。
- **安全**：每个威胁都有对策与残余风险说明。
- **运维**：每个容灾项都有 RTO/RPO 与演练记录。
- **一般项目**：规矩靠"惯例"，无人追问边界。

**是统一标准吗**：不是；"对策 + 残余风险"是共同结构。

## 7. 出问题该查哪一册

- 做完发现"不是要这个" → **X002**（方向）。
- 代码/数据/配置错了，或审核没抓住 → **X003**。
- 门控绿了但没压住问题、判据被污染 → **X004**。
- 审核追不上、周期变长、返工多 → **X005**。
- 评审变签字、门控变仪式、说不清防住什么 → **X006**。

## 背景知识

### 术语与概念

- **交付风险**：导致"做错方向 / 做坏 / 做贵 / 保证失效"的可能性。
- **四道闸**：方案、契约、证据、承诺四个可停下的时刻。
- **元风险**：保证体系自身退化带来的风险。
- **处置策略**：避免 / 减轻 / 转移 / 接受。
- **残余风险**：采取对策之后仍然存在的风险。
- **逃逸缺陷**：审核与门控都没抓住、合并后才暴露的缺陷。
- **抽审**：周期性随机回看，验证流程没有退化成仪式。
- **凑绿**：通过改契约、弱化断言、删检查来让门控变绿。

### 对照

**风险分类**

- **制造业**：设计 / 工艺 / 来料。
- **软件**：需求 / 设计 / 编码 / 测试。
- **运维**：变更 / 容量 / 依赖 / 人为。
- **本系列**：方向 / 质量 / 成本 / 元风险。

**对策结构**

- **FMEA**：严重度 × 概率 × 探测度 + 对策。
- **安全**：威胁 + 对策 + 残余风险。
- **运维**：RTO/RPO + 演练。
- **共同点**：对策要配"残余风险"，否则等于宣称零风险。

**闸的位置**

- **硬件 / 航空**：设计评审 → 投产/飞行准备评审。
- **互联网**：设计 → 代码 → 灰度 → 复盘。
- **出版**：选题 → 审稿 → 校对。
- **判据**：在"此时停下最便宜"的地方设闸。
