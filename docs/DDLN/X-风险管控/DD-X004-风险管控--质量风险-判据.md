# 风险管控 -- 质量风险（判据）

**本册要点**

- 门控最常见的问题不是"不够全"，而是**恒真**：永远不会失败。
- 覆盖率回答"跑到没跑到"，**变异得分**回答"发现不发现得到"——后者才是有效性。
- 判据独立性要能机械检查：依赖、来源标记、代码是否共享。
- **弃权与跳过必须单列**，否则覆盖率虚高。
- 门控脚本自身也是产物：幂等、并发安全、退出码可靠、路径单一真源。
- 告警有效率要维护：无效告警会让整套门控被当成噪音。

## 1. 门控为什么会"恒真"，怎么发现？

**答：** 因为写检查比写断容易：断言两支写同一结果、只判"没崩"、异常被吞、比较对象是自己。发现方法只有一个——**注入一次，看它红不红**。

- **四种典型形态**：两支同值；断言"进程正常退出"；捕获异常后判通过；用被测实现的输出当期望值。
- **发现手段**：非作者注入（改变测产物 → 应变红）；反过来把期望值改错（应变红）。
- **为什么作者发现不了**：作者知道自己测过什么，会顺着"已知能过"的路径验证。
- **处置**：恒真断言必须重写，不能靠"下次注意"。
- **代价**：每个门控多花十几分钟；换来的是"这套检查真的会报错"。

**各家做法**：

- **变异测试**：系统化注入，用得分衡量有效性。
- **硬件验证**：故障注入验证检查器。
- **安全**：红队独立验证检测能力。
- **CI 平台**：用"故意失败的用例"验证框架。
- **一般项目**：无注入，恒真长期存在。

**是统一标准吗**：不是；但"检查必须能失败"是共同前提。

## 2. 为什么覆盖率不能当有效性指标？

**答：** 因为覆盖率只说明"这段代码被执行过"，不说明"执行时有人判断它对不对"。100% 行覆盖 + 恒真断言 = 0 有效性；反过来，变异得分低说明"改了也发现不了"。

- **覆盖率回答**：哪些代码被跑到（覆盖盲区）。
- **变异得分回答**：注入的改动中被发现的比例（判定能力）。
- **两者关系**：覆盖率是必要条件，不是充分条件；变异得分更接近"有效"。
- **还有一层**：功能覆盖（身份 × 检查项 × 边界）比行覆盖更贴近语义。
- **代价**：变异测试要跑很多次，慢；可只在关键模块或夜间跑。

**各家做法**：

- **硬件验证**：功能覆盖仓（bin）驱动，行覆盖只是辅助。
- **编译器测试**：以"能否发现错误码生成"为目标，不做行覆盖统计。
- **互联网**：行覆盖率进报告，但决策看线上缺陷与逃逸率。
- **航空**：结构覆盖有明确等级要求（语句/判定/修正条件）。
- **一般项目**：只报行覆盖率，用它代替质量结论。

**是统一标准吗**：不是。

## 3. 判据独立性怎么机械检查？

**答：** 三件事可自动化：生成脚本的依赖、期望值的来源标记、判据与被测实现是否共享代码。三件都能用静态检查或清单审查落地。

- **依赖检查**：生成脚本不得引用被测实现的产物路径或模块。
- **来源标记**：每个期望值带"规范条款 + 生成器版本"，可追溯。
- **共享代码检查**：模型与实现不得共用同一份语义代码，否则"一致"来自共享。
- **结果记录**：结果里记录参与方与版本，事后可复核。
- **代价**：增加元数据与检查脚本；换来的是"一致"有意义。

**各家做法**：

- **合规生态**：参考模型与实现严格分离，签名由参考侧生成。
- **开源**：靠评审与约定，少有机械检查。
- **企业**：流程规定 + 代码审查。
- **一般项目**：独立性靠口头保证。
- **本仓**：期望值来源可追溯，生成脚本不引用实现产物。

**是统一标准吗**：不是。

## 4. 为什么弃权/跳过必须单列？

**答：** 因为"没判定"与"通过"是两件事；混在一起，覆盖率会虚高，报告会让人误以为覆盖完整。

- **来源**：环境不支持、工具缺能力、配置未启用、用例显式跳过。
- **正确形态**：通过 / 失败 / 未判定三列并列，未判定附原因码。
- **为什么容易混**：多数脚本只有布尔结果，跳过被归入成功路径。
- **代价**：报告不好看；但它暴露的是能力缺口。
- **配套**：未判定项按原因聚合，作为改进输入。

**各家做法**：

- **测试框架**：区分跳过/不支持/失败（如 TAP 与 lit 类状态）。
- **合规套件**：未覆盖项单列。
- **硬件回归**：用例未运行与通过分开统计。
- **一般脚本**：跳过即通过。
- **本仓**：差分统计把弃权单列。

**是统一标准吗**：部分统一（多数成熟框架支持"跳过"语义）。

## 5. 门控脚本自身怎么审？

**答：** 按产物审：幂等（跑两次结果一致）、并发安全（同时跑不互相破坏）、退出码可靠（不被管道吞掉）、路径单一真源（不硬编码）、计数不写死（现场统计）。

- **幂等**：重复运行不应改变结果或状态；否则"重跑一次"就成了不可信操作。
- **并发**：共享工作树时加锁；并行跑要隔离输出目录。
- **退出码**：`cmd | tee log` 拿到的是 `tee` 的码，必须单独取 `cmd` 的码。
- **路径**：通过统一配置解析，禁止硬编码；否则换环境就断。
- **计数**：期望值写死会让"数量变化"被当成通过（或反过来）。
- **代价**：写脚本的成本上升；换来的是门控本身可信。

**各家做法**：

- **CI 平台**：幂等与并发由平台保证。
- **硬件回归**：回归脚本要求可重入、输出隔离。
- **内核自测**：测试自身有框架级检查。
- **企业**：流水线脚本集中维护。
- **一般项目**：脚本一次性，重复跑就出错。

**是统一标准吗**：不是。

## 6. 告警有效率怎么维护？

**答：** 定期审计"这条告警上次真的发现问题是什么时候"；长期零命中的告警要么删掉，要么降级。无效告警会让开发者训练出"忽略"的习惯，整套门控随之失效。

- **审计问题**：最近 N 次触发里，有多少是真问题？
- **处置**：修（让它只对真问题报）、降级（提示而非阻断）、删（无效）。
- **为什么重要**：告警疲劳是不可逆的——一旦大家学会忽略，再加新告警也没人看。
- **配套**：新告警必须附"它防的是什么风险"，否则不进阻断层。
- **代价**：审计要人力；换来的是门控被认真对待。

**各家做法**：

- **静态分析平台**：只保留高置信度告警，低置信度进代码评审提示。
- **运维**：告警定期清理，按"可行动性"分级。
- **安全扫描**：分级处置，避免"全红等于全不看"。
- **硬件**：回归失败必须可归因，否则规则会被关掉。
- **一般项目**：告警只增不减，最后全部忽略。

**是统一标准吗**：不是。

## 7. 实例：覆盖率 100%，变异得分很低

**现象**：行覆盖率报表接近 100%，但把关键判断改反后没有任何用例失败。

**根因**：用例执行了代码，但断言不判结果；覆盖率统计的是"跑到"，不是"判到"。

**规矩**：关键模块的有效性用变异得分衡量；覆盖率只作辅助指标。

**机械防**：
- 关键模块定期跑变异（或人工注入 N 处），记录发现比例。
- 断言清单标注"可注入点"，缺失即退回。
- 报表把覆盖率与变异得分并列展示，禁止只报覆盖率。

## 8. 实例：管道吞掉退出码

**现象**：测试明明失败，门控却报通过；日志里有错误行，但退出码是 0。

**根因**：命令被 `| tee`/`| tail` 包装，取到的是包装器的退出码。

**规矩**：退出码必须取自被检命令本身，并单独记录。

**机械防**：
- 统一用"先跑命令并保存码，再处理输出"的写法。
- 门控脚本自检：故意让命令失败，确认门控报红。
- 证据文件里同时保存命令、输出与退出码三项。

## 背景知识

### 术语与概念

- **恒真检查**：永远不会失败的断言。
- **变异得分**：注入改动中被发现的比例。
- **行覆盖 / 功能覆盖**：被执行到的代码比例 / 被覆盖的功能点比例。
- **弃权**：环境或工具不支持，结果未判定。
- **幂等**：重复执行结果不变。
- **告警有效率**：触发中真正是问题的比例。
- **判据独立性**：期望值派生路径不经过被测实现。

### 对照

**有效性度量**

- **弱**：行覆盖率、用例条数。
- **中**：功能覆盖（身份 × 检查项 × 边界）。
- **强**：变异得分、注入发现率。

**未判定处理**

- **强**：三列并列 + 原因码。
- **弱**：跳过即通过。

**门控脚本质量**

- **强**：幂等、并发安全、退出码可靠、路径统一。
- **弱**：一次性脚本，重复运行即失真。
