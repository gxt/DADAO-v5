# 风险管控 -- 成本风险

**本册要点**

- "审核追不上产出"是**体系风险**，不是勤奋问题：靠加班解决不了，只能靠分层与自动化。
- 评审要设**预算**：规模、速度、时长、等待时间四项，超了要拆任务。
- **分层抽样**：高风险全审，低风险按比例抽审并轮换，抽样率写死不留口子。
- **机器做筛、人做判断**：格式、构建、回归交给机器；方向、边界、权衡留给人。
- 成本度量看四项：返工率、逃逸缺陷、门控时长、评审等待时间。
- 出现排队时，正确动作是**拆任务**或**砍范围**，不是降低标准。

## 1. 为什么"审核追不上产出"是体系风险？

**答：** 因为产出速度由工具决定，审核速度由人决定，两者差距会随时间扩大。当审核成为瓶颈，实际结果不是"审核变快"，而是"审核被跳过"。

- **机制**：排队 → 等待 → 有人开始"先合再说" → 门控被当作形式。
- **信号**：评审等待时间持续上升、单次评审规模变大、评审意见变少。
- **为什么不能靠加班**：加班降低缺陷发现率（时限与注意力都下降），反而更慢。
- **正确方向**：把可控的交给机器、把人的时间投在高风险处、把大改动拆小。
- **代价**：分层与自动化要先投入；换来的是审核不被绕过。

**各家做法**：

- **互联网大厂**：自动化门禁 + 人工只看设计，评审周转按小时考核。
- **开源**：维护者稀缺，靠自动化测试承担大部分把关。
- **硬件**：回归农场跑机器检查，人审设计。
- **企业**：流水线做门禁，评审会只处理例外。
- **一般项目**：全靠人看，产出越快越容易崩。

**是统一标准吗**：不是。

## 2. 评审预算怎么定？

**答：** 四项：单次规模（如 200–400 行）、检查速度（<500 行/小时）、单次时长（<60 分钟）、等待时间（从提交到首轮意见）。前三项管"看得清"，第四项管"不排队"。

- **规模与速度**：有业界实证支撑（超过上限后缺陷发现率骤降）。
- **时长**：60 分钟后注意力崩塌，宁可分两次。
- **等待时间**：超过一天，作者上下文已冷却，返工成本上升。
- **超限处置**：拆任务、砍范围、或先合"最小可用部分"。
- **代价**：拆任务要额外协调；换来的是审核真的发生。

**各家做法**：

- **Google**：小改动 + 快速周转，评审是持续动作而非节点。
- **Linux 内核**：补丁小、单一目的，维护者快速反馈。
- **硬件**：按模块切分评审范围。
- **企业**：评审 SLA（如 24 小时首轮）。
- **一般项目**：无预算，一次看几千行。

**是统一标准吗**：不是；但"小批量 + 快反馈"是共同结论。

## 3. 分层抽样怎么分才不遗漏？

**答：** 按"风险 × 改动性质"分层：高风险（语义、接口、权限、门控自身）全审；中风险抽审；低风险（注释、格式、文档措辞）只跑门控。抽样要**预先定比例**并**轮换**，避免总是抽到同一批。

- **高风险判据**：影响语义、改变对外接口、动权限或门控、跨模块。
- **中风险**：内部重构、性能优化、依赖升级（需看变更说明）。
- **低风险**：注释、格式、纯文档。
- **抽样规则**：固定比例 + 随机轮换；比例写进规则，不临时决定。
- **为什么不能全审**：全审等于都不审；为什么不能全抽：漏掉高风险代价不可承受。

**各家做法**：

- **安全**：按攻击面定审级。
- **测试**：风险驱动测试，按失效后果分配资源。
- **硬件**：关键路径全审，外设模块抽审。
- **企业**：变更分级（重大/一般/微小）。
- **一般项目**：平均用力。

**是统一标准吗**：不是。

## 4. 什么该机器做，什么必须人做？

**答：** 机器做"可判定且重复"的：格式、构建、回归、静态检查、依赖扫描、覆盖统计；人做"需要权衡"的：方向、方案取舍、边界定义、对外承诺、判定是否达标。

- **机器擅长**：一致、可重复、不会疲劳；但只会判"规则写死的事"。
- **人擅长**：发现"规则之外"的问题；但会疲劳、会漏、会受上下文影响。
- **常见错误**：让人做机器能做的事（逐行对格式）；让机器判需要权衡的事（"是否满足意图"）。
- **配合方式**：机器先筛掉 80%，人聚焦 20% 高风险。
- **代价**：前期要把规则写成检查；换来长期节省。

**各家做法**：

- **编译器**：格式与回归交给工具，设计评审留给人。
- **互联网**：自动化门禁 + 人工设计评审。
- **硬件**：仿真回归机器跑，架构评审人做。
- **航空**：工具鉴定 + 独立人工验证。
- **一般项目**：人做一切，机器只编译。

**是统一标准吗**：不是。

## 5. 用什么度量成本？怎么防博弈？

**答：** 四项指标：返工率、逃逸缺陷（合并后才发现）、门控时长、评审等待时间。指标要配对使用，且明确"不可单独考核"，否则一定被博弈。

- **返工率**：同一任务反复修改的次数——高说明方案或标准有问题。
- **逃逸缺陷**：漏到合并之后的缺陷——最接近"保证失效"的度量。
- **门控时长**：决定开发者是否愿意跑；超阈值会被绕过。
- **等待时间**：审核瓶颈的直接信号。
- **防博弈**：指标不挂个人绩效；看趋势不看单点；配套抽审验证数据真实性。

**各家做法**：

- **运维**：错误预算把可靠性量化，但明确不用于个人考核。
- **制造业**：一次通过率与返工率成对使用。
- **软件**：缺陷逃逸率 + 修复时长。
- **企业**：指标常被个人考核绑定，随即失真。
- **一般项目**：无度量，靠感觉。

**是统一标准吗**：不是。

## 6. 什么时候该拆任务，而不是加人加时？

**答：** 当审核排队、评审规模超限、或验收项互相纠缠时——这三种情况加人加时只会让改动更大、耦合更深。拆任务是把"不可审"变成"可审"的唯一办法。

- **信号一**：单次改动超过评审预算。
- **信号二**：评审等待超过约定阈值。
- **信号三**：一个任务里出现多个互不相关的目标。
- **拆法**：按"可独立验收的最小单元"拆；先合基础部分，再合上层。
- **代价**：多次提交、多次评审；换来的是每次都审得动。

**各家做法**：

- **Linux 内核**：系列补丁（patch series），逐个可审。
- **LLVM**：拆成可独立回滚的提交。
- **互联网**：特性开关，先合代码后开功能。
- **硬件**：分模块流片验证，避免一次性大改。
- **一般项目**：越拖越大，最后只能整块合。

**是统一标准吗**：不是。

## 7. 实例：门控太慢被绕过

**现象**：全量门控要一小时，开发者开始"先合后补"；几周后没人再跑全量，缺陷在合并后集中爆发。

**根因**：检查代价与触发频率不匹配；没有分层，所有检查挤在一个入口。

- **规矩**：按代价分层，秒级检查每次跑，全量检查放里程碑。
- **机械防**：秒级门控设耗时上限，超限报警并强制迁移；记录每次门控耗时趋势。

## 8. 实例：审核排队成为瓶颈

**现象**：产出速度提升后，评审排队从半天变成三天；作者上下文冷却，返工率上升，最后出现"先合再说"。

**根因**：审核资源固定，产出弹性增长；没有分层与抽样，全部改动都进同一条队列。

- **规矩**：高风险全审、低风险抽审；等待时间设阈值，超阈值先拆任务。
- **机械防**：统计等待时间与单次规模；超阈值自动提示拆分；抽审比例与轮换规则写进流程。

## 背景知识

### 术语与概念

- **评审预算**：规模、速度、时长、等待时间四项上限。
- **分层抽样**：按风险等级决定全审或抽审。
- **逃逸缺陷**：合并后才发现的缺陷。
- **返工率**：同一任务重复修改的比例。
- **门控时长**：一次门控从开始到结束的时间。
- **特性开关**：先合代码、后开功能的手段。
- **瓶颈迁移**：消除一个瓶颈后，瓶颈转移到下一环节。

### 对照

**审核资源分配**

- **高风险全审**：语义、接口、权限、门控自身。
- **低风险抽审**：格式、注释、文档措辞。
- **平均用力**：最常见的错误。

**成本度量**

- **强**：返工率 + 逃逸缺陷 + 时长 + 等待时间（配对使用）。
- **弱**：只看"审了多少行"或"通过率"。
- **风险**：指标挂个人绩效即失真。

**拆任务信号**

- **规模超限 / 等待超阈值 / 目标不单一**。
- **处置**：按可独立验收的单元拆，先基础后上层。
