# 风险管控 -- 质量风险（产物）

**本册要点**

- 审核的判据是**你自己跑出来的输出**，不是作者的叙述。
- 评审有**预算**：单次 200–400 行、速度 <500 行/小时、时长 <60 分钟——超过就失效。
- 五查顺序：范围 → 语义 → 边界 → 证据 → 残留。
- 反例注入必须由**非作者**做，且注入后要能还原到"复绿"。
- 非代码产物（数据、配置、依赖、权限）要按代码同等待遇审。
- 判定只给三档，且必须带具体命令与输出。

## 1. 为什么审核必须"重跑"而不是"读"？

**答：** 因为"看起来对"与"实际对"之间隔着一个运行环境：路径、版本、端序、并发都可能让"读起来没问题"的代码出错。只有自己的重跑能给出可复核的事实。

- **重跑什么**：任务书的验收命令、证据脚本、关键路径的小例子。
- **抓什么**：**被检命令自己的退出码**（管道会吞退出码，必须单独取）。
- **为什么不能信作者的输出**：可能被截断、美化、选择性摘录；对照可以，但不能当证据。
- **代价**：重跑比读慢；但它给出的是可复现的结论。
- **边界**：重跑不能替代理解——先读关键路径，再重跑验证。

**各家做法**：

- **开源项目**：合并前必须过持续集成，评审者看的是机器结果。
- **硬件**：回归测试跑完才算过，不看"设计者说没问题"。
- **航空**：独立验证团队重跑并留证。
- **企业流水线**：流水线是唯一判据，人工评审只看设计。
- **一般项目**："我本地跑过了"。

**是统一标准吗**：不是；但"证据来自执行"是共同底线。

## 2. 评审规模与速度为什么要设上限？

**答：** 因为人的缺陷发现能力随规模与速度断崖式下降。业界最大规模的一次轻量评审实证（2,500 次评审、320 万行）给出的可用阈值是：**200 行为宜、400 行封顶**；**检查速度 <300 行/小时最佳、<500 可行**；**单次 <60 分钟，不超过 90 分钟**。

- **规模效应**：超过 400 行后缺陷密度急剧下降——审了，但没看见。
- **速度效应**：超过 500 行/小时基本等于浏览；超过 1000 行/小时基本等于没看。
- **时长效应**：60 分钟后注意力崩塌。
- **为什么对 AI 时代更关键**：产出速度远超人的阅读速度，不设预算就等于放弃审核。
- **落地方式**：把上限写进任务模板与评审规则；超限就**拆任务**，而不是"这次先放过"。

**各家做法**：

- **Google**：小改动（small CL）文化，评审周转以小时计。
- **Microsoft**：实证研究显示评审者更关注可理解性与小批次。
- **Linux 内核**：补丁小、单一目的，大补丁要求拆分。
- **硬件**：设计评审按模块切分，单次不覆盖整芯片。
- **一般项目**：一次提交几千行，评审变成盖章。

**是统一标准吗**：不是；但"小批量"是所有实证研究的共同结论。

## 3. 五查顺序为什么是这个顺序？

**答：** 因为便宜的检查在前、贵的在后：范围错就不必读语义，语义错就不必跑证据。顺序本身是一种成本优化。

- **① 范围**：diff ↔ 声明 ↔ 任务范围，三者对齐；多出来的是越界，少了的是没做完。
- **② 语义**：只读关键路径（数据流、状态迁移、边界处理），重点看单位、端序、位宽、符号性。
- **③ 边界**：空值、越界、失败分支、并发、重入；以及"最不像人写的几行"。
- **④ 证据**：重跑 + 独立注入 + 抓退出码。
- **⑤ 残留**：临时文件、调试输出、被删的检查、被弱化的断言。
- **为什么"凑绿"放在最后**：它是"证据"与"残留"交叉才能发现的——删检查、改契约、弱化断言都会在 diff 里留下痕迹。

**各家做法**：

- **正式审查（Fagan 式）**：按检查清单逐项过，先结构后细节。
- **现代代码评审**：先看改动目的与范围，再看实现。
- **安全评审**：先定攻击面（范围），再看具体缺陷。
- **硬件**：先看接口与时钟域（范围），再看门级实现。
- **一般项目**：从第一行读到最后一行。

**是统一标准吗**：不是。

## 4. 为什么反例注入必须由非作者做？

**答：** 因为作者知道自己测过什么，会不自觉地在"已知有效的路径"上验证；非作者不知道，只能按"这条断言凭什么成立"去试，更容易试出恒真。

- **注入什么**：被测产物的一处值/字段/分支；以及**检查脚本自身**（防止脚本永远返回真）。
- **判据**：注入后必须变红；还原后必须复绿。
- **还原纪律**：备份 + 哈希对账，**不用**回滚命令（会连未提交改动一起清掉）。
- **记录**：三段真实输出（注入前、变红、复绿）。
- **代价**：一次注入十几分钟；换来的是"这套检查真的会报错"。

**各家做法**：

- **变异测试**：系统化注入，用"变异得分"衡量测试有效性。
- **硬件验证**：注入故障验证检查器。
- **安全**：红队独立攻击，不告诉防守方路径。
- **开源**：CI 用"故意失败的用例"验证框架本身。
- **一般项目**：无注入，检查是否有效无人知道。

**是统一标准吗**：不是；但"验证者独立于被验证者"是共同前提。

## 5. 非代码产物怎么审？

**答：** 与代码同等对待，但检查项不同：数据看来源与边界，配置看影响面与默认值，依赖看来源与改动，权限看能力边界。

- **数据/期望值**：来源是否独立派生、边界是否覆盖、能否注入反例、重派生是否逐字节一致。
- **配置与构建**：一行配置能改变全部行为——看默认值、看影响面、看是否有开关矩阵验证。
- **依赖与补丁**：来源可追溯、锁定到不可变标识、补丁是否偷偷弱化检查。
- **权限与安全配置**：工具白名单、写入范围、凭据——**这是能力边界**，改它等于改能做什么。
- **为什么容易漏**：这些文件往往不在"代码"的直觉范围里，但风险同样甚至更大。

**各家做法**：

- **基础设施即代码**：配置变更走与代码相同的评审与流水线。
- **安全开发生命周期**：依赖与权限变更有专门审查项。
- **硬件**：约束文件、时序脚本与 RTL 同等评审。
- **企业**：权限变更需审批并留痕。
- **一般项目**：配置随手改，权限随手加。

**是统一标准吗**：不是。

## 6. 判定三档怎么给？

**答：** 接受（你自己的重跑全过且约束无违反）、需修改（指出具体命令与输出）、阻断（设计层问题交协调者）。不给"基本没问题"这种中间态。

- **接受的前提**：重跑通过 + 约束无违反 + 证据可复核；缺一条不能接受。
- **需修改必须具体**：哪条命令、什么输出、期望什么；不写"建议优化"。
- **阻断的场景**：方案本身有问题、跨模块影响未处置、验收标准不可判定。
- **不代修**：审核者不改代码，否则失去独立性、责任也模糊。
- **文档级小错**：不阻断（记录后由收尾统一改），避免为措辞再开一轮；但**验收判据本身的数字错**仍阻断。

**各家做法**：

- **开源**：批准 / 请求修改 / 关闭（附理由）。
- **硬件**：通过 / 有条件通过（列条件）/ 不通过。
- **航空**：按审查节点签核，缺陷必须闭环。
- **企业**：通过 / 退回，退回必附整改项。
- **一般项目**：口头"差不多了"。

**是统一标准吗**：不是。

## 7. 实例：改坏一处，门控仍全绿

**现象**：把关键分支的条件改反，门控依旧全绿；直到线上行为异常才发现。

**根因**：断言写的是"跑完没崩"，不是"结果正确"；两支写同一结果，失败路径不存在。

**规矩**：每条断言都要能指出"改哪里会让它红"；指不出来的断言重写。

**机械防**：
- 非作者独立注入一次：改被测产物 → 确认变红 → 备份还原 → 复绿。
- 断言清单标注可注入点，缺失即退回。
- 汇总区分"通过/失败/未判定"，禁止把跳过计入通过。

## 8. 实例：一行配置改变全部行为

**现象**：代码没动，只改了一个默认开关；测试仍绿，但部分场景行为变了，且只在特定输入下暴露。

**根因**：配置被当成"非代码"，未进评审范围；测试也没有覆盖开关的两种取值。

**规矩**：配置变更与代码同等评审；涉及默认值的改动必须有"开关矩阵"验证。

**机械防**：
- 变更范围检查把配置文件与权限文件纳入。
- 关键开关要求两态都跑一遍（开/关），并在证据里记录。
- 默认值变更需在提交说明里显式写出影响面。

## 背景知识

### 术语与概念

- **评审预算**：单次评审的规模、速度、时长上限。
- **五查**：范围、语义、边界、证据、残留。
- **反例注入**：人为改坏一处，验证检查确实会红。
- **变异得分**：注入的改动中被检查发现的比例。
- **凑绿**：通过改契约、弱化断言、删检查让门控变绿。
- **能力边界**：权限与白名单定义"能做什么"。
- **阻断**：设计层问题，审核者不放行。
- **文档级小错**：不影响判据的措辞/数字笔误。

### 对照

**评审规模实证**

- **业界大规模研究**：200 行为宜、400 行封顶；<500 行/小时；<60 分钟。
- **小批量文化**：Google/Linux 倾向小改动、单一目的。
- **反例**：一次几千行，评审退化为盖章。

**审核依据**

- **强**：审核者自己的重跑 + 退出码 + 注入。
- **中**：作者输出 + 抽验。
- **弱**：只读 diff。

**非代码产物**

- **纳入评审**：配置、权限、依赖、数据。
- **常常遗漏**：默认值、白名单、锁文件。
- **判据**：它变了会不会改变行为或能力边界。
