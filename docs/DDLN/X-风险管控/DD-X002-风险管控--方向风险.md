# 风险管控 -- 方向风险

**本册要点**

- 方向错是**最贵的错**：做得越认真，浪费越大，而代码审核永远发现不了它。
- 方案评审只需**一页**：改什么、选哪个、否了哪个、怎么验证、边界在哪。
- 验收标准必须**命令可判定**；写"功能正常"等于把判定权交给实现者。
- "顺手改"是方向风险的常见形态：范围一变，验证就不再覆盖真实改动。
- 对外文档要单独设闸：把设计写成现状，比代码 bug 更难纠。
- 决策按**可逆性**分类：可逆的快做，不可逆的慢做。

## 1. 为什么"方向错"是最贵的错？

**答：** 因为方向错时，后面每一步都在放大损失：实现越完整、测试越充分、文档越详尽，返工越彻底。而代码审核只判断"写得对不对"，天然看不见"该不该做"。

- **成本结构**：方向错 → 整条链重做；实现错 → 局部返工；笔误 → 改一行。
- **为什么审核看不见**：审核的输入是 diff，diff 里没有"需求是否理解正确"这一维。
- **典型形态**：把"某功能的实现"当成"某问题的解决"；把"能跑"当成"符合意图"。
- **判据**：如果重来一次，你会不会做同样的事？答案是否定，就是方向问题而非实现问题。
- **代价**：方向评审要多花半天；换来的是不把一周花在错的地方。

**各家做法**：

- **硬件**：设计评审在画版图之前，改设计比改硅片便宜几个数量级。
- **航空/医疗**：需求评审 + 追溯矩阵，方向错在纸面上被发现。
- **互联网**：设计文档评审（design review）先于编码。
- **开源**：RFC/提案流程，先达成方向共识再动手。
- **一般项目**：直接开写，方向靠"做着做着就明白了"。

**是统一标准吗**：不是；但"先定方向再动手"是共同做法。

## 2. 方案评审要审到什么程度？

**答：** 一页，五个要素：改什么、选哪个方案、否了哪个为什么、怎么验证、边界在哪。审的人不看代码，只问三个问题：有没有更简单的、失败能否回退、验证能否证伪。

- **改什么**：一句话说清范围与不做的事（"不做"比"做"更能暴露分歧）。
- **选哪个 / 否了哪个**：被否方案与理由，是防止半年后有人重走弯路。
- **怎么验证**：验收手段必须已经存在（不是"应该会有"）。
- **边界**：异常、并发、兼容性、性能这些"不打算管"的部分要明说。
- **三个提问**：更简单的方案是什么？失败时怎么退？什么结果会证明我错了？
- **成本**：半小时到半天；比例：一页方案换掉一次整链返工。

**各家做法**：

- **硬件**：设计评审看架构图与接口，不看实现细节。
- **航空**：初步设计评审关注需求覆盖与安全影响。
- **互联网**：设计文档含"备选方案"与"不做什么"。
- **开源**：RFC 模板固定包含"缺点"与"替代方案"。
- **一般项目**：口头对齐，无记录，事后各执一词。

**是统一标准吗**：不是；但"被否方案要留痕"是共同点。

## 3. 验收标准怎么写才可判定？

**答：** 每条都能用一条命令判定通过与否，并写明边界与反例。写不出命令的条目，说明还没想清楚，不能下发。

- **可判定的形态**："跑 X 命令，退出码 0 且输出含 Y"，或"给定输入 Z，结果为 W"。
- **不可判定的措辞**："功能正常""性能可接受""代码质量良好"——这类词把判定权交给了实现者。
- **边界要写**：最小值/最大值/空输入/失败路径，否则"通过"只覆盖顺利路径。
- **反例要写**：什么情况必须失败（否则又回到"恒真"）。
- **谁审**：验收标准由**不写实现的人**过一遍，防止"按自己的理解写标准"。
- **代价**：写标准比写需求慢；但它同时是方案评审与验收的依据。

**各家做法**：

- **测试驱动开发**：先写测试（即可判定标准）再实现。
- **航空**：需求条目必须可验证（可测/可分析/可演示）。
- **互联网**：验收标准写成检查项或自动化用例。
- **外包项目**：验收标准写进合同，措辞模糊就是纠纷源。
- **一般项目**："做完给我看看"。

**是统一标准吗**：不是；"可验证"是共同要求。

## 4. 为什么"顺手改"是方向风险？

**答：** 因为范围一变，验证覆盖的就不再是真实改动：你验证的是"计划内的改动"，提交的是"计划内 + 顺手"的合集，多出来的部分没有任何证据。

- **典型形态**：顺手重构、顺手改格式、顺手升级依赖、顺手删"没用的"检查。
- **危害**：出问题时无法归因；回滚会连带撤掉有用改动。
- **判据**：改动清单与任务书对不上，就是方向风险信号。
- **处置**：要么拆成独立任务，要么明确放弃（写进"不做"）。
- **代价**：拆任务多一步；换来的是每次改动都可解释。

**各家做法**：

- **Linux 内核**：一个补丁只做一件事，混合改动会被要求拆分。
- **LLVM**：提交审查要求"单一目的"，格式化改动单独提。
- **Google**：小改动（small CL）文化，混合改动难审。
- **企业**：变更单绑定范围，超范围要重新审批。
- **一般项目**：随手提交，历史不可读。

**是统一标准吗**：不是；但"一次只做一件事"是高质量项目的共性。

## 5. 为什么对外文档要单独设闸？

**答：** 因为文档会被当作事实使用：读者不会去跑代码验证"是否已实现"，他们照着文档做决定。把设计写成现状、把计划写成能力，损害比代码缺陷更持久。

- **典型失真**：写"支持 X"但只是"计划支持"；写"性能提升 N 倍"但没有测量条件；写"已验证"但只跑了冒烟。
- **闸的位置**：发布前，由**不写这部分的人**核对"现状 vs 设计"是否分清。
- **可核对要求**：每个能力声明都能指向一个可复现的证据（命令、输出、版本）。
- **代价**：发布前多一道核对；换来的是读者不被误导。
- **延伸**：讲义、说明、对外承诺都适用；越是"给别人看"的内容，越要设闸。

**各家做法**：

- **标准组织**：规范状态（草案/正式/废止）显式标注。
- **开源项目**：README 标注成熟度（实验性/稳定），变更日志区分"计划"与"已发布"。
- **商业产品**：发布说明与路线图分开，路线图明确"非承诺"。
- **企业**：对外材料需法务/产品审核。
- **一般项目**：文档与实现长期不同步。

**是统一标准吗**：不是。

## 6. 可逆性分类怎么用？

**答：** 先判"这个决定能不能低成本撤回"：可逆的快速做、边做边学；不可逆的必须先评审、留记录。把两类混在一起，要么拖慢可逆的，要么放过不可逆的。

- **可逆**：命名、目录结构、内部接口、实验性开关——错了就改。
- **不可逆或高代价**：对外接口、数据格式、协议、编码定义、公开承诺。
- **用法**：决策记录加一个字段"可逆/不可逆"，评审强度随之不同。
- **避免两种错误**：把可逆的当不可逆（流程僵化）；把不可逆的当可逆（事后无法收拾）。
- **代价**：判断可逆性要一点经验；但比一律重流程便宜得多。

**各家做法**：

- **互联网产品**：可逆改动灰度发布，不可逆改动多重评审。
- **硬件**：流片不可逆，评审最重。
- **标准组织**：已发布规范基本不可改，只能出新版。
- **开源**：破坏性变更需要弃用周期。
- **一般项目**：一律同样流程，或一律不流程。

**是统一标准吗**：不是。

## 7. 实例：验收标准含糊导致"字面满足"

**现象**：任务书写"实现 X 功能并保证正确"，交付后"能用"但边界全错；返工时争议是"标准没写清"还是"实现没做好"。

**根因**：验收标准不可判定，判定权落到实现者手里；实现者按自己的理解选了最容易达成的解释。

**规矩**：验收标准必须命令可判定，并写明边界与必须失败的情形。

**机械防**：
- 任务模板强制"验收标准"栏，每条含命令与期望输出。
- 下发前由非实现者过一遍：这条能不能用一条命令判定？不能就退回。
- 收尾时把标准逐条对上真实输出，缺一条即未完成。

## 8. 实例：文档把设计写成现状

**现象**：讲义（或说明文档）写着"支持某能力"，实际只是计划；读者据此设计实验，全部落空。

**根因**：文档没有"现状 / 设计"的强制区分，作者按最理想的版本写。

**规矩**：对外内容必须显式区分"已实现（有证据）"与"设计中（未验证）"。

**机械防**：
- 能力声明必须附证据指针（命令、输出、版本），无证据的降级为"设计"。
- 发布前由非作者核对一遍"现状 vs 设计"用词。
- 文档模板固定两段式：现状 / 设计。

## 背景知识

### 术语与概念

- **方向风险**：做了不该做的事（需求误读、方案选错、范围漂移、承诺过度）。
- **一页方案**：改什么、选哪个、否了哪个、怎么验证、边界在哪。
- **可判定标准**：能用一条命令判通过与否的验收条件。
- **范围漂移**：实际改动超出声明范围。
- **对外承诺**：文档、说明、讲义中对能力的声明。
- **可逆性**：决定被撤回的成本。
- **闸**：可以停下来做判断的时刻。

### 对照

**方向评审形态**

- **硬件**：设计评审先于版图。
- **航空**：需求评审 + 追溯矩阵。
- **互联网**：设计文档评审。
- **开源**：RFC/提案。
- **共同点**：在"改起来最便宜"的时候判断方向。

**验收标准**

- **强**：命令可判定 + 边界 + 必须失败的情形。
- **中**：可演示、可人工核对。
- **弱**："功能正常"。
- **判据**：换个人能否独立判定。

**可逆性**

- **可逆**：命名、内部接口、实验开关。
- **不可逆**：对外接口、数据格式、编码定义、公开承诺。
- **处理**：可逆快做、不可逆慎重。
