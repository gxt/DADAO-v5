# 运行平台 -- 测试机运行环境

## 1. 为什么核内地址是 48 位，高 6 位是 cfxha？

**答：** 48 位 = 256 TiB，足够用；高 6 位直接编址 64 个核芯功能扩展，让“访问哪个 cfx 的资源”由地址本身决定。

- 高 6 位 `bits[47:42]` 选择 cfxha（64 个核芯功能扩展）。
- 剩余 42 位给每个 cfx 的内部空间。
- 不需要额外的“cfx 选择”寄存器或指令，地址即路由。

## 2. 为什么 RAM 只有一个段，基址在 `0xFC00_0000_0000`？

**答：** 测试机只需一段 RAM；放在 cfxha 63（power）段，避免与 cfx0–3 的核内空间冲突，也让 bootrom、SEE、应用都在同一段。

- 16 MiB，唯一 RAM 段。
- 基址 `0xFC00_0000_0000`（cfxha 63 / power）。
- 早期放在全 0，后来迁到这里。

## 3. 为什么复位向量是 `0xffff_ffff_0000`？

**答：** 它是 `cfx_power_hypv_excp_vector`，即 cfxha 63 的 hypv 异常向量；复位后硬件从那里取指。

- 64 KiB boot ROM。
- 用 `-bios` 加载 bootrom。
- 复位向量保持不变，与 RAM 基址迁移解耦。

## 4. 越界访问/取指为什么要分 `CFXMEM`（0x81）和 `unmapped`（0x87）？

**答：** `CFXMEM` 有 spec 原因（核内地址空间非法访问），`unmapped` 是测试机历史约定（无 cfx 归属）；两者语义不同，不能混。

- `umon` 段（cfxha 0）越界 ⇒ `CFXMEM`（0x81）。
- 其余段（含 power 63）越界 ⇒ `unmapped`（0x87）。
- 越界取指与越界数据访问同等对待，都要报异常。
- 退出码表已冻结，不得重排。

## 5. 为什么有 4 种运行模式，测试机只用 hypv/user？

**答：** 4 种模式（user/jail/supv/hypv）是架构定义；测试机为控制首版成本只启用 hypv 和 user，不启用 supv/smon。

- user/jail 为普通用户态，supv/hypv 为特权态。
- bootrom 在 hypv 配置完权限与向量后，直接跳到 user。
- 测试机只实现 cfx0/1/2/3/63。

## 6. 为什么 cfx 有 global mask / switch mask 两套掩码？

**答：** global mask 管“当前能不能触发”，switch mask 管“陷入后切到哪个掩码”；两者分离才能完成权限切换。

- 0 = 可触发，1 = 屏蔽；自身 cfxha 对应位由硬件忽略。
- `switch_run_mode` 决定陷入后的运行模式。
- 异常进入时，硬件把模式与掩码换成 switch 值。

## 7. trap 和 semihosting 为什么用两条不同路径？

**答：** 一般 trap 要进入 cfx 向量（软件处理），semihosting 是宿主 I/O，不需要向量；混在一起会让实现者误把 semihosting 送进向量。

- 一般 trap：`immu18[17:16] ≠ 2'b11` → 异常进入流程 → cfx 向量 → 由 `escape` 返回。
- semihosting：`immu18[17:16] == 2'b11` → 译码短路 → 不进入向量 → `IP += 4` 返回。
- 两条路由已冻结，不得混用。

## 8. semihosting 为什么用 `immu18[17:16] == 2'b11` 作 tag，而不是专用指令？

**答：** 复用 `trap` 编码，不新增指令；用 `immu18` 的高 2 位做 tag，与 cfxha 无关，任何 cfx 都能发起。

- 该 tag 无上游 spec 依据，属 v5 测试机约定。
- 与一般 trap 只靠这 2 位区分。
- 服务号在 `rd16`，参数块指针在 `rb16`，返回在 `rd8`。

## 9. 为什么 semihosting 无 `escape`，直接 `IP += 4` 返回？

**答：** semihosting 不进入向量，没有“异常现场”要恢复；直接跳过 `trap` 即可。

- 服务完成后由实现层 `IP += 4`，并写回 `rd8`。
- 与一般 trap 的 `escape cfxha, [excp_cause_ip, 4]` 返回不同。
- guest 侧不需要写 `escape`。

## 10. 为什么用 `SYS_EXIT` 取代 exit port？

**答：** semihosting 已经提供“guest 请求宿主”的通道，停机不必再占一个 MMIO 设备；退出码也能忠实传到宿主 `$?`。

- `SYS_EXIT`（0x18）/ `SYS_EXIT_EXTENDED`（0x20）。
- 常规退出原因码为 `0x20026`（ApplicationExit）。
- exit-port MMIO 设备已随旧 RAM 段一起删除。

## 背景知识

### 术语与概念

- **cfx（核芯功能扩展）**：按功能划分的核内资源单元；cfxha 是其 6 位编号。
- **cfxha**：48 位核内地址的高 6 位（`bits[47:42]`），选择 64 个 cfx 之一。
- **PTBR**：页表基址寄存器；地址转换第一步用它选择地址空间，并检查运行模式权限。
- **semihosting**：guest 通过 `trap` 请求宿主 I/O（打开/读写文件、取时间、退出等）。
- **trap / escape**：`trap` 进入 cfx 异常向量；`escape` 完成异常退出并返回。
- **IP**：当前正在执行的指令地址（不是下一条）。
- **ABI**：寄存器用途与参数传递约定；semihosting 复用 `rd16`/`rb16`/`rd8`。
- **大端**：多字节数据的高位字节在低地址；v5 semihosting 的参数块按大端读取。

### 对照

- **Arm Semihosting**：v5 的服务号值取自 Arm Semihosting；但 v5 用 `trap` 的 `immu18` tag 发起，而不是 Arm 的 `SVC`/`HLT`。
- **RISC-V semihosting**：通常用 `ebreak` 加特定寄存器约定；v5 用 `trap` + `immu18[17:16]==2'b11`。
- **一般 trap**：进入 cfx 向量、由 `escape` 返回；**semihosting**：不进入向量、直接 `IP += 4`。
- **exit port**：早期用 MMIO 设备停机；v5 改为 semihosting `SYS_EXIT`，不再保留 exit port。
