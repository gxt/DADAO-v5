# DDLN 写作与目录规则

> 本文件是 `docs/DDLN/` 的**内容侧规则**：目录、命名、草稿/定稿流程、写作规范、各家对照要求。
> agent 的权限、shell 白名单、提交纪律不在此文件（归 agent 配置）。
> 两者冲突时，以**更严格**者为准。

## 目录结构

`docs/DDLN/` 按系列分目录，根目录只留 `README.md` 与 `.gitignore`：

- `A-指令系统/`
- `B-参考模型/`
- `C-资源管理/`
- `D-运行平台/`
- `E-编译工具/`
- `F-测试体系/`
- `G-操作系统/`
- `H-系统集成/`
- `X-风险管控/`
- `Y-研发流程/`
- `Z-发展历程/`

约定：

- 文件建在所属系列目录内，不再放回 DDLN 根目录。
- 命名：`TT-<系列字母><编号>-<系列名>--<分册名>.md`，如 `TT-C001-资源管理--核芯功能扩展.md`；`DD-` 同理。
- 系列名统一四个字（2+2），与已定名系列保持一致。
- 尚未定名的系列只留占位文件，定名后再建目录、再迁移。

## 草稿与定稿

- `TT-*` 是草稿（被 `.gitignore` 忽略）；`DD-*` 是定稿。
- **定稿 = 把对应 `TT-*` 复制成 `DD-*`**，TT 原件保留（不改名、不移动、不删）。
- **`DD-*` 不做直接更改**：它与对应 `TT-*` 只可能"等同"或"落后"；落后时只能用复制从 `TT-*` 覆盖，改内容一律先改 `TT-*`。
- **改 `DD-*` 先复制成 `TT-*`**（TT 不存在时以此建立工作副本），编辑只落在 `TT-*`；何时复制回 `DD-*` 由用户明确要求。
- **同步**：把各子目录中的 `TT-*` 逐个复制为同名 `DD-*`，这是 `DD-*` 追平 `TT-*` 的唯一方式；何时执行由用户明确要求。

## 写作规则

1. **每题先给一句话答案**，再列要点；简洁，不过度展开，也不过度压缩。
2. **不做交叉引用**：不写仓库路径、不写决策编号、不写"见 Qx"、不在末尾加"依据"行。
3. **英文**：术语可用英文；非术语动词/普通词用中文（如 `spill` → 寄存器溢出）。
4. **慎用表格**：能用列表或段落表达就优先用列表/段落；表格单元格若在显示上会跨行且超过 3 行，不要用表格。
5. **背景知识**：`## 背景知识` + `### 术语与概念` + `### 对照`；只补正文没讲的，合并重复项。
6. **数字/事实不编造**：估算标"约 / 区间"；区分事实与推理；未核实的写"待核"。
7. **跨篇或结构性改动先与用户商量**：新增系列、拆并分册、改全篇体例，不在单篇内自行决定。
8. **现状与设计分开写**：设计意图与"当前实现到哪一步"要显式区分，不把未实现写成已实现。

## 指导原则（写作前先自问）

目标是**更深**，不是更长：宁可把一个点讲透，也不要把所有点都铺开。动笔前先回答这四个问题，并把答案体现在内容里（不必写进正文）：

1. **顶尖专家会做哪些用户没要求的事？** 追溯概念的原始出处；给出边界、反例与常见误解；说明"为什么不是另一种设计"；把当前概念与相邻概念连起来；给出可核对的数量与事实。
2. **他们会从哪些最原始的素材入手？** 标准原文（IEEE 754、ISO/IEC 等）、原始论文（如 Knuth 的 MMIX）、厂商/基金会官方 ISA 手册（x86、ARM、RISC-V）、参考实现源码与测试（LLVM、QEMU）、历史文档与早期版本——而不是只读已经整理好的二手材料。
3. **他们会用什么具体方法和工具？** 逐条对照标准条款与手册表格；用汇编器/反汇编器/模拟器做小例子（在权限允许时）；手算边界值（0、±0、NaN、Inf、最大值、溢出点）；交叉核对多个独立来源并记录分歧。
4. **除了你我，还有什么能证明结果正确？** 标准/手册的原文条款；可复现的汇编/反汇编输出与模拟器实测；第三方实现（LLVM/GCC/QEMU）的行为；已发表的教材、论文或官方勘误。

## 标准与各家对照（写作要求）

**6 个参考 ISA**：x86-64、ARM64、RISC-V、MIPS、SPARC、PowerPC。对照时以这 6 个为基准；被说明对象（SimRISC/DADAO）不占这 6 个名额。需要新增参考 ISA 时先问用户。

- **有统一标准**：在 Q 内标注标准与条款（如 IEEE 754-2019 §7.5、ISO/IEC 2382-1:1993、RFC 1700），并说明本项目是"遵循 / 偏离 / 扩展"。
- **各家方案不同**：从 6 个参考 ISA 中选有代表性的 4 个以上分别说明；缺项写"无 / 不适用"，不要用"大家都这样"概括。
- **分析原因**：从异常模型（陷阱 vs 状态位）、性能/面积、兼容性、编码成本、软件约定五个角度解释"为什么不同"。
- **不确定的条目**：标"待查手册 / 待核"，不臆造；估算标"约 / 区间"。
- **适用范围**：每个 Q 至少回答"这是统一标准，还是各家不同"；纯本项目专有设计（如 `rwii`、RAS）可只写设计动机，但要说明"别家没有 / 做法不同"。
- **对照版式：一家一行**。"各家做法"与 `### 对照` 都用子列表，一个对象一条，不把多家挤在一行用分号分隔。
