# 参考模型 -- ISA 语义模型

**本册要点**

- 把语义写成**可执行的形式语言**，换来的是"可被工具检查"，而不只是"可被人阅读"。
- 形式模型的产出不止仿真器：类型检查、文档、覆盖统计、测试生成、定理证明入口。
- **内存与外设必须外置**到 harness：模型只管架构状态与指令语义。
- 跨边界只留**极少的字节级原语**，多字节访问由模型按目标端序组装。
- 从厂商文档生成模型，是本领域最可靠的一条路——前提是上游提供机器可读描述。
- 成本不在写第一版，而在**跟规范同步**。

## 1. 为什么把语义写成可执行的形式语言，而不是"文字 + 伪代码"？

**答：** 因为文字与伪代码无法被机器检查：写错了没人发现，写法不一致也没人发现。形式语言能类型检查、能执行、能统计覆盖，把"规范是否自洽"从人工审读变成工具报错。

- **可检查**：类型错误（位宽不匹配、未定义变量）在编译期暴露。
- **可执行**：同一份定义直接跑出仿真器，规范与实现合一。
- **可统计**：哪些语义规则被测试走到，能算出来。
- **可派生**：文档、测试序列、定理证明定义都从同一份源产生。
- **代价**：学习成本与工具链成本；写一份可执行语义的工作量约等于写一个模拟器。

**各家做法**：

- **ARM64**：架构规范本身就是机器可读描述，形式模型是其下游产物。
- **RISC-V**：形式可执行规范被官方采纳，与参考模拟器互为参照。
- **PowerPC**：从 IBM 的 XML 语义描述机械转换。
- **x86-64**：研究性手写模型，覆盖部分指令，无官方支持。
- **MIPS**：CHERI 变体有形式模型，通用 MIPS 没有。
- **SPARC**：无已知形式模型（**待核**）。

**是统一标准吗**：不是。是否有、用哪种语言，由各生态决定。

## 2. 形式模型能提供什么？

**答：** 五类产出：类型检查、文档、可执行仿真、覆盖统计、测试与证明的入口。它们共用一份源，所以不会互相漂移。

- **类型检查**：把"规范写错"变成编译错误。
- **文档生成**：一份源出多种格式，避免文档与模型不同步。
- **可执行仿真**：直接跑 ELF，作为对照实现。
- **覆盖统计**：哪些规则被用例走到，哪些从没被触发。
- **测试生成**：按语义自动产生指令序列，覆盖边界与组合。
- **证明入口**：导出定理证明器定义，供交互式证明或二进制验证。
- **边界**：这些都只覆盖"架构可见语义"，不覆盖时序与性能。

**各家做法**：

- **RISC-V**：上述五类产出都有公开实践。
- **ARM64**：以文档与仿真为主，证明在特定项目中进行。
- **PowerPC**：以文档与仿真为主。
- **x86-64**：研究项目多聚焦语义与内存模型。
- **MIPS**：CHERI 项目覆盖能力与证明。
- **SPARC**：无公开实践（待核）。

**是统一标准吗**：不是。

## 3. 为什么内存与外设必须外置？

**答：** 因为内存与外设是**平台**而非**架构**：同一份 ISA 语义配上不同内存大小、不同设备，行为就不同。把它们写进模型，模型就无法复用，也无法与不同平台对照。

- **模型负责**：架构状态（寄存器、控制状态）、指令语义、异常与陷入的架构效果。
- **harness 负责**：内存分配、设备、加载器、时间与终止条件。
- **跨边界**：只保留读字节、写字节这类原语；多字节访问在模型内按端序组装。
- **好处**：换平台只换 harness；模型保持与平台无关。
- **风险**：边界划不清时，语义会悄悄漏到 harness 里，模型的"规范权威性"就打折。

**各家做法**：

- **RISC-V**：模型 + C harness，平台设备在 harness 侧。
- **ARM64**：模型与平台分离，平台由参考模型/仿真器提供。
- **PowerPC**：同样分离。
- **研究性模型**：常把内存简化进模型，换取易读性。
- **本项目的历史先例**：内存住在 harness，模型只通过字节级原语访问，并按大端组装多字节。

**是统一标准吗**：不是。

## 4. 从厂商文档生成模型意味着什么？

**答：** 意味着"规范即模型"：上游若有机器可读的语义描述，模型就是它的机械转换，人工抄写环节被消除，规范与模型的偏差降到最低。

- **前提**：上游提供机器可读描述（架构描述语言、结构化 XML 等）。
- **收益**：不存在"手抄漏一行"；规范更新可重新生成。
- **代价**：转换器本身要维护；上游描述的抽象层次决定模型好不好用。
- **对比手写**：手写灵活、可读，但每一行都是潜在的抄写错误。
- **现实**：多数 ISA 没有机器可读描述，只能手写。

**各家做法**：

- **ARM64**：从机器可读架构描述生成。
- **PowerPC**：从 XML 生成。
- **RISC-V**：手写为主（规范以文字 + 形式模型并行维护）。
- **x86-64**：手写研究模型。
- **MIPS / SPARC**：无公开生成路径（待核）。

**是统一标准吗**：不是。

## 5. 写一份 ISA 语义模型的成本在哪？

**答：** 不在第一版，而在**跟规范同步**：规范改一处，模型要改、测试要重跑、文档要重生成，而这条链条上任何一环断了，模型就变成"过时的权威"。

- **首版成本**：与写一个模拟器相当；难点在异常、陷入、边界语义。
- **同步成本**：每次规范变更都要重新生成/修改并回归。
- **验证成本**：模型自己也要被验证（与第二路实现对照、人工复核边角）。
- **维护成本**：有人负责、有版本、有发布节奏。
- **降本手段**：先做子集（易错边角 + 常用指令），用生成器补齐重复部分。

**各家做法**：

- **RISC-V / ARM64**：有专门团队长期维护。
- **PowerPC**：由上游描述驱动，同步成本较低。
- **研究项目**：常停在论文规模，随后过时。
- **企业私有 ISA**：多不公开模型，靠内部仿真器。
- **本项目**：尚未决定是否投入。

**是统一标准吗**：不是。

## 6. 模型如何与规范版本绑定？

**答：** 同号发布或显式映射：模型必须声明"我对应规范的哪一版"，且这个声明要能被机械读取，否则判据的时效性无法判断。

- **同号**：模型版本与规范版本一一对应，最直观。
- **显式映射**：模型版本独立，但带一份"对应规范版本"的声明。
- **为什么必须绑定**：判据失效常常不是算错，而是"按旧规范算的"。
- **配套**：结果记录里带上模型版本与规范版本。
- **代价**：每次规范变更都要发新模型版本。

**各家做法**：

- **标准生态**：规范与模型同步发布，版本号对齐。
- **开源项目**：模型独立演进，用提交哈希对应。
- **企业**：内部版本矩阵，构建时锁定。
- **一般项目**：无版本声明，判据时效不可知。
- **本研究仓**：判据需声明对应的规范版本。

**是统一标准吗**：不是。

## 7. 什么时候才值得上形式模型？

**答：** 只在"规范趋于稳定、且需要向上游或硬件证明一致性"时值得；持续变更阶段上形式模型，维护成本会超过收益。

- **稳定期资产**：形式模型的价值在"一份定义产出仿真器、文档、覆盖与测试"，前提是定义本身不再频繁变。ISA 还在改时，模型跟着改的成本与收益不成比例。
- **权威性不会自动成立**：模型只覆盖写进去的部分，未覆盖的扩展会以"跳过/不支持"出现；在自有扩展上，它不能替代规范文本，也不能自动成为裁判。
- **外部先例的教训**：只做少量切片、其余标记不支持的"形式模型"，看起来完整，实际不能承担日常判据；把它放进门控，会让"没覆盖"伪装成"没问题"。
- **重启触发条件**：ISA 冻结、流片前需要与 RTL 对拍、或需要对关键性质做定理证明——三者出现其一再投入，且先限定范围（例如只做内存模型或只做异常语义）。
- **替代手段**：歧义探测 + 精确计算 + 裁定回归三件窄事，能在高频变更期覆盖大部分风险，成本远低于全量形式化。
## 8. 机器可读语义库能不能直接拿来用？

**答：** 不能直接换一个指令系统用；但它的**形态**值得照抄——编码、语义、文档、仿真器从同一份数据产出。

- **先分清两层**：手册里的伪代码块通常**不可执行**；机器可读真源是另一层数据文件，语义片段带类型、能被编译执行。把"手册里有伪代码"当成"已有可执行规范"是常见误解。
- **一条指令一条记录**：编码位域、汇编语法、语义片段、合法性条件、可见权限放在同一条记录里，改一处、下游各处同步。
- **先展开再使用**：数据经继承与配置展开成"已解析规格"，下游工具只读展开结果，避免每个工具各自解释条件分支。
- **一份数据多路产出**：文档、指令集模拟器、C 头文件、解码包、指令附录、配置手册都从同一源生成；改语义不必逐个改下游。
- **规模可统计但不等于正确**：指令、寄存器、扩展的条数能现场数出来，但"条数多"只说明覆盖广，不说明语义对。
- **成熟度要看清**：公开生态普遍自述"结构会变、内容未完成"，**只校验了编码与汇编语法**这类可机械对账的部分。适合作形态参考，不适合作外部依赖。

**各家做法**：

- **RISC-V**：数据文件 + 类型化语义片段 + 多路生成，规模最大（指令上千、寄存器数百），仍在演进；另有形式语言模型作为正式语义。
- **ARM64**：规范本身即机器可读，语义片段是正式定义的一部分，配套官方参考实现生态。
- **PowerPC**：厂商 XML 语义描述机械转换。
- **x86-64**：无官方机器可读语义，研究性模型覆盖部分指令。
- **MIPS**：通用 MIPS 无；CHERI 变体有。
- **SPARC**：无公开机器可读语义（**待核**）。

**是统一标准吗**：不是。连"语义放在数据文件的哪一层"都没有共识。

## 背景知识

### 术语与概念

- **可执行语义**：用形式语言写成的、能被执行的指令语义。
- **harness**：包在模型外面的驱动与平台（内存、设备、加载器）。
- **跨边界原语**：模型与 harness 之间允许的少量操作（如读/写字节）。
- **端序组装**：多字节值按目标端序在模型内拼装。
- **规格覆盖**：被用例走到的语义规则比例。
- **同号发布**：模型与规范版本一一对应。
- **子集模型**：只覆盖部分指令的模型，用于快速起步。
- **机器可读语义库**：把编码、语义片段、文档等集中成结构化数据的仓库。
- **类型化语义片段**：带位宽/类型检查的指令行为描述，能被编译执行。
- **已解析规格**：经继承与配置展开后的数据，供下游工具直接读取。
- **厂商扩展位**：在基础指令系统之上声明私有扩展的机制。

### 对照

**语义描述形态**

- **机器可读架构描述**：ARM64（可直接生成模型）。
- **结构化语义描述**：PowerPC（XML 转换）。
- **形式语言手写**：RISC-V、x86-64、CHERI-MIPS。
- **文字 + 伪代码**：多数商业 ISA。

**模型与平台的分工**

- **强分离**：模型只碰架构状态，平台在 harness（主流做法）。
- **弱分离**：内存简化进模型，易读但不可复用。
- **判据**：换平台是否要改模型。

**版本绑定**

- **同号**：最直观，维护成本高。
- **提交哈希**：灵活，需要额外映射表。
- **无声明**：判据时效不可知，最危险。
