# 参考模型 -- 可执行模型作判据

**本册要点**

- 可执行模型能当判据，前提是**它只从规范派生**；否则它只是"另一个实现"。
- 黄金模型（脚本）负责可读与易改，模拟器负责真实运行；两者互补，不能互相替代。
- **弃权必须单列**：环境不支持不是通过，是"未判定"。
- 判据的**版本**要与规范版本一起锁进结果，否则时效不可知。
- 参考模型也会错：发现分歧时先判"哪边错"，不能默认被测错。
- **周期级模型不能当语义判据**：差异可能来自微架构而非语义。

## 1. 为什么可执行模型能当判据？

**答：** 因为它把"规范说的语义"变成可运行的东西：给定同一输入，它能给出应有的寄存器与内存状态。判据不是它的代码，而是它**从规范派生**这一事实。

- **前提一**：模型只读规范，不读被测实现的源码或产物。
- **前提二**：模型的版本与规范版本绑定，可核对。
- **前提三**：结果里记录模型版本，事后能复现。
- **为什么不用"人读规范"当判据**：不可规模化，且人也会读错。
- **边界**：模型只管架构可见状态，不管时序与性能。

**各家做法**：

- **RISC-V**：形式模型与参考模拟器都可作对照，二者不一致时需第三方裁决。
- **ARM64**：商用参考模型（Fast Model/FVP）用于架构测试，闭源。
- **QEMU（多架构）**：常被当"事实参照"，但它明确不是规范。
- **gem5**：周期级模型，差异可能来自微架构。
- **本研究仓的历史先例**：用规范派生的脚本模型作"中立裁判"，与三路实现差分。

**是统一标准吗**：不是。

## 2. 黄金模型与模拟器各适合什么？

**答：** 黄金模型适合"读得懂、改得快、判得细"；模拟器适合"跑真程序、覆盖整机行为"。前者是尺子，后者是跑道。

- **黄金模型（脚本级）**：逐指令实现语义，输出寄存器与内存快照；易读、易审、易加边界用例。
- **模拟器（系统级）**：加载 ELF、跑完整程序；能发现"单指令都对、组合起来错"的问题。
- **黄金模型的弱点**：不跑真程序，覆盖不到加载、调用约定、库交互。
- **模拟器的弱点**：代码量大，自己有 bug，且难判断"哪条语义错了"。
- **配合方式**：先用黄金模型判单指令与边界，再用模拟器判程序级行为。
- **不做全量第四实现**：在已有编译器、模拟器、硬件之外再维护一份"全量黄金模型"，等于多养一个实现；它同样会有 bug，还会诱导"以实现为准"。只保留三件窄用途：歧义探测、精确计算（浮点/位宽/舍入）、把已裁定结论固化成回归断言。
- **歧义探测的形态**：遇到规范未明处，模型显式返回"未指定/规范缺口"并阻断，不选默认值；把"哪条、哪几种解释、各自结果"列出来交给用户，而不是给一个看似确定的答案。
- **裁定回归**：用户每做一次语义裁定，就把该裁定固化成向量或断言；以后任何实现漂移都会被这一条抓住，不靠记忆。

**各家做法**：

- **RISC-V**：参考模拟器 + 形式模型的仿真器，两者并用。
- **ARM64**：参考模型（架构级）+ 硬件/仿真器（系统级）。
- **QEMU**：只有模拟器路线，逐指令判据靠测试内断言。
- **内核测试**：以模拟器或硬件跑完整系统。
- **本研究仓的历史先例**：脚本黄金模型作裁判，模拟器提供程序级覆盖。

**是统一标准吗**：不是。

## 3. 为什么"弃权"必须单列？

**答：** 因为"没判定"与"通过"是两件相反的事：把弃权算成通过，会让覆盖看起来完整，而实际上那块从未被检验。

- **弃权的来源**：harness 不支持某条指令、环境缺设备、配置未启用。
- **正确处置**：单列统计，并在报告里指出"哪一块未判定"。
- **为什么容易混**：多数框架只分通过/失败，跳过与不支持被归入通过。
- **代价**：弃权多时报告不好看；但它暴露的是能力缺口，不是噪音。
- **配套**：弃权要有原因码，且能按原因聚合。

**各家做法**：

- **lit 类框架**：有"不支持"状态，与失败区分。
- **TAP 协议**：有"跳过"状态。
- **合规套件**：未覆盖项在报告里单列。
- **一般脚本**：跳过即通过，最危险。
- **本研究仓的历史先例**：差分统计把"弃权"单列，与一致/分歧并列。

**是统一标准吗**：部分统一（TAP 与多数测试框架都支持"跳过"语义）。

## 4. 为什么版本锁定对判据尤其重要？

**答：** 因为判据一变，"通过"的含义就变了：同一份向量昨天通过、今天失败，可能只是模型升级了。版本不锁，回归结果无法解释。

- **锁什么**：模型版本、规范版本、配置（位宽、扩展、端序）、harness 版本。
- **记在哪**：结果文件里，与用例结果同层。
- **比较规则**：只有版本相同的结果才能比较趋势。
- **代价**：升级要重跑基线；换来的是"变化可解释"。
- **反例**：升级模型后大批用例变红，无法判断是模型修对了还是引入了 bug。

**各家做法**：

- **标准生态**：模型与规范同步发布，版本号即判据版本。
- **开源项目**：以提交哈希为准，结果里记录哈希。
- **企业**：构建时锁定版本矩阵。
- **一般项目**：不记录版本，回归不可解释。
- **本研究仓**：结果需带模型与规范版本。

**是统一标准吗**：不是。

## 5. 参考模型自己错了怎么办？

**答：** 先判定"哪边错"，再决定改谁：与规范逐条比对、用第二路实现交叉、必要时人工推导。默认"被测错"是最常见的误判。

- **判定顺序**：查规范条款 → 看第二路实现 → 手算边界值 → 最后才怀疑被测实现。
- **常见模型 bug**：边界截断、符号扩展、端序、异常优先级。
- **记录方式**：模型 bug 也要登记，并修模型、补用例（防止复发）。
- **为什么容易搞反**：模型被当成"权威"，一旦分歧就归咎被测方。
- **代价**：判定过程慢；但这是唯一能保住判据可信度的做法。

**各家做法**：

- **合规生态**：模型 bug 走公开勘误流程。
- **开源项目**：靠多实现交叉 + 议题讨论。
- **企业**：参考模型有专门团队维护与响应。
- **一般项目**：模型即真理，错了也不知道。
- **本研究仓**：分歧需归因，不得默认被测错。

**是统一标准吗**：不是。

## 6. 为什么周期级模型不能当语义判据？

**答：** 因为周期级模型的差异可能来自微架构（流水线、缓存、预测），而不是架构语义；用它判语义会把"实现自由度"当成缺陷。

- **语义判据的要求**：只依赖架构可见状态（寄存器、内存、异常）。
- **周期级模型的输出**：还包含时序、缓存命中、总线行为——这些不在架构定义里。
- **正确用法**：周期级模型用于性能研究与微架构验证，语义判据交给功能级模型。
- **代价**：功能级模型跑得慢于"只跑关键路径"，但结果可判定。
- **反例**：用周期模型比对执行时间，得出"实现不对"的结论。

**各家做法**：

- **功能级模拟器**：语义验收的标准载体。
- **周期级模型**：性能与微架构研究。
- **硬件仿真**：时序与协议验证。
- **混合**：功能级判语义、周期级判性能，分两套门控。
- **本研究仓的历史先例**：周期级模型参与差分时，只比架构可见状态。

**是统一标准吗**：不是。

## 7. 实例：用实现生成期望值

**现象**：测试全绿，但换成另一版编译器后行为变了，测试仍然全绿——因为期望值是上一版编译器生成的。

**根因**：期望值来源经过了被测实现，判据被污染；测试实际在验证"两版实现一致"。

**规矩**：期望值只能从规范派生；生成脚本不得引用被测实现的产物。

**机械防**：
- 生成脚本做源码级检查：不得引用被测实现的输出路径或产物。
- 期望值带来源标记（规范条款 + 生成器版本）。
- 审查时抽查若干条期望值，手算核对。

## 8. 实例：把"弃权"算成"通过"

**现象**：覆盖率报告显示 100%，但其中一批用例是"环境不支持，跳过"；真实覆盖远低于报告。

**根因**：统计口径把"未判定"并入"通过"，报告因此失真。

**规矩**：弃权单列，并给出原因码；覆盖率只统计"已判定"的用例。

**机械防**：
- 结果文件里 `skipped` 与 `pass` 分开统计。
- 报告头部显示三类计数（通过 / 失败 / 未判定），不允许只显示通过率。
- 弃权原因按类别聚合，作为能力缺口的输入。

## 8. 模型的产出是判据，还是测试向量？

**答：** 主产出是**能跑的可执行模型**；测试向量是它的下游派生视图，不是替代品。

- **只有向量时看不见交互**：单指令向量表覆盖不到"取指 × 地址检查""访存 × 总线拒绝""异常 × 现场保存"这类跨单元缺陷，而它们往往是真 bug 的大头。
- **可执行模型能跑整段程序**：加载已有镜像、逐条比状态、走到退出，才能暴露交互缺陷。
- **向量仍然必要**：它负责边界枚举（宽度、符号、对齐、异常）与"每条语义路径至少被走到一次"的覆盖断言。
- **输入必须独立设计**：向量的输入空间（边界值、随机种子、组合）不能由模型自己挑，否则是自己出题自己判卷。
- **覆盖统计来自模型结构**：分支与条件由模型给出，"哪些规则从没被触发"才可机械回答。
- **顺序判断**：先做能跑的可执行模型，再从它派生向量；反过来只会得到一张永远不完整的期望值表。

**各家做法**：

- **ARM64**：官方机器可读规范直接生成模型，配套一致性测试套件；向量由套件而非模型自行生成。
- **RISC-V**：形式模型产仿真器，另有独立一致性测试套件；两者不共用输入生成器。
- **x86-64**：研究性模型 + 商用测试，向量多来自实测回归。
- **PowerPC**：语义描述产模型，测试以厂商套件为主。
- **MIPS / SPARC**：视项目而定，缺少公开的可执行规范（**待核**）。

**是统一标准吗**：不是；但"模型产判据、套件产输入"这个分工是较一致的实践。

## 9. 有了参考模型，模拟器还剩下什么价值？

**答：** 速度、系统、生态与"第二意见"——四样都不能由参考模型替代。

- **速度**：解释执行通常比优化过的模拟器慢一到三个数量级；长跑测试与真实软件只在后者上跑得完。
- **系统面**：设备与总线、启动固件、多权限级、地址翻译、半主机调用等平台能力，参考模型一般不建模。
- **生态**：加载器、调试器、执行跟踪、状态快照、覆盖率工具，围绕模拟器成熟。
- **独立第二方**：两者独立实现时，分歧才有信息量；若让模拟器照抄模型，"差分"就退化成自证。
- **纪律**：分歧以**规范条款**裁定，而不是"模型一定对"；否则模型一旦写错，整条验证链一起错。
- **互补关系**：模型回答"语义对不对"，模拟器回答"程序在平台上跑得对不对"。

**各家做法**：

- **ARM64**：机器可读规范 + 高性能模拟器并存，前者判语义、后者跑软件。
- **RISC-V**：形式模型作黄金参照，模拟器作快速平台，另有独立一致性套件。
- **x86-64**：以商用模拟器与实测为主，无官方形式模型。
- **PowerPC**：厂商模型与模拟器并存。
- **MIPS / SPARC**：以模拟器为主，缺少形式参照（**待核**）。

**是统一标准吗**：不是。

## 背景知识

### 术语与概念

- **判据（oracle）**：判断结果对错的依据，本系列要求从规范派生。
- **黄金模型**：脚本级语义模型，便于审读与加用例。
- **参考模拟器**：能跑完整程序的实现，用作对照。
- **弃权**：环境或工具不支持，结果未判定。
- **版本锁定**：把模型、规范、配置、harness 版本一起记录。
- **仲裁**：多路分歧时判定哪一路错的过程。
- **架构可见状态**：寄存器、内存、异常等规范定义的状态。
- **可执行模型**：能加载镜像并执行指令语义的模型，产出状态序列与终态。
- **交互缺陷**：只有多单元组合（取指、访存、异常）才暴露的缺陷。
- **派生视图**：从模型或数据生成的下游产物，如向量表、文档、头文件。
- **第二意见**：独立实现给出的对照结论，用于发现分歧。

### 对照

**判据载体**

- **脚本黄金模型**：易读易改，覆盖单指令与边界。
- **参考模拟器**：覆盖程序级行为，代码量大。
- **形式模型生成的仿真器**：与规范同源，可信度高。
- **周期级模型**：适合性能，不适合语义判据。

**未判定状态**

- **强**：测试框架区分跳过/不支持/失败。
- **弱**：脚本只报通过/失败。
- **判据**：报告里能否看出"哪块没测"。

**分歧仲裁**

- **强**：规范条款 + 多实现 + 人工推导。
- **弱**：默认被测错。
