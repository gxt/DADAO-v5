# 参考模型 -- 判据派生与差分

**本册要点**

- 期望值有四种来源：手算、生成器、签名、程序输出；粒度与可扩展性依次变化。
- 生成器必须能"**重派生 + 逐字节比对**"，否则它会悄悄漂移。
- 签名是"把状态压成可比值"，粒度选窄会漏检，选宽会难定位。
- 差分统计至少三类：**一致 / 分歧 / 弃权**；分歧要能定位到具体一路。
- 差分只能覆盖"规范 → 实现"，**看不见"上游文档 → 规范"**。
- 独立性要能机械检查：生成脚本不得引用被测实现的产物。

## 1. 期望值有哪几种来源，边界在哪？

**答：** 手算最可审计、生成器最可扩展、签名最便于跨实现比较、程序输出最接近真实运行；四者粒度不同，不能互相替代。

- **手算**：适合少量边角（溢出、对齐、保留编码），可审计但不可扩展。
- **生成器**：按规范批量产出期望值；必须可重派生比对，且不引用被测实现。
- **签名**：把最终状态压成字符串；跨实现可比，但定位信息少。
- **程序输出**：端到端结果（退出码、标准输出）；最接近用户视角，粒度最粗。
- **选择判据**：要"发现"用生成器，要"定位"用手算，要"跨实现比"用签名，要"看整体"用程序输出。

**各家做法**：

- **合规套件**：签名比对为主（跨实现、可自动化）。
- **编译器测试**：结构断言 + 参考输出。
- **内核自测**：程序输出 + 测试内断言。
- **硬件验证**：参考模型逐拍比对（周期级）。
- **本研究仓**：向量 + 生成器 + 签名混合。

**是统一标准吗**：不是。

## 2. 生成器为什么要"重派生 + 逐字节比对"？

**答：** 因为生成器与产物会互相漂移：产物被手改、生成器改了但没重跑、输入变了没发现。只有"重新生成并与入库产物逐字节比对"才能把漂移变成可判定的失败。

- **重派生**：同一输入、同一生成器，产出应完全一致（顺序、时间戳、路径都要固定）。
- **逐字节比对**：不是"语义等价"，而是字节一致——排除隐性格式变化。
- **差异定位**：报出第一处不同的位置，便于快速归因。
- **进门控**：比对必须自动跑；手动比对等于没有。
- **代价**：要求生成过程确定（禁随机、禁时间戳、禁绝对路径）。

**各家做法**：

- **编译器**：表生成后与入库版本比对。
- **协议项目**：从 schema 生成代码，CI 校验生成结果无差异。
- **文档站**：目录与索引自动生成并校验。
- **一般项目**：生成物手工维护，漂移长期存在。
- **本研究仓**：生成器提供检查模式并接门控。

**是统一标准吗**：不是。

## 3. 签名怎么设计，代价是什么？

**答：** 签名要覆盖"所有架构可见状态"，但每多一维，跨实现比较的成本与定位难度都上升；常见做法是寄存器全量 + 内存摘要 + 异常状态。

- **必须覆盖**：通用寄存器、浮点/向量寄存器、控制状态、内存中被写过的区域、异常与陷入状态。
- **内存摘要**：不能只算整块哈希（定位不了），也不能全量导出（体积大）；常取"被写区域 + 摘要"。
- **粒度权衡**：粒度窄（只比退出码）漏检；粒度宽（全内存导出）难定位、体积大。
- **稳定性**：签名算法必须固定版本，否则跨版本不可比。
- **配套**：签名之外保留失败细节（差异寄存器列表），否则只有"不同"没有"哪里不同"。

**各家做法**：

- **合规套件**：寄存器 + 内存区域签名，逐字节比对。
- **模拟器测试**：常只比寄存器，漏检内存错误。
- **编译器测试**：比输出文本，不比状态。
- **硬件验证**：逐拍全状态比对，成本最高。
- **本研究仓**：向量带期望状态（寄存器 + 内存片段）。

**是统一标准吗**：不是。

## 4. 差分统计分几类？分歧怎么定位？

**答：** 至少三类：一致、分歧、弃权；分歧还要记"哪几路不同"，否则只知道"有问题"，不知道"谁跟谁不同"。

- **一致**：所有参与路给出相同结果。
- **分歧**：至少一路不同；记录"参与路集合 + 每路结果摘要"。
- **弃权**：某路不支持该用例；不算通过，也不算分歧。
- **定位方法**：按用例聚合（同一指令集中分歧 ⇒ 语义疑点）、按路聚合（某一路普遍不同 ⇒ 该实现可疑）。
- **趋势意义**：分歧数下降不等于质量提升，可能是覆盖减少或弃权增多——三个数要一起看。

**各家做法**：

- **合规套件**：与参考签名比对，失败即"该扩展该用例不同"。
- **编译器**：多实现对比编译产物（少见于生产流程）。
- **内核**：多配置构建矩阵，失败按配置归类。
- **硬件**：参考模型逐拍比对，首个差异点即定位。
- **本研究仓**：四路差分 + 弃权单列。

**是统一标准吗**：不是。

## 5. 差分的盲区在哪，谁来补？

**答：** 盲区在"上游文档 → 规范"这一段：所有实现都读同一份规范，规范抄错时四路一致地错。补齐只能靠形式模型与人工对照原文，且要留下偏差清单。

- **盲区一**：规范抄错（多路一致地错）。
- **盲区二**：规范漏写（各实现按自己理解填空，分歧出现才暴露）。
- **盲区三**：测试没覆盖（没跑到的语义，一致也无意义）。
- **补齐手段**：形式模型（可执行、可检查）+ 逐条对照上游原文 + 偏差登记。
- **为什么不能自动化**：判断"规范是否忠实于原文"需要读懂两份文本，目前只能人工 + 形式化辅助。

**各家做法**：

- **机器可读规范**：上游即模型，盲区最小。
- **形式模型 + 文字规范**：靠人工保证一致，盲区较小。
- **仅文字规范**：盲区最大，靠评审。
- **企业**：内部规范由架构团队统一维护。
- **本研究仓**：规范与上游逐条对照，偏差登记。

**是统一标准吗**：不是。

## 6. 独立性怎么机械检查？

**答：** 检查三件事：生成脚本的依赖、期望值的来源标记、模型与实现的代码是否共享。三件都能用静态检查或源码审查落地。

- **依赖检查**：生成脚本不得 import 被测实现的模块或读取其产物路径。
- **来源标记**：每个期望值带"规范条款 + 生成器版本"。
- **代码共享检查**：模型与实现不得共用同一份语义代码（否则一致性来自共享而非独立）。
- **结果记录**：结果里记录参与路与版本，事后可复核。
- **代价**：增加元数据与检查脚本；换来的是"一致"有意义。

**各家做法**：

- **合规生态**：参考模型与实现严格分离，签名由参考侧生成。
- **开源项目**：靠评审与约定，少有机械检查。
- **企业**：流程规定 + 代码审查。
- **一般项目**：无检查，独立性靠口头保证。
- **本研究仓**：生成脚本不引用实现产物，期望值带来源。

**是统一标准吗**：不是。

## 7. 实例：签名太粗，内存错误漏检

**现象**：所有用例通过，但程序读到的数据不对；排查发现错误发生在内存写入，而签名只覆盖了寄存器。

**根因**：判据覆盖的状态不完整——签名窄到只剩寄存器，写入错误无处体现。

**规矩**：签名必须覆盖"所有架构可见状态"，至少包含寄存器、被写内存区域、异常状态。

**机械防**：
- 签名定义作为固定章节评审，逐项列出覆盖的状态。
- 新增状态（如新增寄存器组）时，签名定义必须同步更新，否则门控报警。
- 保留失败细节（差异寄存器/内存列表），避免只有"不同"没有"哪里不同"。

## 8. 实例：只比退出码

**现象**：程序退出码都是 0，测试全绿；但输出内容错误、或部分计算被优化掉。

**根因**：判据粒度太粗，退出码只反映"有没有崩"，不反映"算得对不对"。

**规矩**：程序级测试必须比对输出或状态，不能只比退出码。

**机械防**：
- 程序级用例要求"期望输出"或"期望状态摘要"，缺一不得入库。
- 审查时抽查：把输出改坏，确认用例会红。
- 结果报告区分"执行成功"与"结果正确"两个维度。

## 背景知识

### 术语与概念

- **期望值**：用例应当得到的结果，须从规范派生。
- **重派生**：由输入与生成器重新产出内容并比对。
- **签名**：把最终状态压成可比较字符串。
- **差分**：多实现跑同一向量并比较。
- **弃权**：某路不支持该用例，结果未判定。
- **独立性检查**：确认判据派生路径不经过被测实现。
- **偏差清单**：规范与上游原文的差异登记。

### 对照

**判据粒度**

- **粗**：退出码、日志关键字。
- **中**：输出文本、寄存器快照。
- **细**：寄存器 + 内存区域 + 异常状态签名。
- **判据**：粒度必须覆盖"这一层可能出错的状态"。

**差分参与路数**

- **两路**：模型 + 模拟器，最常见。
- **三路以上**：研究项目或认证项目。
- **单路**：只有测试内断言，盲区最大。

**独立性保障**

- **强**：源码级依赖检查 + 来源标记 + 代码不共享。
- **中**：评审与约定。
- **弱**：口头保证。
