# 参考模型 -- 并发与内存模型

**本册要点**

- 内存模型描述的不是"某条指令算什么"，而是"**一组并发读写允许出现哪些结果**"。
- 两种表达：**公理式**（列出允许/禁止的约束）与**操作式**（给出可执行的抽象机）。
- 测试形态是 **litmus**：小程序 + 允许/禁止的结果集合，而不是"输入 → 输出"。
- `fence` 与 LR/SC 的语义要验的是"允许的结果集合"，不是"某次运行的结果"。
- 本项目**暂不做**可执行内存模型与 litmus；这不是缺陷，但要写清代价。
- 若要做，最小路径是：定结果集合 → 写少量 litmus → 接门控。

## 1. 为什么内存模型不能用指令级期望值表达？

**答：** 因为指令级判据是"给定状态 → 下一状态"的确定函数；而内存模型允许**多种合法结果**：同一段并发程序，在不同硬件上可以出现不同结果，只要都在允许集合内。

- **指令级**：单线程语义，结果是唯一的。
- **内存模型**：多线程语义，结果是"集合"；判据是"某结果是否被允许"。
- **为什么重要**：把"某个合法结果"当唯一期望值，会把正确实现判成错。
- **边界**：内存模型不管"指令怎么算"，只管"读写何时可见、以什么顺序可见"。
- **代价**：需要新的测试形态与判据形式，不能复用指令级向量。

**各家做法**：

- **x86-64**：TSO 模型，相对简单，工具成熟。
- **ARM64**：多副本原子模型，另有非多副本变体，语义复杂。
- **RISC-V**：弱内存模型，有形式描述并配合合规套件。
- **PowerPC**：弱内存模型，历史上以公理式描述为主。
- **MIPS / SPARC**：公开工具较少（**待核**）。

**是统一标准吗**：不是。表达方式（公理式 / 操作式）与抽象层次各家不同。

## 2. 公理式与操作式模型各是什么？

**答：** 公理式给"允许的结果必须满足哪些约束"，操作式给"一台抽象机按什么规则执行"；前者适合推理与工具检查，后者适合生成可执行模型与测试。

- **公理式**：定义事件、关系（读看到哪个写、顺序关系）、以及"合法执行"的约束集合。
- **操作式**：定义抽象机的状态与转移（缓冲、队列、刷新规则），跑出来即为一个合法执行。
- **取舍**：公理式紧凑、便于工具化；操作式直观、便于仿真。
- **实践**：两者常并存，互为交叉验证。
- **代价**：无论哪种，都需要形式化专家与工具链支持。

**各家做法**：

- **PowerPC**：公理式描述历史悠久。
- **ARM64**：操作式与公理式都有研究实现。
- **RISC-V**：有形式化描述与可执行模型。
- **x86-64**：TSO 的公理式描述较简洁。
- **MIPS / SPARC**：公开描述较少（待核）。

**是统一标准吗**：不是。

## 3. litmus 测试的形态是什么？

**答：** 一个小程序（两个线程、几条读写）+ 一组"允许/禁止的结果"；判定的是"这个结果是否被模型允许"，而不是"程序输出是否正确"。

- **结构**：线程体 + 初始值 + 观测点（最终寄存器/内存值）。
- **判据**：结果 ∈ 允许集合 ⇒ 通过；结果 ∈ 禁止集合 ⇒ 失败。
- **为什么要小**：结果空间可枚举，才能穷举"允许哪些"。
- **工具**：可执行模型跑 litmus，枚举结果并比对允许集合。
- **代价**：需要模型支持；没有模型时只能靠硬件实测，覆盖极低。

**各家做法**：

- **ARM64 / PowerPC / RISC-V / x86-64**：都有公开的 litmus 套件与工具。
- **硬件厂商**：用 litmus 验证实现是否符合内存模型。
- **形式方法研究**：litmus 是验证内存模型的主要手段。
- **一般项目**：几乎没有内存模型测试。
- **本研究仓**：暂无。

**是统一标准吗**：不是（形态相似，允许集合各架构不同）。

## 4. `fence` 与 LR/SC 的语义怎么验？

**答：** 验"允许的结果集合"：对每一组并发场景，检查实现是否产生了模型禁止的结果；`fence` 的作用是排除某些重排，LR/SC 的作用是保证读改写原子性。

- **`fence`**：定义读写之间的顺序约束（前序/后序集合）；验证方式是"没有 `fence` 时允许、有 `fence` 时禁止"的对照。
- **LR/SC**：验证"保留-条件存储"的原子性与失败语义（`sc` 失败时不得写入）。
- **粒度**：按字节宽度（1/2/4/8）分别验，宽度不同语义可能不同。
- **对齐**：跨缓存行的原子操作通常不保证原子性，需单独界定。
- **判据**：禁止结果出现 ⇒ 失败；允许结果出现 ⇒ 通过（不能要求"必须出现"）。

**各家做法**：

- **ARM64**：`ldaxr/stlxr` + 内存序后缀，配 litmus 验证。
- **RISC-V**：`lr/sc` + `fence` 的集合语义，有形式描述。
- **x86-64**：`lock` 前缀 + `mfence`，TSO 下语义较简单。
- **PowerPC**：`lwarx/stwcx` + 同步指令。
- **MIPS / SPARC**：`ll/sc` 类机制，公开验证材料较少（待核）。

**是统一标准吗**：不是。

## 5. 为什么本项目暂不做，代价是什么？

**答：** 因为内存模型需要形式化描述 + 工具 + 长期维护，而当前没有并发程序的真实消费方；不做的代价是"`fence` 与 LR/SC 的语义只有文字规范，没有机械判据"。

- **不做的收益**：省下形式化与工具链投入，集中在单线程语义与工具链。
- **不做的代价一**：并发场景只能靠人工评审与少量实测，覆盖极低。
- **不做的代价二**：`fence` 的"够不够强"无法判定，只能照抄惯例。
- **不做的代价三**：将来接操作系统（多核）时，内存模型问题会在最贵的阶段暴露。
- **缓解**：先用"少量手工 litmus + 硬件实测"兜底，并明确记录"未验证"。

**各家做法**：

- **主流架构**：都有公开发布的内存模型与工具。
- **新兴架构**：常先给文字描述，工具随后补齐。
- **教学项目**：多省略内存模型，只在文字里提一句。
- **本研究仓**：明确列为空白，写入待办。

**是统一标准吗**：不是。

## 6. 若要做，最小路径是什么？

**答：** 三步：先定"允许的结果集合"（哪怕只覆盖核心场景），再写十几个 litmus，最后接门控并单列统计；不要一上来追求全量形式化。

- **第一步：定集合**：选核心场景（消息传递、读写重排、原子加），明确允许/禁止。
- **第二步：写 litmus**：每场景几条，覆盖有/无 `fence` 的对照。
- **第三步：接门控**：跑在功能级模型上；结果分"允许/禁止/未判定"。
- **第四步（可选）**：引入公理式描述与工具，做穷举验证。
- **判据**：出现禁止结果即失败；未判定单列。

**各家做法**：

- **教学项目**：从十几个 litmus 起步，够讲清概念。
- **产品项目**：先覆盖核心同步原语，再扩展。
- **研究项目**：全量形式化 + 穷举。
- **认证项目**：与合规套件绑定。

**是统一标准吗**：不是。

## 背景知识

### 术语与概念

- **内存模型**：规定并发读写可见性与顺序的规则集合。
- **允许的结果集合**：模型允许出现的观测结果。
- **litmus 测试**：小程序 + 允许/禁止结果的组合。
- **公理式模型**：以约束集合描述合法执行。
- **操作式模型**：以抽象机状态转移描述合法执行。
- **LR/SC**：加载保留 / 条件存储，构成原子读改写对。
- **`fence`**：约束前后读写顺序的指令。
- **未判定**：模型或工具不支持某场景。

### 对照

**表达方式**

- **公理式**：约束集合，适合工具检查。
- **操作式**：抽象机，适合仿真与教学。
- **并存**：多数架构两种都有研究实现。

**测试形态**

- **litmus**：小程序 + 允许集合，主流。
- **压力测试**：大并发程序，覆盖低、难判定。
- **无测试**：只靠文字规范，最常见。

**验证深度**

- **穷举**：小场景全枚举，成本高。
- **抽样**：随机执行，覆盖有限。
- **仅实测**：硬件跑一遍，几乎不可判定。
