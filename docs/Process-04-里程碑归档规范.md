# 里程碑归档规范

> **状态**：生效（2026-11-01 修订）｜**上位依据**：无——属**工程过程规范**（可逆、单模块、无外部契约，不命中 ADR 判据，见 `docs/Process-03`）。
> **机器门控**：`tools/infra/check_archive.py`（`make check-archive`，**L1**）——结构 / 册字段 / README 三节对应 / issues 快照逐项机械判定，`--self-test` 提供可达 FAIL；判定口径以脚本为准，本规范给规则与理由。
> **首个实例**：M1 归档，见 `.tao/archive/M1/`；**模板实例**：M9/M10（五节齐全，`INFRA-117t` 归一后）。
> **关键词**：本规范用「**必须**（MUST）／**应当**（SHOULD）／**可以**（MAY）」表达规范性等级。

## 1. 里程碑生命周期（开启 → 执行 → 收敛 → 归档）

> **约定（用户 2026-10-06 裁定，2026-11-01 修订）**：里程碑采用 **「INTEG 开启 / INTEG 结束」闭环**——**M5 起**由 **INTEG 模块**开闭（开启 = INTEG 的规划 `k`，结束 = INTEG 的 `m`）；**M1–M4 由 SPEC 模块 `SPEC-*k` 开启**（历史做法，保留不改）。

里程碑从开启到归档分**四阶段**：

1. **开启**（INTEG 开启）：由 **INTEG 模块的规划 `k` 任务**承担——产出**里程碑定义**（`.tao/knowledge/milestones.md`）+ **前置 ADR**（涉决策时）+ **任务分解** + **串行链**。
2. **执行**：各模块**任务串行链**——**同改共享文件（`contracts/`/`Makefile`/`spec/`/`tests/` 等）一律串行**；模块 `m`（如设）**就近核验**（模块任务收敛时即核验本模块 `m`）。
3. **收敛**（INTEG 结束）：由 **INTEG 模块的 `m` 任务**承担（**集成门槛**）——其依赖的各模块 `m`（如设）均置 `里程碑` ⇒ 主会话置**项目里程碑**为 **`达成`**。
4. **归档**：按本规范 **§3 台账梳理 → §4 归档判据 → 归档**（提交须经用户确认）。

- **模块 `m` 是按需产物（用户 2026-11-01 裁定）**：**不强制**每个模块都有 `m`——仅当该模块需要**单独里程碑验收**时设立；项目收敛可由 **INTEG 收尾任务**（`k`/`m` 均可）承担。
- **数量不纠结（历史事实，合规、不补不删）**：M7 多 `m`、M3 缺 qemu `m`、M8–M10 缺模块 `m` 均**符合本规范**；`check_archive.py` 只校验「有册则字段合规」，不校验数量。
- **历史说明**：**M1–M4 由 SPEC 模块 `SPEC-*k` 开启**（历史做法，保留不改）；**M5 起**采用上述 **INTEG 闭环**（开启 = INTEG 的 `k`，结束 = INTEG 的 `m`）。

## 2. 目的与触发

- **目的**：项目里程碑达成后，把该里程碑的**任务书**与**任务流水/台账历史**归档，防止 `.tao/tasks/` 与活台账无限膨胀、防止历史内容被误读为现行事实。
- **触发时机**：项目里程碑置「达成」后（即该里程碑各模块 `m`〔如设〕全部置 `里程碑`）。
- **性质**：归档**不删除、不改变历史内容**——任务书用 `git mv` 保留 rename；**任务流水冻结到归档 README §2**，并从活台账删除（**冻结**，不是「复制后仍保留」）。
- **活台账只留**：当前/维护任务行，**不写归档指针**（历史由 `.tao/archive/<M<i>>/` 自身承载）。

## 3. 归档前：遗留台账梳理（**MUST**）

> **时机**：里程碑达门槛后、**正式归档前**（即归档任务〔如 `INTEG-010t`〕**之前**）。
> **目的**：遗留台账（`issues.yaml` / `lessons.md`）随任务累积会混入「已消解仍 `open`」「`scope` 陈旧」「教训/过程记录混入 issue」「上一里程碑已 `moot`」等内容；归档会把「里程碑阶段 closed（≤ 达成日）」冻结，故**必须**先梳理，保证活台账与现行事实一致、归档快照干净。

**步骤（逐条，须可追溯）**：

1. **关闭已消解项**：本轮（或前序任务）已消解的 `open` issue → `closed` + `resolved_by`（指向消解任务/日期）。
2. **校正 `scope`**：按**当前**里程碑定义校正（里程碑重定义后，原 `M<n>` 陈旧项 → 校正到实际里程碑；`post-M1` 等模糊值明确化）。
3. **移出「教训/过程记录」类**：凡属记录/教训而非「待办 issue」的条目 → **移入 `.tao/knowledge/lessons.md`**（`issues.yaml` 中删除或留极简指针；**id 不复用**，如实说明）。
4. **判定 `moot`/过期项**：已被后续任务覆盖、或里程碑已达成而失效的 → `closed`（附理由）或保留（附依据）；**不得凭印象**。
   - **里程碑边界项**（「本里程碑**部分交付**、剩余归下一里程碑」的 issue；用户裁定 2026-10-05）：须**拆分处置**——**交付部分单独 `closed`**（新增独立 `closed` 条目，`resolved_by` 指向交付任务；**原 id 保留给未交付的 `open` 条目**，不复用），**未交付部分留 `open`** 并将 `scope` 校正到下一里程碑；**不得**整条一并 `closed`，也不得一律保留。
5. **头部同步**：更新字段约束（`status` / `resolved_by`）；`gate` 判据**已退役**——M1 阶段阻断判据随 M1 达成（2026-09-22）退役，现无在役 `gate` 项（`INFRA-113t`）。`issues.yaml` 无「文件头里程碑状态」字段，同步只涉及该文件顶部注释与字段约束。
6. **交付**：**逐条判定表**（id → 动作 + 依据）+ `check_issues.py` **EXIT 0**。

> **承担**：可由一个专门清理任务承担（首个实例：`INFRA-033t`，2026-10-04）。本步骤属归档**前置**——未完成不得进入 §4 归档判据的执行。

## 4. 归档判据（四类，均须**机械可判**）

1. **任务书**：`**项目里程碑**` 字段**恰好等于**该里程碑编号，且状态为**终态**（`已验证` / `里程碑`）。
   - **状态必须精确**：只允许 `已验证` 或 `里程碑`；**不得**带括注——原括注（如「第 3 轮返工后」）移至紧跟其后的 `> **状态注记**：…` 或审阅记录。通常 `t`/`k` 册为 `已验证`、`m` 册为 `里程碑`；历史归档中 `INTEG-037m` 记为 `已验证`，按字段原值保留，门控**不做后缀映射**。
   - **缺失状态补状态（用户 2026-11-01 裁定）**：仅当有**完成区 / 审阅记录证据**时才补，不凭印象。
   - **里程碑字段判定口径**：编号必须等于所在归档号；**历史归档**中已存在的尾随括注（如 `M9（FP 完备性）`）属历史注记，门控按编号判定、**不改不删**；**新归档**必须写裸 `M<i>`。
   - 过渡期（`M<i>→M<i+1>`）与下一里程碑（`M<i+1>`）的任务**不归档**。
   - **归档任务自归档**（用户裁定 2026-10-05）：**归档任务自身归入其所归档的里程碑**——最后一步 `git mv` 自身入该里程碑 archive；历史遗漏回溯补入。
2. **任务流水**：日期 ≤ 该里程碑**达成日**的「已验证」表行（活台账列 `| 编号 | 完成时间 | 一句改动 |`；原名 `changelog.md` 条目）**冻结到归档 README §2**（归档流水表列仍固定 `| 编号 | 状态 | 完成时间 | 一句改动 |`，搬入时补状态 `已验证` 并规范化），并从 `milestones.md` 删除（§7），不得保留 `（登记）`。**「待开始（未开工）」与「进行中（已提交待验收 / 待返工）」表的行不归档**——前者无完成时间、不属历史；后者尚未落地，随里程碑迁移后在新里程碑重判。
3. **`MEMORY.md` 行**：内容「纯该里程碑」的行（如「M<i> 实现」「M<i> 任务规划」及纯里程碑期的模块状态行）；**混合**了后续里程碑内容的行（如「M1 完成 + M2 过渡」）**不整行归档**，只归档其中纯里程碑部分（必要时人工拆分，不机械切行）。摘要进 README §4。
4. **`issues.yaml` 的 `closed` 项**：`resolved_by` 对应任务**提交日 ≤ 该里程碑达成日**的 `closed` issue（即**里程碑阶段**关闭项）。提取为 archive 的**台账快照**（§5/§7）；**达成日之后**（含过渡期 `M<i>→M<i+1>`、由后续任务关闭）的项**不归档**，留在活台账。
   - **判据来源**：`resolved_by` 内嵌任务 ID（如 `QEMU-004t`）；其提交日以 `git log --grep <taskID>` 或该 ID 的侧记日期确定，**不得**凭印象；边界（达成日当天）以「≤ 达成日」为准。
   - **灰区不计**：达成日之后、但属「上一里程碑范围收窄」的关闭项（如 M1 的 `fence` 移出、`rela.si` 删除，均 2026-09-23~30）**不计**里程碑阶段（用户裁定：灰区不算）。

## 8. 验收与纪律

- **门控**：`make check-archive` 已挂 **L1**（`make check` 默认包含）；`--self-test` 必须 rc=0（基线 PASS + 13 类注入 FAIL，各自可达）。
- **最终态（`INFRA-117t` 归一后）**：`python3 tools/infra/check_archive.py` **严格默认**、无过渡 flag；**须 rc=0**（M1–M10 全部归档结构/册字段/五节/流水/issue 快照齐备）。M2 两册状态括注已移入 `> **状态注记**`；原 `notes/` 5 份已并入 `m7-retrospective.md` 附录 A–E；M9/M10 README 五节齐全、流水已冻结。
- `make check` **EXIT 0**。
- `git mv` 后 `git status` 显示 `R`（rename）。
- **不误伤并行未提交工作**：只 `git add` 归档相关文件；并行任务书/补丁一律不动（本例曾遇 QEMU FP 并行工作，归档提交只含归档文件）。
- **不与并行任务同树并发**：归档/收尾**应当**避开同一工作树上正在执行的其它任务——并行任务在跑时**暂缓**归档，等其完成/提交后再动。否则**共用文件**的改动（如 `tools/spec/check_scope.py`、`.tao/knowledge/MEMORY.md`）会被**对方的提交**卷走（本例 M1 归档与 `INFRA-032t` 并发，2 处路径修复被卷入 `6e0741b`）。
- 生成的 `README.md` 与改动后的 `milestones.md`/`MEMORY.md`：**无表内空行、无连续空行**——markdown 表格的 `|---|` 后**必须**紧跟数据行；blockquote（`>`）**不得**插在 `|---|` 与数据行之间；文件尾**不得**残留空行。
- 提交**必须**经用户确认（`AGENTS.md`）。

## 9. 教训（M1 归档实录）

1. **表断行**：把归档指针（blockquote）插在 `| --- |` 与数据行之间会**断开表格**；指针须放表头之上（changelog）或做成表内合法行（MEMORY）。
2. **多行 cell**：changelog 存在跨物理行的 cell（行首 `| 2026-` 识别为行首，其余归上一行）；解析/搬运须按「行首正则」分组，勿按物理行切割。
3. **行首/行尾空行**：搬运后须清理每个条目首尾的空行，否则会在表内留下孤立空行。
4. **`\n` 拼接**：用 `"\n".join(段落)` 组装文档时，段落尾的 `\n` 会与 join 的 `\n` 叠加成连续空行；逐行组装（list of lines）更稳。
5. **指针放顶部**：changelog 为 append-only，指针放底部会被后续 `/complete` 追加的条目埋没。
6. **并行同树 → 混提**：归档/收尾若与另一任务在**同一工作树**并发，**共用文件**的改动会被**对方的提交**卷走（本例 `INFRA-032t` 期间 2 处路径修复进了 `6e0741b` / SPEC-089t 的提交）。纪律：并行任务在跑时**暂缓**归档，或等其完成/提交后再动；收尾提交**只 `git add` 本任务文件**（见 §8）。
