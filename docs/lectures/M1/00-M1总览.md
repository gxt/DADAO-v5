# M1 总览：为什么是这些模块、为什么是这个顺序

> 本课是 M1 的第一篇。它不教具体技术，只回答两个问题：**M1 要做哪些模块？为什么按这个顺序做？**

## 学习目标

学完本课，你应能：

1. 说清 M1 的**端到端目标**；
2. 讲出 M1 每个**模块的职责**，以及「为什么非它不可」；
3. 画出 M1 的**模块依赖与执行顺序**，并解释每一步为何在前、为何在后；
4. 说出贯穿整个项目的两条主线：**方法论**与 **Agent 协作**。

## M1 要造什么

先说清楚：我们造的不是「一个程序」，而是一条**最小但完整**的工具链——把「人写的汇编」变成「机器码」，让机器码「跑起来」，再用**独立**的测试确认它跑对了。这三件事分别对应**汇编器**、**模拟器**和**验证**。它们围绕的同一个核心概念，是**指令系统架构（ISA）**：

> **〔术语〕指令系统架构（ISA, Instruction Set Architecture）**
> 硬件与软件之间的**契约**：规定指令、寄存器、内存模型、异常等**可见行为**，而不规定如何实现。
> 来源：Patterson & Hennessy《计算机组成与设计》第 1 章；《The RISC-V Instruction Set Manual, Volume I》第 1 章。

> **〔术语〕汇编器 / 反汇编器（assembler / disassembler）**
> 汇编器把汇编文本翻译成机器码；反汇编器反向翻译。
> 来源：LLVM 官方文档（`llvm-mc`、`llvm-objdump`）。

> **〔术语〕模拟器（emulator）**
> 用软件实现 ISA 的可见行为，用于在尚无硬件时运行程序。
> 来源：QEMU 官方文档（System Emulation）。

M1 的**端到端目标**（摘自项目里程碑说明）：

> `llvm-mc` 能汇编/反汇编全部 M1 指令；`qemu-system-dadao` 能在 MMU-off 裸机模式执行标量程序；独立测试向量经「MC 汇编 → QEMU 执行 → 结果比对」一致，形成 MC↔QEMU 集成闭环。

## 为什么是这些模块

要完成上面的闭环，缺一不可的是这几个模块：

| 模块 | 职责 | 为什么非它不可 |
| --- | --- | --- |
| `spec` | 规范归一化：ISA 合约、编码表、ABI/ELF 合约、ADR | 行为的**唯一真相**；没有它，实现各按理解、无法验证 |
| `infra` | 构建基础设施：组件锁、fetch/apply、Makefile、容器 | 保证**可复现**：同样的 commit + 同样的步骤 → 同样的结果 |
| `testcases` | 独立测试向量 | 提供**独立 oracle**：向量只从规范派生，不从实现生成 |
| `llvm` | LLVM MC（汇编 / 反汇编 / 编码） | 让「人写的汇编」变成「机器码」 |
| `qemu` | QEMU CPU target + 裸机机器 | 让机器码**跑起来**并产生可观测结果 |
| `integ` | 端到端集成 + 跨模块接口对齐 | 单模块各自过 ≠ 组合正确；需要把组合**验证**起来 |

这里已经用到两个关键概念，值得单独说清：

> **〔术语〕独立 oracle（independent oracle）**
> 判断实现是否正确，必须有一个**独立于被测实现**的期望来源；否则「自己测自己」无法发现系统性错误。
> 来源：Myers《The Art of Software Testing》「测试预言（test oracle）」；Kent Beck《Test-Driven Development》「先写期望」。

> **〔术语〕Spec-first / 组件锁**
> **Spec-first**：所有行为期望来自规范，不从实现反推。**组件锁**：外部组件按精确 commit 锁定，保证可复现。
> 来源：本项目 `AGENTS.md`（核心原则）。

> 顺带说明：`golden`（黄金模型）属后续阶段；`gem5` / `sail` 是 M2+ 的第二、第三参考实现，用于多路差分。

## 为什么是这个顺序

M1 模块依赖关系（摘自 `milestones.md`）：

```
infra ───────────────┐
                     ├──→ llvm ───┐
spec ──→ testcases ──┤           ├──→ integ ──→ M1
                     └──→ qemu ───┘
```

- **`infra` + `spec` 最先**：一个是「**能建起来**」（构建基础设施），一个是「**建什么**」（规范基线）——两者是所有下游的前置。
- **`testcases` 紧随 spec**：向量是下游 MC/QEMU 的验证依据，越早建立越好。
- **`llvm` ∥ `qemu` 并行**：汇编器与模拟器**互不依赖**（都只依赖 `infra`+`spec`），可两条线并行推进。
- **`integ` 最后收口**：把 `llvm` + `qemu` + `testcases` 组合成端到端闭环，M1 才算达成。

## 两条贯穿线

- **方法论**：Spec-first（期望来自规范）、独立 oracle（验证与被测分离）、组件锁（可复现）、决策留痕。其中「决策留痕」在本项目里的载体是 **ADR**：

> **〔术语〕ADR（Architecture Decision Record，架构决策记录）**
> 记录难以逆转的架构决策：背景 / 决策 / 理由 / 影响。
> 来源：Michael Nygard, *Documenting Architecture Decisions*；本项目 `adr-authoring.md`。

- **Agent 协作**：本项目的实现由 AI Agent 按「**约束系统**」完成——人写约束（任务书 / 合约 / ADR），Agent 写代码（详见后续专篇）。

## 坑案例

**案例一：为什么向量不能由被测实现生成？**

- **现象**：若用模拟器（或编译器）的输出当作「期望值」，当模拟器自身有 bug 时，测试照样通过。
- **根因**：期望来源与被测实现同源，错误被「一起复制」，测试失去发现力。
- **修复**：测试向量必须**独立派生自规范**（本项目从 `spec/` 与 ISA 合约派生）。
- **教训**：**验证的独立性是命根子**——oracle 与被测对象必须来自不同来源。

**案例二：为什么先冻结规范、再开始实现？**

- **现象**：若边实现边改规范，实现与规范「互相将就」，最后无法判断谁对。
- **根因**：缺少稳定基线。
- **修复**：先让所有规范产物（合约 / 编码表 / ADR）评审通过并**冻结**，再开始实现。
- **教训**：**先定基线，再动实现**。

## 小结与延伸阅读

- M1 = 一条「规范 → 工具链 → 模拟器 → 集成」的**最小闭环**。
- 每个模块都为这条闭环补上**不可替代**的一环；顺序由**依赖**决定，而非喜好。
- 两条贯穿线：**方法论**（Spec-first / 独立 oracle / 组件锁 / ADR）与 **Agent 协作**。
