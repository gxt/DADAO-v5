## Context（背景）

### 用户裁定（原话，**逐字引录**；渠道 = 经主会话问答，2026-10-18）

> 「**1、聚合/union 参考主流ISA实现；2、RF寄存器，这个的顺序和大端/小端没关系吧？！所以，有冲突吗？3、binary128似乎也和大端没关系吧？？？其它大端机器是怎么做的？4、**」

> 「**对于binary128，大端内存如果连续load到寄存器中，如果想要用ldm/stm，还确实是需要高半在偶号，低半在奇号**」

> 「**1、三套游标；2、我的想法是低32位，请参见rf0中的定义，而且，32位整数是怎么做的？难道也是用高32位？**」

**裁定范围（如实界定）**：三条已裁定 **①** 聚合/union **按主流 ISA 分类**（不是「一律内存」）、**②** `va_list` = **三套游标**、**③** 16 B 值（binary128）**高半在偶号寄存器**、**④** `float` 取**低 32 位**（并追问 32 位整数同理）。**未裁定**：`va_list` 的具体字段与顺序、寄存器保存区归属、聚合分类的**尺寸门槛适用范围**（是否覆盖命名参数）、栈上 16 B 对齐细则 —— 这些是本 ADR 的**提案**（`D1`–`D9`），待逐条确认。

### 现状与缺口（逐条带现场依据）

1. **`spec §3.3` 现状 = caller 写整块保存区、`va_list` 即 `void*`**：`spec/DADAO-21-ABI-应用程序二进制接口.md:248-338` —— 明文「`va_list` 即为 `void*` 指针」「调用者…将所有参数…写入栈上的连续保存区」，`va_start` = `(char*)sp + N*8`，`va_arg` 统一 `+8` 步进。**根因**：`§3.2.1`（`:150-157`）三 bank 独立计数 ⇒ 旧文断言「callee 无法仅从寄存器重建声明顺序」。
2. **三游标设计消掉上述根因**：三 bank 各自的**下一个槽 + 剩余槽数** + 一个**栈游标**即可按声明顺序走 —— 参数按类别只消耗所属 bank 的槽；某 bank 的剩余槽数归零（`left = 0`）时该参数取栈，栈槽只被「溢出参数」按声明序消耗 ⇒ **单个栈游标足够**（`D4` 给出正确性论证）。
3. **聚合分类现状 = 8 槽位 / 64 B 上限**：`spec §3.2.3`（`:176-229`）HFA/HPA「叶子字段总数 ≤ 8」、通用聚合 `≤ 64 字节 ⇒ RD`（`> 64 B ⇒ 间接指针`）；`contract-abi §6.4` 同口径（用户 2026-10-09 裁定「B」）。**本次「≤ 16 B 进寄存器 / > 16 B 走内存」与之冲突**（见 `D3` 的 ⚠ 范围项）。
4. **变参 + 寄存器耗尽在契约层无条款**：`contract-abi §4` 标题限「非变参」、`§4.3` 溢出区限非变参、`§5` 把变参 `Excluded` 顺延 M4、`§6` 逐项无该条 ⇒ `LLVM-102t` 的 B 项已按停点标 `BLOCKED`；实现侧现场 = `DADAOISelLowering.cpp:740-742` 主动 `report_fatal_error`。
5. **`float` 只占低 32 位是 ISA 事实**：`spec/SimRISC-00:89`「rf 寄存器字长 64 位，当存放单精 32 位数据时，只使用低 32 位，高 32 位不做特殊规定」；`spec/SimRISC-01:198`「`ld.t`/`ldm.t` 的 `[63:32]` 不变」；`spec/SimRISC-03:161`「加载单精浮点 … 只需设置低 32 位」；`rf0` = 浮点控制/状态寄存器（`DADAO-21:54`、`contract-abi §1.4`），**不是零寄存器**。
6. **32 位整数同样在寄存器低位 + 扩展**：`spec/SimRISC-01:75`「装入指令 … 进行零扩展或符号扩展」；`contract-abi §4.2`（caller 按类型符号性扩展为 canonical 64 位）。
7. **16 B 值的半字顺序由 `ldm.o`/`stm.o` 的递增语义钉死**：`spec/SimRISC-01:24-27`（`ldm.o_rrri_rf`）、`:43-47`（`stm.o_rrri_rf`）；`:123` 例「`stm.b {rd16:rd23}` 将 rd16–rd23 分别存放到以 rb2 为基址的 8 字节连续地址中」⇒ **寄存器号递增 = 地址递增**。大端下 128 位值的**高半在最低地址** ⇒ `rf16`（低号/偶号）= 高半、`rf17` = 低半 ⇒ `ldm.o {rf16:rf17}, [rbH, rdC]` / `stm.o` **一条指令直通**，无需 swap。
8. **16 B 值无现成 ABI 条款**：`contract-abi §6.3` 明文 **`i128` 传参/返回不支持**（用户 2026-10-08 裁定）；`ADR-0030 D2` 已确认 binary128 走 RF 双槽，但半字顺序写作「低位在偶号」（本次由 `D6` 修订）。
9. **`va_list` 必须可按值传递/复制**（`vfprintf` 等）：主流实现用「数组长度 1 的结构体」（`typedef struct {…} va_list[1]`）使形参退化为指针；本 ADR 沿用此形态。

### 命中 ADR 判据（`docs/Process-03`）

**高代价**（改 clang `EmitVAArg` / 后端调用约定 / musl `va_list` 头 / 既有保存区路径）、**跨模块 / 需一致**（spec / llvm / infra / testcases）、**多方案且需记录取舍**（caller 块 vs callee 保存、单游标 vs 三游标、64 B vs 16 B 门槛）、**外部契约**（C 标准提升、psABI 对照）⇒ 立本 ADR。

## Decision（决策）

> 每条含 **决定 / 理由 / 被否**，并标依据来源（「用户已确认」/「主会话证据」/「架构师提案」）。**提案未经逐条确认前不得视为 `Accepted`**。

### D1 — `va_list` = 三 bank 游标 + 每 bank 剩余计数 + 栈游标（字段与顺序固定）【用户已确认：三套游标】

- **决定**：
  ```c
  typedef struct {
      uint64_t *rd_next;    /* 下一个可用 RD 参数槽（指向保存区） */
      uint64_t *rb_next;    /* 同上，RB */
      uint64_t *rf_next;    /* 同上，RF */
      int64_t   rd_left;    /* 本 bank 剩余可用槽数；0 = 已耗尽 */
      int64_t   rb_left;
      int64_t   rf_left;
      uint64_t *stack_next; /* 下一个栈溢出槽（= incoming_sp 起） */
  } __va_list_tag;
  typedef __va_list_tag va_list[1];
  ```
  - **字段顺序即 ABI 可观测事实**（3 `next` → 3 `left` → `stack`；全 8 B，共 **56 B**，无填充），调用方与被调方、以及 `musl` 头文件三处必须逐字一致。
  - 三游标各自**只在本 bank 内推进**（+8 B/槽），`left` 同步递减；`stack_next` **只被溢出参数推进**。
  - `left = 0` 的 bank 视为耗尽（`next` 不参与，实现可置 `NULL`）。
  - `va_copy` = 结构体逐字段复制；`va_end` = 空操作（无动态资源）。
- **为何必须有 `left`（不是 4 个裸指针）**：`va_list` 会按值/按指针传给**另一个编译单元**（`printf` → `vfprintf`，musl `src/stdio/vfprintf.c` 内继续 `va_arg`）。被调方看不到原变参函数的 `start_bank`/保存区基址，**无法从 `next` 推出该 bank 的末槽**；若只给裸指针，`va_arg` 会越过本 bank 保存区、读进相邻 bank 的保存区（静默错值）。把「剩余槽数」随游标携带，是跨函数 `va_arg` 正确性的**必要条件**。
- **理由**：三 bank 独立计数（`spec §3.2.1`）⇒ 单游标无法表达「按声明序、按类别分流」；`left` 让「HFA 整组是否放得下」「16 B 是否够两槽」变成一次整数比较，无需指针与 bank 末址比较。与主流「保存区 + 偏移/剩余量」同构（AArch64 `__gr_top` + 负偏移 `__gr_offs`；RISC-V `__va_arg_ptr` + 偏移）。
- **被否**：① **`typedef void* va_list`（现状 §3.3）** —— 无法承载三 bank 分流（`D2` 的根因）；② **仅 3 游标 + 1 栈指针（4 裸指针）** —— 跨函数 `va_arg` 无法判末槽（上述必要条件），会静默越界；③ **AArch64 式 top+offset（每 bank 2 字段）** —— 语义等价但 7 字段，且 16 B 聚合需把偏移差换算回槽数，计数更直接；④ **`union` 复用同一指针** —— 三 bank 同时活跃时会互相覆盖。

### D2 — 寄存器保存区归 **callee**（取代 caller 写整块保存区）【主会话证据：取代现状；实施细则 = 架构师提案】

- **决定**：
  - **变参 callee** 在自己栈帧内分配**寄存器保存区**：每个 bank 连续 `(32 - start_bank)` 个 8 B 槽（`start_bank` = 该 bank 命名参数占用后的下一个槽），用 `stm.o {rXstart:rX31}, [基址, rdC]` **一条指令/bank** 落盘。
  - `va_start(ap, last)` 初始化 **3 游标 + 3 剩余计数 + 栈指针**：三游标分别指向本 bank 保存区的首个可变参数槽，`left_bank = 32 - start_bank`；`stack_next = incoming_sp`（`rbfp + 8`）。
  - **caller 不再写任何保存区**：只按 `§3.2` 的既有规则放寄存器/栈；溢出参数仍在 `incoming_sp` 起的连续栈区。
  - 保存区只保存**从 `start_bank` 到 31**（命名参数已消费的槽不必保存）；某 bank 命名参数已用尽（`start_bank = 32`）⇒ 该 bank 不分配保存区、游标直接置「已耗尽」。
- **理由**：caller 不知道 callee 会从哪些 bank 取、取多少；现状「无论是否使用寄存器都把全部参数写一遍」是**每调用点**的固定成本，且把同一值写两遍（寄存器 + 栈）。callee 保存是主流做法（AArch64 变参 prologue 保存 `x0–x7`/`v0–v7`），且只在**变参函数**付费。`stm.o` 已有 `rd`/`rb`/`rf` 三种形式（`spec/SimRISC-01`）⇒ 无跨 bank 搬运。
- **被否**：① **caller 写整块保存区（现状 §3.3）** —— 成本前置到所有调用点、与「寄存器传参」重复、且无法表达「某 bank 已耗尽」；② **`va_list` 直接指向入参寄存器** —— 寄存器会被后续调用/使用破坏，`va_arg` 可在任意点执行；③ **caller 提供保存区指针** —— 新增隐藏参数、改调用约定，收益为零；④ **只保存实际用到的 bank**（按 `va_arg` 类型收缩）—— `va_list` 可传给 `vfprintf`，编译期不可知，会静默取到未保存槽。
- **代价（如实）**：每个变参函数最多 `3×16×8 = 384 B` 帧 + 最多 48 条 store（实际按 `start_bank` 递减）；非变参函数零成本。后续可用 shrink-wrapping 优化，但**语义以上述保守保存为准**。

### D3 — 聚合/union 分类：**≤16 B 按类别进寄存器、>16 B 走内存**（命名与变参同一套）【用户已确认：按主流 ISA；⚠ 尺寸门槛的适用范围待确认】

- **决定**（`T` = 聚合/union，`size` = `sizeof(T)`，`align` = `alignof(T)`）：

  | 类别 | 判据 | ≤16 B 的传递 | >16 B |
  | --- | --- | --- | --- |
  | **HFA** | 递归展开后叶子全为**同一**浮点类型（`float`/`double`），且 `size ≤ 16` | **RF**，1 叶子 = 1 槽（最多 4×`float` / 2×`double`） | **内存** |
  | **HPA** | 递归展开后叶子全为指针，且 `size ≤ 16` | **RB**，1 叶子 = 1 槽（最多 2 指针） | **内存** |
  | **其它（整数类）** | 非 HFA/HPA（含 **union**、混合成员、含填充） | **RD**，按 8 B 块：`size ≤ 8` = 1 槽；`9–16` = 2 槽（高半在低号槽，`D6`） | **内存** |

  - **union 一律不展开**（`spec §3.2.3:182` 既有规则）⇒ 永不为 HFA/HPA，按**整块字节视图**归整数类（≤16 B → RD；>16 B → 内存）。与主流「union 按 composite 的整数类处理」一致。
  - **混合成员结构**（如 `{float f; int i;}`、`{double x; char c;}`）归整数类 → **RD**（**不是**内存）——「不是 HFA/HPA」只排除浮点/指针专用通道，不排除寄存器。
  - 对齐：`align > 8` 的聚合在 RD/RB 中**从偶号槽起**（跳过奇号槽）；RF 的 16 B 值同样偶号起（`D6`）。整组槽位不足 ⇒ **整体走栈、不拆半**。
  - **变参沿用同一分类**（用户口径）；`va_arg` 按 `D4` 步进。
- **⚠ 适用范围（须用户确认）**：本表若**同时覆盖命名参数**，则**取代** `spec §3.2.3` / `contract-abi §6.4` 的「8 槽位 / 64 B」上限（用户 2026-10-09 裁定「B」）。若用户只希望改**变参**，则命名参数维持 64 B、本表退化为「变参专用」，且「变参沿用命名参数分类」一句不成立。**本提案取「命名与变参统一 ≤16 B」**（主流 RISC-V/AArch64/x86-64 的共同门槛）。
- **理由**：16 B = 2×XLEN，是主流 64 位 psABI 的聚合寄存器上限（x86-64 SysV 两个 eightbyte；AArch64 16 B；RISC-V 2×XLEN）；把上限从 64 B 收到 16 B 可显著降低 `va_arg`/调用点的槽位推算复杂度，并让「整组不足 ⇒ 整体走栈」成为唯一溢出路径（不出现「半在寄存器半在栈」）。HFA 取 16 B 是 **RISC-V 式**（2×FLEN），**不取** AArch64 的「HFA 最多 4 成员/32 B」例外 —— 换取跨类别同一门槛。
- **被否**：① **聚合/union 一律走内存**（用户已否；且与既有 HFA/HPA 条款冲突）；② **保持 8 槽位 / 64 B**（`va_arg` 需处理 1–8 槽任意组合 + 半溢出，复杂度与错误面最大）；③ **union 单独定一套**（无主流先例、增加分支）；④ **混合成员走内存**（比主流保守，且会把 `{float,int}` 这类高频小结构推上栈）。

### D4 — 变参中聚合的 `va_arg` 步进规则【架构师提案（由 D1/D3 推导）】

- **决定**：
  1. `va_arg(ap, T)` 先按 `D3` 分类，得到「bank + 槽数」或「栈占用」。
  2. **该 bank 的 `left` ≥ 所需槽数**（HFA/HPA 需整组叶子数；整数类需 1–2 槽且偶号对齐可满足）⇒ 从该 bank 游标取，游标 += 槽数、`left` -= 槽数。
  3. **该 bank 不足**（`left = 0`，或 `left <` 整组槽数）⇒ **整值从 `stack_next` 取**，`stack_next` += 栈占用（`round_up(size, 8)`，`align ≥ 16` 时按 16 对齐并可能跳过一个 8 B 槽）；**该 bank 游标与 `left` 都不推进**（避免后续参数错位）。
  4. **HFA/HPA 按叶子逐个还原**（RF 每叶子 1 槽；RB 每叶子 1 槽），不按整块字节拼接。
  5. **`>16 B` 聚合**：只可能来自栈（`D3`），按 `size` 复制（语义 = 按值），对齐 `max(8, align)`。
  6. **正确性依据（为何单栈游标够用）**：caller 与 callee 走**同一份声明序**；某参数只在「其所属 bank 已耗尽」时占栈槽 ⇒ 栈槽的消耗顺序 = 溢出参数在声明序中的出现顺序；两侧对「是否耗尽」的判定完全相同（`left` 与 caller 的槽位计数同源）⇒ `va_list` 只记**剩余量**、不记「已用计数」。
- **理由**：三条规则即可覆盖「寄存器足够 / 整组不足 / bank 耗尽」；`va_arg` 不需要调用点元数据。与主流 `va_arg` 实现同构（按类型分类 → 取寄存器或栈 → 推进）。
- **被否**：① **统一 8 B 步进（现状 §3.3）** —— 16 B 值/HFA 多叶子会被拆错，且无法区分 bank；② **bank 不足时拆半**（低半在寄存器、高半在栈）—— 与 `ADR-0030 D2`「不拆半」冲突、`ldm.o` 无法直通；③ **只记「已用槽数」** —— 每次 `va_arg` 需再算 `32 - start - used`，且 `start` 仍要携带；直接记剩余量状态更少；④ **`va_arg` 一律从栈读** —— 与 D2 的保存区设计矛盾，等于退回 caller 块。

### D5 — `float` 占 RF 槽**低 32 位**；32 位整数同理（低位 + 符号/零扩展）【用户已确认：低 32 位】

- **决定**：
  - **`float`**：RF 槽 `[31:0]` = IEEE binary32 值，`[63:32]` **不作规定**（`spec/SimRISC-00:89` 原文）；`ld.t` 只改低 32 位、`st.t` 只存低 32 位（`SimRISC-01:198`、`SimRISC-03:161`）。
  - **32 位整数**（`int`/`unsigned int`；以及按 C 提升后落 `int` 的 `short`/`char`）：RD 槽 `[31:0]` = 值，`[63:32]` = **符号/零扩展**（caller 完成，`contract-abi §4.2`；装载侧同规则 `SimRISC-01:75`）。**不是**「值放高 32 位」。`long` 在本 target 为 64 位（LP64），不属此条。
  - **内存 slot（大端）**：N 字节值的有效字节**右对齐**在 8 B 槽的 `8-N … 7`（现状 `§3.3` 的表格**保留**）——这与「寄存器低 32 位」是**同一数值**的两种容器表示，不是两套约定。
  - HFA 的 `float` 叶子同样占 RF 低 32 位；`va_arg` 遇 `float` 属 UB（C 标准要求 `double`，见 `D8`）。
- **理由**：ISA 只有 `ld.t`/`st.t` 的 32 位形式且作用在低半（`SimRISC-01:198`、`SimRISC-03:161`）；若 `float` 放高 32 位，每次浮点运算前都要 `shr.o 32`、存回再 `shl.o 32`，且 `rf0` 的写语义（`[63:32]` 不变）会与 FCSR 冲突。**寄存器内位序与端序无关**：端序只决定内存字节顺序（用户第 2 问的答案：无冲突）。32 位整数放低位是同一道理，且与 `contract-abi §4.2` 的 canonical 扩展一致（用户第 3 问的答案：**不是**高 32 位）。
- **被否**：① **`float` 放高 32 位** —— 每条浮点指令前多 2 条移位、`ld.t`/`st.t` 不匹配、`rf0` 语义冲突；② **32 位整数放高 32 位** —— 与 `§4.2`/装载扩展规则冲突，所有窄整数运算需额外移位；③ **寄存器/内存两套相反约定** —— 静默错值，无门控可自动发现。
- **注**：`rf0` 是**浮点控制/状态寄存器**（`DADAO-21:54`、`contract-abi §1.4`），**不是**零寄存器 ⇒ `rf16–rf31` 从 16 起分配、`rf0` 不参与参数传递（与 `ADR-0030 D2` 一致）。

### D6 — 16 B 值：**高半在偶号（低号）寄存器**，低半在奇号（高号）【用户已确认；修订 `ADR-0030 D2`】

- **决定**：
  - **参数**：`rf16` = 高半、`rf17` = 低半；`rf18`/`rf19` … 依此类推；RB 承载的 16 B 值同规则（`rb16` = 高半、`rb17` = 低半）；RD 承载的 16 B 整数类聚合同规则。
  - **返回**：`rf8` = 高半、`rf9` = 低半（binary128）；即 `ADR-0030 D2` 的「低位在偶号」**修订为「高位在偶号」**（参数与返回同时改）。
  - **配对起点必须偶号**：所需槽数 = **2**（游标偶号）或 **3**（游标奇号，先跳 1 槽）；`left <` 所需槽数 ⇒ 整值走栈、**不跳过也不推进**；否则奇号先跳 1 槽（`next += 8`、`left -= 1`）再取 2 槽。两侧同规则。
  - **`__int128` 的传参/返回仍按 `contract-abi §6.3` 不支持**（本 ADR 不改该条）。用户原话中的 `rb16`/`rb17` 例按「**RB 承载的 16 B 值**（如 16 B 聚合/HPA 对）」理解；若用户意图是**解禁 `i128`**，须另行裁定。
- **理由（大端 + `ldm.o`/`stm.o` 直通）**：`ldm.o`/`stm.o` 的寄存器号递增 = 地址递增（`SimRISC-01:24-27`、`:43-47`、`:123`）；大端下 128 位值的**高半在最低地址** ⇒ 低号寄存器装高半时，`ldm.o {rf16:rf17}, [rbH, rdC]` / `stm.o {rf16:rf17}, [rbH, rdC]` **一条指令**完成 16 B 搬运；若低半在偶号，必须两条 `ld.o` 或先 load 再 `rd2rf`/swap，且易在优化后静默错序。其它大端机器（s390x / PPC64 BE）同样按内存字节序把高半放低号寄存器对（**内容溯源，非执行必需**）。
- **被否**：① **低位在偶号（`ADR-0030 D2` 原措辞）** —— 大端下与 `ldm.o`/`stm.o` 相反，需 swap；② **半字顺序由实现自定** —— 编译器/库/手写汇编三方静默不互操作；③ **高半在奇号** —— 与 ① 等价（低半在偶号）；④ **改成小端存储** —— 违背 `DADAO-21 §数据表示` 的全局大端。

### D7 — 溢出与栈规则：**按 bank 独立溢出**，`va_arg` 可切栈【用户已确认：溢出原则；对齐细则 = 架构师提案】

- **决定**：
  - 某 bank 槽位用尽 ⇒ **该 bank 的后续参数**进栈；其它 bank 继续用寄存器（沿用 `spec §3.2.4`，`ADR-0018 C4` 的**全局声明序单栈区**）。
  - 栈槽：标量 8 B；`long double` / binary128 / 16 B 值 = **16 B 占两槽、16 B 对齐**（必要时跳过一个 8 B 槽）；`>16 B` 聚合按 `size` 向上取整到 8 B、对齐 `max(8, align)`。
  - `va_arg` 切栈时按 `D4` 步骤 3 推进；栈上 16 B 值同样**高半在前**（最低地址 = 高半），与 `ldm.o`/`stm.o` 一致。
  - **不引入**「某 bank 耗尽则全部参数走栈」的全局规则（与 `§3.2.4` 冲突，且无必要）。
- **理由**：与 `ADR-0030 D2` 的「寄存器不够 ⇒ 整值退栈、不拆半」一致；16 B 对齐是 `ldm.o`/`stm.o` 的硬要求（`SimRISC-01` 对齐规则，未对齐触发 `MALIGN`）。
- **被否**：① **一旦某 bank 耗尽就全走栈** —— 改变既有 `§3.2.4` 语义、且浪费其它 bank 槽位；② **不保证 16 B 对齐** —— 栈上 binary128 只能用两条 `ld.o`，`ldm.o` 直通失效并可能 `MALIGN`；③ **溢出参数按 bank 分组存放** —— 与 `ADR-0018 C4` 的全局声明序单栈区冲突。

### D8 — 默认实参提升（C 标准，沿用现状）【外部契约，非用户裁定】

- **决定**：变参调用点按 C 标准提升：`char`/`short`（有/无符号）→ `int`；`float` → `double`；`_Bool` → `int`；其余不变。`va_arg` 必须使用**提升后**类型（`va_arg(ap, float)` 为 UB）；`va_arg(ap, char)` 须写 `va_arg(ap, int)` 再截断（现状 `§3.3` 表格保留）。
- **理由**：C 标准（`6.5.2.2`）与既有 `spec §3.3` 一致；改则破坏 `printf` 等全部可变参库函数。
- **被否**：① **不做提升** —— 违背 C 标准、`%f`/`%c` 断裂；② **提升到 64 位而非 `int`/`double`** —— 与 C 的 `va_arg` 类型匹配规则冲突（`int` 与 `long` 在 `va_arg` 中不可互换）。

### D9 — 规范落点与授权边界【流程约束】

- **决定**：本 ADR **不改** `spec/` / `contract-abi` / 实现。确认后按 `docs/Process-06` 取得用户**原话授权**再改册：`spec/DADAO-21 §3.3`（整节重写，见附录 A）、`§3.2.3`/`§3.2.4`（16 B 门槛与溢出交互）、`§3.4`（返回对顺序）、`§2.2`（16 B 栈对齐）；`contract-abi §4.2`/`§4.3`/`§4.4`/`§6.3`/`§6.4`。实施落点 = `LLVM-101t` / `LLVM-102t`（B 项解阻塞）+ 新立任务（待确认后）。
- **理由**：`spec/` 有只读册锁（`check-spec-readonly`）；已 `Accepted` 的 `ADR-0030 D2` 正文不得就地改写（只加修订注记）。
- **被否**：① **在 ADR 内写死规范正文**（`docs/Process-03`）；② **未授权先改 `spec/`**（`docs/Process-06`）；③ **直接改 `ADR-0030 D2` 正文**（已 `Accepted`，须新增 ADR/逐条确认）。

## Rationale（总述）

- **一致性**：`D1`/`D2` 把「三 bank 独立计数」的代价从**每个调用点**移到**变参函数自身**，并用「3 游标 + 3 剩余计数 + 栈指针」把「声明序 + 类别分流」变成可执行的游标；`D3`/`D4` 让聚合在命名与变参两侧共用一张分类表；`D5`/`D6` 让寄存器语义与 ISA 的 `ld.t`/`ldm.o`/`stm.o` 直通，不再需要 swap。
- **最小代价**：不改 ISA、不改编码、零 QEMU 改动；主要新工作 = clang `EmitVAArg` + 后端调用约定 + musl `va_list` 头 + 保存区 prologue。
- **可验证性**：三游标可逐字段断言；半字顺序可由 `ldm.o`/`stm.o` 反汇编 + 大端内存 dump 双向判别；聚合分类表可逐类构造最小用例；溢出可构造「17 个整型实参 + 变参尾」（`LLVM-102t` B 的 `repro_varargs`，期望 136）。

## Consequences（影响）

- **clang/LLVM**：`DADAOABIInfo::EmitVAArg` 改为按 `D3`/`D4` 分类取寄存器或栈；变参 prologue 生成三 bank `stm.o`；`va_start` 初始化三游标 / 三计数 / 栈指针；`D6` 的半字顺序影响 `f128` 成对载体与 `ldm.o`/`stm.o` 选择；`D3` 的 16 B 门槛若覆盖命名参数，会改 `classifyArgumentType` 与既有 lit 向量。
- **musl**：`arch/dadao/bits/` 的 `va_list` 定义（七字段结构：3 `next` + 3 `left` + `stack_next`）+ `stdarg.h` 宏；`vfprintf` 等按指针传递 `va_list` 的代码须与结构体布局一致。
- **契约**：`contract-abi §4.2`/`§4.3`/`§4.4`/`§6.3`/`§6.4` 须在确认后同步（`docs/Process-02`）；`check-spec-drift` 要求契约引用的 ADR 为 `Accepted` ⇒ **本 ADR 为 `Proposed` 期间契约不得引用**。
- **测试**：变参标量（int/double/pointer 混合）、HFA/HPA/union/混合结构、`>16 B` 聚合、binary128 参数/返回、寄存器耗尽（每 bank 单独耗尽 + 多 bank 交错）、16 B 栈对齐、大端半字顺序；oracle 独立派生（手算 + 内存 dump，不从 LLVM/QEMU 反推）。
- **性能**：变参函数最多 384 B 帧 + 48 store；调用点零额外保存。非变参零影响。
- **兼容性**：`va_list` 由 `void*` 变为 4 指针结构 ⇒ **既有二进制/源码不兼容**；须与 musl/编译器同批切换，旧目标文件不得混链。

## 附录 A：`spec §3.3` 改写提案（**仅提案，未落 `spec/`**）

> 用途：确认后由实施任务按 `docs/Process-06` 授权改册。以下为**替换 `spec/DADAO-21-ABI §3.3` 全节**的建议文本（标题与编号不变）。

### 3.3 可变参数：Variable Arguments（提案）

`va_list` 为七字段结构（字段顺序固定，ABI 可观测）：

```c
typedef struct {
    uint64_t *rd_next;
    uint64_t *rb_next;
    uint64_t *rf_next;
    int64_t   rd_left;
    int64_t   rb_left;
    int64_t   rf_left;
    uint64_t *stack_next;
} va_list[1];
```

**寄存器保存区（callee 侧）**

变参函数在自己的栈帧内为每个参数 bank 分配保存区：从该 bank 的 `start`（命名参数占用后的下一个槽）到 31，连续存放，使用 `stm.o` 保存。命名参数已用尽某 bank 时，该 bank 不分配保存区。

**`va_start(ap, last_named_arg)`**

按命名参数在各 bank 的占用数初始化 `rd_next`/`rb_next`/`rf_next` 指向保存区首个可变参数槽，`rd_left`/`rb_left`/`rf_left` = `32 - start`；`stack_next = incoming_sp`（`rbfp + 8`）。

**`va_arg(ap, type)`**

1. 按 `§3.2.3` 的分类表确定 `type` 的 bank 与槽数（HFA → RF，HPA → RB，其它/union/混合 → RD）；`> 16 B` 只在栈上。
2. 该 bank 的 `left` ≥ 本参数所需槽数 ⇒ 从游标取，游标 += 槽数、`left` -= 槽数。
3. 否则从 `stack_next` 取，`stack_next` += 栈占用（8 B / 16 B，按对齐补齐）；该 bank 游标不推进。
4. 16 B 值：高半在低号（偶号）槽、低半在高号（奇号）槽；所需槽数 = 2（偶号）或 3（奇号，先跳 1 槽），`left` 不足则整值走栈（不跳过、不推进）。
5. HFA/HPA 按叶子逐个还原；`> 16 B` 聚合从栈按值复制。

**调用者**

不再写保存区；只按 `§3.2` 的规则把参数放入寄存器或栈。寄存器耗尽的参数进栈（按 bank 独立判定），栈区按全局声明序连续存放。

**大端 slot 布局**（沿用现状）

8 B slot 内 N 字节值右对齐（byte `8-N` 至 `7`），低地址字节为符号/零扩展位。

**实参提升**（C 标准，沿用现状）

`char`/`short` → `int`；`float` → `double`；`_Bool` → `int`；`va_arg` 须使用提升后类型。

**与现状的差异**

- `va_list`：`void*` → 七字段结构（3 游标 + 3 剩余计数 + 栈指针；不兼容）。
- 保存区：caller 写整块 → callee 按 bank 保存。
- `va_arg`：统一 `+8` → 按类别/槽数/栈切换推进。
- 16 B 值：无规定 → 高半在偶号、偶号配对、栈上 16 B 对齐。
- 聚合：≤64 B 进寄存器 → ≤16 B 按类别进寄存器、>16 B 走内存（**待 `D3` 范围确认**）。

> **同时需要改的相邻节**（不在本附录展开）：`§3.2.3`（16 B 门槛与 union/混合归类）、`§3.2.4`（与变参溢出的交互）、`§3.4`（返回对 `rf8`=高/`rf9`=低）、`§2.2`（16 B 栈对齐）。

## 附录 B：与主流 64 位 psABI 的对照（**内容溯源，非执行必需**）

| 议题 | x86-64 SysV | AArch64 AAPCS64 | RISC-V LP64D | 本提案 |
| --- | --- | --- | --- | --- |
| 聚合寄存器上限 | 16 B（两个 eightbyte） | 16 B | 2×XLEN = 16 B | **16 B** |
| HFA | 无（按 SSE 类拆分） | ≤4 成员（最多 32 B） | ≤2×FLEN = 16 B | **≤16 B（RISC-V 式）** |
| `>16 B` 聚合 | 内存（按值） | 内存（按值） | 按引用 | **内存（按值，`D7`）** |

| 128 位值半字顺序 | —（x87 栈式/内存） | 单 `q` 寄存器 | 偶-奇对（低半在偶号） | **偶-奇对（高半在偶号，大端直通）** |

> 结论：本提案在「16 B 门槛 + 整组走栈」上与三家同向；在「128 位对顺序」上按**本机大端 + `ldm.o`/`stm.o`** 取高半在偶号（与 RISC-V 的小端约定相反，但与本机内存序自洽）。
