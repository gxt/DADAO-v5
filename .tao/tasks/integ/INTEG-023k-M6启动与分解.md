## M6 建议方案（供用户挑，**不替他定**）

### S1 测试策略候选（核心问题的**设计主线**）

> 每条格式：**做什么 ｜ 规模 ｜ 自动化方式 ｜ 独立 oracle 来源 ｜ 代价 ｜ 前置 ｜ 与 `Process-05` TDD 的关系**。

**① 差分测试（与参考实现 / golden 对比）**
- **做什么**：同一 IR / 汇编输入，**双端执行**，对比输出（如 v5 `llc`+QEMU ↔ 参考模型）。
- **规模**：中–大（可批量）。
- **自动化**：脚本批量驱动（输入生成 → 两端跑 → diff）。
- **独立 oracle 来源**：**参考实现**（非 spec 派生）⇒ **只发现分歧、不单独证正确**（两端可能同错）。
- **代价**：中（需参考实现可用）。
- **前置**：参考实现可运行 ⇒ **`DADAO-0628` 为 SimRISC 0.4.1**，与 v5（0.5.4）**ISA 不同** ⇒ **不能直接对拍**；或需另建"第二实现"。
- **与 `Process-05` 关系**：属 L3 的**补充**手段，**不得**替代 independent oracle（`AGENTS.md`「Independent oracle」）。

**② 结果级 golden model（独立 oracle，承接 `ISS-019/026/081`）**
- **做什么**：按 `spec/` 语义**独立实现** Python golden model，算出「IR / 指令 → 结果」的期望值。
- **规模**：大（ISA 全量；可分阶段：先整数 codegen 覆盖面）。
- **自动化**：批量（向量 → golden 期望值 → 与 QEMU 执行结果比对）。
- **独立 oracle 来源**：**`spec/`（独立派生）**——**唯一**符合 `Process-05 §2` L3 判据的路径。
- **代价**：大（需启动 `GOLDEN` 模块 + 契约完备）。
- **前置**：`GOLDEN` 模块启动；`contract-*` 覆盖对应能力。
- **与 `Process-05` 关系**：**L3 唯一判据来源**；**M6 若以「编译正确性」为主线，此条是根本依赖**。

**③ 生成式 / 随机 IR（fuzz）**
- **做什么**：随机生成 IR / 程序，跑 `LLVM → QEMU`，对拍 golden（②）或差分（①）。
- **规模**：大。
- **自动化**：fuzz harness（生成器 + 收缩）。
- **独立 oracle 来源**：**需 ① 或 ②**（**单独 fuzz 无 oracle，只能查崩溃 / 挂起**）。
- **代价**：中–大。
- **前置**：②（或①）先就位。
- **与 `Process-05` 关系**：属「规模 ∝ 能力」的**放大器**，但**判据仍须是独立 oracle**（不得用「跑通不崩」当正确性证据）。

**④ 真实 C 程序链路（clang / 最小 libc 之辨）**
- **做什么**：以 **C 程序**为输入：`clang 前端 → v5 LLVM → QEMU` 执行，比对**程序自带期望输出**（独立于工具链）。
- **规模**：中（程序集可扩）。
- **自动化**：脚本批量（编译 → 跑 → 比对 stdout / 退出码）。
- **独立 oracle 来源**：**程序自带期望值**（如已知算法输出、`printf` 结果）——**独立于工具链**。
- **代价**：中；**关键分歧**：**是否引入 clang 前端 / 最小 libc**？
  - **含 clang**：能测完整前端→后端链路，但**引入大依赖**（clang/头文件/libc），且 M4 曾明确「留后」。
  - **不含 clang**：退为「**C 子集源 + 自带 driver**」（手写 IR / 极简 driver 生成 IR），覆盖有限但**零新依赖**。
- **前置**：clang/libc 决策（见 §S4）。
- **与 `Process-05` 关系**：属 L3 的**端到端载体**；期望值须**独立派生**（**不得**用「v5 编出来的结果」当期望值）。

**⑤ 其它（lit 量产 + `llc`/QEMU 双端对拍）**
- **做什么**：
  - **lit 大量用例**：扩 L1（MC）/ L2（CodeGen 结构）用例量级（`tests/llvm/lit/**`）——**只锁回归、不证语义**（`Process-05 §2`）；
  - **`llc` 与 QEMU 双端对拍**：IR → `llc` 出 asm/obj → QEMU 执行 → 与 host 端（golden / 程序期望）对比。
- **规模**：可小到大（取决于用例生成）。
- **自动化**：lit + 脚本。
- **独立 oracle 来源**：L2 无（手写 CHECK）；L3 同 ②/④。
- **代价**：小–中。
- **前置**：无（可与 ② 并行）。
- **与 `Process-05` 关系**：L1/L2 属**防回归**层；**L3 语义仍靠 ②/④**。

> **建议（供参考，不替用户定）**：以 **② golden model（整数优先）**为**骨架**，用 **⑤ lit 量产**与 **④ C 子集/真实程序**做**端到端放大器**，**① 差分**作**独立第二意见**（在有参考实现时），**③ fuzz**在 ② 就位后做**规模扩展**。是否引入 **clang/libc** 单独裁定（见 §S4）。

### S2 RAM@0 尺寸取值建议 + 对已落纸项的影响清单

**尺寸选项**：**1 GiB / 2 GiB / 4 GiB**；**建议「先 1 GiB 起步」**（够跑完整 ELF + 大量测试；可按需再扩，避免一次占满低地址空间）。**最终由用户定**。

> **2026-10-08 实测更新（主会话，并入 §D）**：RAM 是**单次运行**口径；现最大单程序 `.o` = **1128 B**、`m5-e2e` 10 个 bin 合计 **980 B** ⇒ **16 MiB 已远超**、**1 GiB 余量极大**、4 GiB 无必要。**主会话建议：先维持 16 MiB**（省 `spec/` + 锁 + ADR + 断言 + 补丁连带改动），**撞上限再改**。⇒ §S4 #1/#2 的建议据此**下调为「维持 16 MiB / 暂不授权」**（见 §D.3）。

### S3 ELF 直载 + 链接器完善的范围

**（a）QEMU 直接加载 ELF（用户第 3 点）**
- **现状**：M4 ELF 路径（`ADR-0004 D2.2/D2.3` 路径 A）已支持单 ELF：`PT_LOAD` + VA=PA 装载 + 取 `e_entry`（`QEMU-042t`）。
- **待完善**（`ISS-168` 等）：
  - **`dadao_load_regions[]` 扩表**：`hw/dadao/dadao-machine.c` 现仅列**旧 RAM 段 + ROM**，**未含 RAM@0** ⇒ 链进 RAM@0 的 ELF 段**暂不可加载**（`QEMU-049t` 遗留）；
  - **多段 `PT_LOAD`**（.text/.data/.bss 分离）、**RELA 重定位的加载期应用**、**入口 / 栈初始化**语义；
  - **RAM@0 段**（与 §S2 尺寸联动）；
  - **「`-bios` + ELF」组合语义**：复位 PC `0xffff_ffff_0000` → bootrom 初始化 → 跳 ELF `e_entry`（**`e_entry` 传递方式待定**）——**注**：用户第 3 点「QEMU 直接加载 ELF」**倾向 M4 path A**（**不用 bootrom**）⇒ 本组合路径**是否仍需要**（`ISS-168`）**待用户裁定**（见 §S4 #7）。

**（b）链接器（LLD）更完善（用户第 4 点）**

### D.0 两条实测结论（本轮并入，**依据 = 主会话实测**）

- **实测①（RAM 尺寸口径）**：RAM 是**单次运行**口径；现最大单程序 `.o` = **1128 B**、`m5-e2e` 10 个 bin 合计 **980 B** ⇒ **16 MiB 已远超**、**1 GiB 余量极大**、**4 GiB 无必要**。**建议先维持 16 MiB**（省 `spec/Machine-01` + 锁 + ADR + `check-interface` 断言 + QEMU 补丁 + 重建的**连带改动**；撞上限再改 1 GiB）。
- **实测②（上游 LLVM 测试可复用性）**：本仓库锁定源码（`.work/source/llvm-project/llvm/test/`）实测——`ExecutionEngine` **476**、`CodeGen/Generic` **208**、`Verifier` **416**、`Transforms` **12085**（文件数）；**无** `test/{MC,CodeGen}/DADAO`（我方 lit 在**本仓库** `tests/llvm/lit/**`，共 **58** 个源文件）。**结论：上游测试几乎不能直接用**——v5 **无 JIT/`lli`**（故 `ExecutionEngine` 无载体）**且 ISA 不同**（`CodeGen/Generic` 的 CHECK 面向其它 target）。**可复用「素材与框架」**：把上述 IR **当输入**，走「`llc`→`ld.lld`→**QEMU 直载 ELF** + 独立期望值」管道；**判据三来源 = 手写 / 从 `spec` 派生 / golden（独立参考结果）**。

### D.2 测试策略方案（**素材来源 × 判据来源 两轴**）

**（a）两轴定义**

- **素材轴（测试输入从哪来）**：① **自写**（手写 IR/`.s`/C 子集，可审计、`Process-05 §4`「手写少量」）；② **上游 IR**（`.work/source/llvm-project/llvm/test/{Transforms,CodeGen/Generic,Verifier}` 的 `.ll` **当输入**）；③ **生成**（fuzz / IR 生成器）。
- **判据轴（期望值从哪来）**：① **手写**（已知算法输出 / 程序自带期望值）；② **`spec` 派生**（host 侧独立模型按 `spec/`+`contract-*` 重算，**唯一符合 `Process-05 §2` L3 判据**）；③ **golden**（**独立参考结果**——`GOLDEN` 模块的黄金模型产出，承接 `ISS-019/026/081`）。

**（b）素材 × 判据 适配矩阵**（**禁止**用工具链自身产物当期望值，`AGENTS.md`「Independent oracle」）

| 素材＼判据 | 手写 | `spec` 派生 | golden |
|---|---|---|---|
| 自写 | ✅ L1 编码（`contracts/opcodes.yaml`）/ L2 结构（手写 CHECK，**仅防回归**） | ✅ L3 整数语义（**骨架**） | ✅ L3 对照 |
| 上游 IR | ⚠️ 仅作冒烟 | ✅ L3（把上游 `.ll` 当输入，期望值独立重算） | ✅ L3 规模化（**主放大器**） |
| 生成（fuzz） | ❌ | ⚠️ 需模型可覆盖 | ✅ 收缩后对 golden 对拍 |

**（c）管道（**统一为 QEMU 直载 ELF**，替代 `objdump` bin + bootrom）**

```
<输入: 手写 .ll/.s | 上游 .ll> → llc (-march=dadao) → .s/.o
    → ld.lld (DADAO target, ET_EXEC) → ELF
    → qemu-system-dadao -M dadao-m1 [纯 ELF 直载]  → 退出码 / 控制台 / -d cpu 寄存器 dump
    → 与「判据轴」的期望值比对（host 侧）
```

> **前置**：ELF 直载（#12–#13）+ 链接器完善（#8–#10）；`e_entry`/栈语义（#13）。**`-bios`+bin** 旧路径保留对照（`test-codegen`/`test-elf`/`test-semihost` 不回归）。

**（d）规模与自动化 —— 分层（**不新增慢门控**，用户明确）**

- **日常快档（在 `make check` 内，秒级）**：现有 `check-lit`（L1/L2，58 源）+ `check-qemu-semantics` + 少量 L3 **smoke**（如 `test-codegen` 15 例）。**M6 新增的向量默认走「快档可容」子集**——即进 `make check` 的只有**少量、秒级**用例；**不把全量套件挂进 `make check`**。
- **里程碑全量档（**opt-in，独立 target，不进 `make check`**）**：新增 `make test-m6`（**用户裁定后才建**），跑「golden 对拍 + 上游 IR 复用 + lit 量产 + fuzz 收缩」的**数百—上千**用例；**默认不参与 `check`**，由里程碑收尾/回归时显式运行（**呼应「不要新增慢门控」**）。
- **自动化**：全部由脚本驱动（生成→`llc`→`ld.lld`→`qemu`→比对→非零退出）；证据脚本落 `.work/evidence/<任务ID>/`，可复用检查器入 `tools/<module>/`（`AGENTS.md`「一键证据脚本」）；**反例门控**（`Process-05 §5`）为硬要求。

### D.3 需用户裁定清单（**逐条：选项 + 架构师建议 + 依据**）

> **架构师建议仅为提案**；凡涉 **ADR / `spec/` 授权 / 契约变更**者，**须用户逐条裁定**（`AGENTS.md`「ADR decision 逐条确认」「子代理硬约束 9」）。

1. **RAM@0 尺寸**：A **维持 16 MiB**（**建议**）/ B `1 GiB` / C `2 GiB` / D `4 GiB` / E 其它。**依据**：实测①（最大 `.o` 1128 B、10 bin 合计 980 B ⇒ 16 MiB 远超）；维持可**免去** `spec`/锁/ADR/断言/补丁/重建的连带改动。

3. **内涵逐项（D.1 第 1–20 项）纳入与否**：**逐项裁定**（保留 / 修改 / 否决）。**依据**：`Process-05 §3`「规模 ∝ 能力」，**不超前建大套件**。
4. **是否引入 `clang` 前端 / 最小 `libc`**：A **均不引**（**建议**，M4 已留后）/ B 引最小 libc、不引 clang / C 引 clang + libc / D 暂不做。**依据**：大依赖；完整调用约定为前提。
5. **「`-bios` + ELF」组合是否仍需要**（`ISS-168`）：A **不需要**（**建议**，纯 ELF 直载）/ B 需要（须定 `e_entry` 传递方式 + 立 ADR）/ C 推迟。**依据**：用户 2026-10-08 原话「用 elf 的时候，则不需要 bootrom，只需要 semihosting」。
