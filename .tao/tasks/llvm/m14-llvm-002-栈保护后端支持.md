## 背景（实测事实，勿改）

- **缺口实测（`m14-infra-001`，2026-11-13）**：`clang -target dadao-unknown-elf -O1 -fstack-protector-strong` ⇒ rc=1，诊断 `error: unable to lower stackguard`；`-mstack-protector-guard=*` 同样被拒。宿主 x86 clang 同源 rc=0 ⇒ 结论由 **target** 决定，不是 host 环境。
- **用户 2026-11-13 裁定**：**现在补后端**（不再长期用 `-fno-stack-protector` 规避）；Linux KSPP 默认 `-fstack-protector-strong`，K0 内核构建需要它。
- **上游机制定位（架构师只读核对；engineer 须现场复核并在完成区贴证据）**：
  1. 失败点：`llvm/lib/CodeGen/SelectionDAG/SelectionDAGBuilder.cpp` 的 stackguard 展开——当 `TLI.useLoadStackGuardNode() == false` 且 `TLI.getSDagStackGuard() == nullptr` 时 `diagnose("unable to lower stackguard")`（`visitIntrinsicCall(@llvm.stackguard)` 与 `visitSPDescriptorParent` 各一处分派）。DADAO 当前既未注册 SSP hook，也未注册 SSP libcall ⇒ 落该分支。
  2. 通用 provider 通道：`TargetLoweringBase::insertSSPDeclarations` / `getSDagStackGuard` 由 `RTLIB::STACK_CHECK_GUARD` 的 **libcall impl** 驱动（声明/返回 `__stack_chk_guard` 全局）；失败块符号由 `RTLIB::STACKPROTECTOR_CHECK_FAIL` 决定（`llvm/lib/CodeGen/StackProtector.cpp::CreateFailBB`；该 impl 也缺失时另报 `no libcall available for stack protector`，本任务两条都要注册）。
  3. DADAO 已有同形先例：`DADAOSubtarget::initLibcallLoweringInfo` 已注册 `mem*`/soft-float/i128 libcall（`LibcallLoweringInfo` 由 subtarget 初始化，`LibcallLoweringInfo.cpp` 调 `Subtarget.initLibcallLoweringInfo`）。
  4. 前端门禁：`clang/lib/Driver/ToolChains/Clang.cpp` 的 `RenderSSPOptions` 对 `-mstack-protector-guard=` 按 triple 白名单（x86/aarch64/arm/riscv/ppc/systemz）校验，dadao 不在其中 ⇒ `err_drv_unsupported_opt_for_target`。`-mstack-protector-guard=` 最终写 module flag（`CodeGenModule` → `Module::setStackProtectorGuard`）；`StackProtector::getStackGuard` 仅在 `getIRStackGuard` 返回非空且 GuardMode 为 `tls`/空 时走 IR guard 路径，否则走 SelectionDAG 路径（DADAO 的 `getIRStackGuard` 为 null ⇒ 默认与 `global` 都走 SDAG；若放过 `tls` 也会落同一条 SDAG 路径而**静默用全局符号**，故必须显式拒绝）。
- **运行时来源（本任务只需声明、不定义）**：`__stack_chk_guard`（指针宽度、外部链接地址对象）与 `__stack_chk_fail`（`void(void)`、`noreturn`）由链接方提供——Linux 内核自带（`CONFIG_STACKPROTECTOR` 的 panic 路径）、picolibc `libc/ssp/stack_protector.c` 自带、musl 亦自带。**本仓不新增运行时文件**。

## 目标

1. 在 DADAO 后端实现 stack protector lowering：canary 存入帧、guard 取值、epilogue 比对、失败路径调用 `__stack_chk_fail`；
2. `-fstack-protector` / `-fstack-protector-strong` / `-fstack-protector-all` 三档在 `-O0/-O1/-O2` 下均 rc=0 且生成完整检查序列；
3. 明确并落地 guard 来源：**全局符号 `__stack_chk_guard`**（默认模式）；`-mstack-protector-guard=global` 被接受且与默认输出一致；`tls` **明确拒绝**（不静默降级）；
4. lit 覆盖开/关 SSP 的结构与对象级断言；E2E 证明越界写真的触发 `__stack_chk_fail`；
5. `-fno-stack-protector` 输出与改动前**逐字节一致**（对象 md5），既有门控全绿。

## 接口规范

**输入**：`clang -target dadao-unknown-elf` 的 C 源；`llc -march=dadao` 的 IR（函数属性 `"stack-protector"`/`"-strong"`/`"-all"`；module flag `"stack-protector-guard"`）。

**输出（语义契约）**：

1. **guard 取值**：从外部全局符号 `__stack_chk_guard` 做一次 volatile 载入（指针宽度 = 64 位），符号**只声明不定义**；不得内联常量、不得伪造定义。
2. **canary 布局**：被保护函数的帧内有 canary 槽，prologue 存入 `__stack_chk_guard` 的值；槽位与被保护数组的相对位置由通用 SSP pass + 帧布局决定，后端**不得改变对象顺序/栈槽排序**使越界写绕过 canary（E2E 触发组是唯一判据）。
3. **epilogue 比对**：每个返回点前从槽载入、与 guard 比较，不等 ⇒ 跳失败块。
4. **失败路径**：调用外部符号 `__stack_chk_fail`（`void(void)`，`noreturn`），无参数、无返回值；符号只声明不定义。
5. **选项语义**：
   - 默认（不写 `-mstack-protector-guard=`）与 `-mstack-protector-guard=global` 走**同一** codegen 路径，`-S` 输出逐字节一致；
   - `-mstack-protector-guard=tls` ⇒ **编译期报错**（driver 与后端两侧都不得静默降级为 global）；理由：DADAO 的 ABI 未定义 TLS canary 槽（`rb3=rbtp` 存在，但槽位/偏置未冻结）；
   - `-fno-stack-protector` ⇒ 与改动前完全一致，不产生任何 `__stack_chk_*` 引用。
6. **约束**：不改 ABI/寄存器分配（`rb3=rbtp` 不动）、不改 `spec/`/`contracts/`/`docs/Process-*`；与 `-mcmodel=default|large`、`-O0..-O2`、`-fno-pic`（K0 静态场景）正交。

## 实现落点（建议；engineer 可按现场调整，但须在完成区披露）

1. **libcall 注册（首选、最小改动）**：`components/llvm-project/patches/llvm/lib/Target/DADAO/DADAOSubtarget.cpp.patch` 的 `initLibcallLoweringInfo` 增两条：
   - `RTLIB::STACK_CHECK_GUARD → RTLIB::impl___stack_chk_guard`
   - `RTLIB::STACKPROTECTOR_CHECK_FAIL → RTLIB::impl___stack_chk_fail`
   这两条使 `TargetLoweringBase::insertSSPDeclarations`/`getSDagStackGuard`/`CreateFailBB` 的通用路径生效（上游 Lanai 的 `SystemLibrary` 正是把这两个 impl 一起登记）。
2. **若通用声明形态不满足**（例如外部全局的 `dso_local`/对齐/地址空间与 DADAO 的 ABS48 载入不合）：在 `DADAOISelLowering.{h,cpp}.patch` 覆写 `insertSSPDeclarations` / `getSDagStackGuard`，显式声明指针宽度、ABI 对齐的外部全局；**只声明不定义**。
3. **`tls` 拒绝**：后端在 `insertSSPDeclarations`/`getSDagStackGuard` 检查 `M.getStackProtectorGuard() == "tls"` ⇒ `M.getContext().emitError(...)`（fail-closed）；前端在 `RenderSSPOptions` 把 dadao 加入允许列表但只接受 `global`，`tls` 用既有的 `err_drv_invalid_value_with_suggestion`（建议值 `global`），**不新增诊断 id**。
4. **不需要**：`LOAD_STACK_GUARD` 机器节点、`useLoadStackGuardNode`、FrameLowering 改动（先按通用帧布局验证；确需改 FrameLowering 时先在同一任务内说明理由）。
5. 补丁按 `docs/Process-01` 生成：在运行期组件检出内改源码 → 本地 commit（E1 干净 + base+1）→ `python3 tools/infra/make_patch.py llvm-project` 重导出；**禁手工编辑补丁**（`@@` 行数会错）。

## 风险与处置

1. **PIC/DSO 场景**：`__stack_chk_guard` 是外部全局，PIC 下需 GOT 载入；K0 走静态/`-fno-pic`，本任务只对静态场景强制。若 PIC 路径不通 ⇒ **范围收窄到静态并在完成区写明**，不要伪造 PIC 支持。
2. **帧布局/PEI 交互**：canary 槽由通用 SSP pass 的 alloca 决定；DADAO 的 banked 寄存器/溢出区自定帧，须确认槽位不被重排到数组「下方」导致越界写不到 canary——E2E 触发组是唯一判据（结构断言不算）。
3. **tail-call 交互**：DADAO 有 tail-jump 降级；被保护函数的检查必须在该路径之前完成。若发现 `tailjmp` 绕过检查 ⇒ 在 lit 中加一例并在完成区说明处置（禁止只测普通 `ret`）。
4. **SETCC/BRCOND 自定义降级**：SSP 比对是 i64 `SETNE`，DADAO 的 `SETCC` 已 Custom（`cmp*` 结果归一化）；若比对/分支形状异常，先在 lit 固定形状，再改后端——不要改通用 `StackProtector`。
5. **前端改动波及其它 target**：dadao 判断必须精确（`EffectiveTriple.getArch() == Triple::dadao`），不得放宽到 `!isX86()` 之类。
6. **矩阵/报告联动**：改完能力后 `tools/linux/toolchain_matrix.json` 的 `stack-protector` 行不改 ⇒ `check-linux-toolchain` 必红（`declared=unsupported` vs 实测 `supported`）；改了矩阵不重生成报告 ⇒ 报告与矩阵不同源（`python3 tools/linux/check_toolchain.py --report --check` FAIL，须在证据脚本里跑）。按「范围」两条同步。
7. **`-fstack-protector-all` + `noreturn`/叶函数**：所有函数都插检查（含无局部数组者），确认不会因无帧函数而漏检查；`-O0` 也要 rc=0。
8. **`__stack_chk_guard` 的对齐**：全局需 ABI 对齐（指针 8 字节）；对齐不足会让载入变成非对齐访问（DADAO 对齐异常）。E2E 与 objdump 都要覆盖。
