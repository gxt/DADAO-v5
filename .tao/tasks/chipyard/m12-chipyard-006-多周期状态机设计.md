## 用户裁定（原话）

「ldm/stm，要做。多周期的状态机设计，应该提前进行；应该通过分析各条指令的实际运行情况，给出一个推荐方案，我来裁定；内部运算的逻辑，可以1到2个周期完成，ld/st类的，都需要存储接口的交互，这部分原本就应该多周期」（2026-11-09）

**补充澄清（同日）**：「1–2 周期」是**举例**，3、5 周期也都可以——**周期数怎么合适怎么来**，不要被「单周期核」的名字绑住。

## 目标

**只做分析与推荐，不实现**。产出「每类指令的周期划分 + 状态机结构」的方案，供用户裁定。

1. **逐类分析**（按执行特性，不是按指令册）：
   - 纯寄存器运算（算术/逻辑/移位/比较/位操作）：**周期数由分析决定**（用户 2026-11-09：1–2 是举例，3、5 周期也都可以，「怎么合适怎么来」）；权衡可仿真性、面积、时序
   - 内部多周期运算：乘法、除法、`clmul`、FP 除法/开方（迭代）
   - 访存：`ld`/`st` 各宽度（**存储接口交互，天然多周期**）；对齐/越界检查放在哪个状态
   - 多寄存器：**`ldm`/`stm`**（N 个寄存器，逐拍还是突发）
   - 控制流：条件分支、`jump`、`call`/`ret`（返回地址计算与 RAS 交互）
   - 原子：`lr`/`sc`（总线交互 + 保留标记）
   - semihosting `trap`：等宿主应答（变长）
2. **推荐方案**：
   - 状态机划分（取指 / 译码 / 执行 / 访存 / 写回 / 特殊），每状态的职责
   - 每类指令的**周期数**（含最坏情况）与状态转移
   - **存储接口握手**：与 TL 的 `valid/ready` 交互、请求挂起与重试
   - `ldm`/`stm` 的实现方式（逐寄存器 vs 突发）与中断/异常点的处理
   - 与现有 `WumingCore` 状态机（005 已实现取指/执行）的衔接：改哪些、保留哪些
3. **备选方案 + 取舍**：至少给 2 个方案（如「统一多周期状态机」vs「快路径 1 周期 + 慢路径状态机」），列优缺点。

## 验收标准

1. 分析覆盖**全部非 cfx 指令族**（按 `spec/SimRISC-0x` 逐册），每类给出周期数与依据
2. 推荐方案含：状态图（文字或 mermaid）、状态转移表、每类指令的周期数
3. `ldm`/`stm` 有明确实现方式与异常处理方案
4. 存储接口握手写明：请求发起、等待、重试、错误（`CFXMEM`/`MALIGN`）的处理时机
5. 给出「对 005 现有 `WumingCore` 的改造范围」（改哪些文件、是否重写）
6. **不实现**：不改 RTL、不建构建
7. 报告落 `.tao/knowledge/refs/m12-006-cycle-design.md`；完成区 ≤30 行、无运行期路径
8. **待用户裁定项单独列一节**（周期数取舍、ldm/stm 方式、是否重写 005）
