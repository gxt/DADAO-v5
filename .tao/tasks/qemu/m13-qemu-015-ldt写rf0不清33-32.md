# m13-qemu-015: `ld.t`/`ldm.t` 写 `rf0` 不得清掉 `[33:32]`（零扩展后再掩码的缺陷）

**模块**：qemu
**项目里程碑**：M13
**依赖**：无（与 `m13-gem5-013` 同期，已由其在 gem5 侧修好）
**可并行分片**：否
**预估**：1–2 h
**状态**：待开始

## 背景（`m13-gem5-013` 实测发现，跨模块）

- 口径（用户 2026-11-14 裁定）：`ld.t`/`ldm.t` **只写低 32 位、高 32 位保持原值**；写 `rf0` 时经 FCSR 写掩码，32 位写入范围内**只有 `[4:0]` 真正生效**，`[33:32]` 在写入宽度之外 ⇒ **必须保持原值**。
- gem5 侧已修（`writeFloatLow32` 的 `idx == 0` 分支）；chipyard 实测本来就对（`0x7FF8_0000_7FC0_001F`）。
- **QEMU 有缺陷**：`target/dadao/` 的 tetra 写口（`store_rf_tetra()` 一类）把 `ld.t` 的值**零扩展到 64 位**后交给 `RF0_WRITE_MASK`；掩码只放行 `[33:32]` 与 `[4:0]` ⇒ 零扩展值把 `[33:32]` **清零**。实测见证值：QEMU 得 `0x7FF8_0000_7FC0_0000` / `0x7FF8_0000_7FC0_001F`，而 spec 与 chipyard/gem5 为保留 `[33:32]` 的形式。

## 目标

1. `ld.t`/`ldm.t` 写 `rf0` 的路径：只把**低 32 位**值交给掩码（或等价：先取 `old[63:32]` 高半、再对低 32 位应用 `[4:0]` 掩码），使 `[33:32]` 与 `[63:32]` 的其余位**保持**。
2. `ld.o`/`ldm.o`（64 位写入）保持现有正确行为（`[33:32]` 由值给出）。
3. 其它 ft 结果族（`ftadd`/`ft2ft`/…）经同一窄写口时行为不变（它们本来就是低 32 位值）。

## 验收（逐条贴真实 rc）

1. **改前正证**：改前二进制 `ld.t rf0 ← 0xFFFF_FFFF` ⇒ `0x7FF8_0000_7FC0_0000` 形（`[33:32]` 丢失；贴 md5 与 `--dump` 见证）。
2. **改后**：`0x7FF8_0000_7FC0_001F` 形；`ld.t rf5` 高半保持；`ld.o rf0` 不变。
3. **三平台逐字节**：`ld.t` 13 点、ft 目的族 29 点、rf0 掩码探针 9 点 ⇒ chipyard/QEMU/gem5 全等（与 `m13-gem5-013` 的证据同口径）。
4. 回归：`check_qemu_trans` 264/264、`check-inst` 红集不扩大、`check-patch_tree` qemu 段 0 问题、`--source-state` qemu OK、`check-component-changelog`。
