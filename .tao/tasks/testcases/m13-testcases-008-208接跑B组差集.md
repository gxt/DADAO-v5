## 背景

`m13-testcases-003` 的 B 组（90 例，无预算上限）只在 207 上跑（32 并发 × 2 档），而 **208 从 13:34 起空闲**。按 `Process-09 §16`「节点不空转」与「调度粒度 = 用例」，应把**尚未开始的用例**转给 208，把 B 组墙钟接近减半。

## 目标

1. **快照差集**：在 207 的 B 组工作目录里读取「已开始」的 case 集合（按用例目录存在判定），与 B 组名单（`B-static.json`/`B-dynamic.json` 的并集）做差 ⇒ **未开始集合**。
2. **在 208 上用 `run_pool.py` 跑差集**（32 并发，两档可并行），每例独立超时（沿用 B 组口径：无实际上限，安全上限 172800 s）。
3. **即产即落**：`progress.jsonl` 落 `.work/evidence/m13-testcases-003/split/B-extra/`，与 207 的结果**按 case 合并**（同 case 两边都跑过时，取先完成的一份，记录 `node` 与 `attempt`）。
4. **不干扰 207**：不改 207 上的运行、不同步节点、不删其产物。

## 非范围

- 不改 `m13-testcases-003` 的任务书与其 A 组结果
- 不改驱动/引擎/用例
- 不重跑 207 已完成的例（除非差集计算错误需要纠正）

## 验收标准

1. **差集正确**：给出公式与现场计数——`B 名单总数 90 = 207 已开始 X + 208 差集 Y`（X+Y=90，无重无漏；Y 为本次任务规模）
2. **208 实际领跑**：`progress.jsonl` 逐行含 `case/status/seconds/reason/utc/node/attempt/fingerprint`（`Process-08 §1.9`），node 为 208
3. **合并规则可判定**：同 case 两节点都有结果时，给出取哪份、依据（先完成 / md5 相同）
4. **207 未被干扰**：任务前后 207 的进程集合、work 目录 mtime 不受影响（只读快照）
5. **可续跑**：`--resume` 跳过已完成；中断后重跑不重复
6. 一键证据脚本（含可达 FAIL 注入：例如把差集算成全量 ⇒ 应 FAIL）
7. 完成区 ≤30 行、无运行期路径
