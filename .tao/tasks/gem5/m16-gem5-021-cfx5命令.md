# m16-gem5-021: cfx5 命令接入 gem5 cache

**模块**：gem5
**项目里程碑**：M16
**依赖**：`m16-gem5-020`（cache 前置）
**可并行分片**：否
**预估**：3–4 h
**档位**：中改（复核 ≤40 min）
**状态**：已验证

## 背景

`m16-gem5-020` 已开 Classic L1；本任务把 cfx5 的 `cache_ctrl` 命令接到 L1（D/I），复用 gem5 现成机制，不新造 cache。

## 要做

1. **命令解码**：cfx5 的 `cache_ctrl`/`cache_addr_start`/`cache_addr_size`，按 `m16-spec-001`。
2. **请求构造**：复用 ARM `dc cvac/civac/ivac` 模板（`src/arch/arm/isa/insts/data64.isa`）：`Request::CLEAN | Request::INVALIDATE | DST_POC`，经 `initiateAcc`/`completeAcc` 发到 L1；I 侧 invalidate 复用 `src/arch/arm/self_debug.cc` 的 `isCacheInvalidate` 语义。
3. **D 侧**：clean 写回保留、invalidate 丢弃、flush 写回+删除；范围 all/单行/区间；`cache_enable=0` 时不维护。
4. **I 侧**：clean no-op；invalidate/flush 后取指重取；I 无 dirty。
5. **`off` 路径**：cfx5 按 `CFXREG`（与 QEMU 口径一致）；不回归 020 的 off/on 基线。

## 不做

- 不改 `src/mem/cache/**`（只发标准 maintenance 请求）；
- 不设周期阈值；
- 不写用例（`m16-testcases-009`）。

## 约束

- 独立 `git worktree`；**不提交 git**；补丁按 `docs/Process-01` 导出，`make_patch.py gem5` 幂等；
- 不写运行期路径；术语「寄存器组」。

## 验证

运行期证据目录内的 `run.sh`：

1. D 侧：脏行 invalidate 后内存旧值、clean 后新值、flush 后失效；
2. I 侧：改写代码后 invalidate，取指执行新代码；
3. 范围/使能/异常逐条；`off` 下 01 册 38/38 与 vast 10/10 不回归；
4. **可达 FAIL**：注入「invalidate 变成 clean」⇒ 红；注入「I 侧不失效」⇒ 红；`cp`+md5 还原后回绿；
5. `check-gem5-decode`、`check-patch-tree` gem5 段、`check-tasks` 记录 rc；`--inject` ≥2 路。

## 完成区

**测试结果**：运行期证据目录内 `run.sh` → **17/17 PASS（rc=0）**；`run.sh --inject all` → **30/30 PASS（rc=0）**（2 路注入各「源码变更 → 重建 → 判红 → `cp`+md5 还原 → 重建 → 回绿」）。关键实测（`cache-model=on`，Vast）：自检向量 A–F 全绿（guest rc 0x10）——寄存器面 6 点（`exist`=0b11、`enable` 复位=exist、`addr_start` 只留 `PA[55:0]`、`addr_size`、`ctrl` 只写、`exist` 只读）；D 侧单行 5 点（脏行 invalidate 后读到内存旧值 / clean 后仍命中且已写回 / flush 写回）；`all` 2 点、`PA 区间` 2 点（区间内丢、区间外保留）、`enable=0` 3 点（不维护但编码仍校验）、异常与 no-op 4 点（`[3:2]=11`、区间 `size=0`、`[15:14]=00` 与 `op=none` 不报、机器外 PA 无效果）。dcache demand hits/misses：clean **686/20**、invalidate **685/21**、flush **685/21**（clean 保留行，另两者丢行）。`off` 下 cfx5 仍 `CFXREG`；`off` 01 册 **38/38**（0 FAIL 行）、`run_m5_e2e --profile vast` **10/10**。
**修改文件**：组件源 6 个：`src/arch/dadao/node_cfx.hh`、`node_cfx.cc`、`isa.hh`、`isa.cc`、`DadaoISA.py`、`configs/dadao/fs.py`（已收敛 `base+1` 并导出）；`components/gem5/patches/` 对应 6 份补丁（`make_patch.py gem5` 重跑 `0 written, 106 unchanged`）；`components/gem5/changelog.md`（M16 追加一条）；运行期证据目录内 `run.sh` + `cfx5_main.s`/`cfx5_drop.s`/`cfx5_off.s`/`cfx5_selfmod.s`；本任务书。
**验收结果**（真实 rc）：`check-gem5-decode` 0；`check-tasks` 0；`check-component-changelog` 0；`make_patch.py gem5` 0（幂等）；`check-patch-tree` **gem5 段 0 problem**（整树 rc=2，22 problem 全在 musl 等既有段，非本任务文件）；`build_gem5.py --jobs 32` 0（基线 1 次 + 注入/还原各 2 次）。未改 `src/mem/cache/**`、未改 `spec/`/契约、未提交 git。
**新发现/坑**：
① **I 侧「取指重取」在本 gem5 模型上不可观测**：命令确实发出（`--cpu-type timing` 下 `icache.demandMisses` 44→46，说明请求到达取指口并失效了枚举到的行；reviewer 实测值，完成区原写 24→25），但把新指令写进**从未执行过**的代码行后再取指，执行的仍是旧指令——`cfx5_selfmod.s` 全程无 cfx5 访问（只有 `st.w` + `ld.uw` 回读 + `jump`），在 `--caches`／无 cache／`--cpu-type timing` 三种配置下都如此（回读到新字、取指执行旧字）。⇒ 与本实现无关，是 DADAO gem5 模型「数据写代码段后取指不可见」的既有缺口，修它要动 `src/cpu/simple/**` 或取指/译码通路（超出 021）。
② **`invalidate all` 会打掉 BootROM 交接留在 L1 的脏行**：`cache-model=on` 的 Vast BootROM 交接阶段写入的页表/monitor 数据留在 L1 脏行；一条契约合规的 `D|invalidate|all`（或覆盖这些脏行的单行/区间）会丢弃它们，下一次异常进入 monitor 失败直至 `UNDI` 死循环（`flush all` 不会）。⇒ 020 接线的既有隐患，与本实现无关；自检向量的 C 段先做一次 `D|flush|all` 再验 `invalidate all`（语义等价、不踩该隐患）。
   **reviewer 订正**：现象已复现（去掉绕行后 `simulate() limit reached`、rc=125），但“monitor 段经 D-cache 拷入且不写回、内存是旧内容”这一机制**未复现**（drop 体 `D|invalidate|all` 与 `I+D invalidate|all` 均 guest rc=0x10 存活）；致命脏状态更可能是交接写入的页表/monitor 数据，具体定位随 020 后续修复任务（`m16-gem5-022`）。
③ 他会话的 `make install-host` writer 自 07:51 仍持 llvm/qemu/bootrom（pid 66104），`run_inst_tiny`/`run_m5_e2e` 需 `DADAO_ALLOW_CONCURRENT=1`；本任务未改 qemu/llvm，二进制未动。
**遗留问题**：① 上条 ①（I 侧不可观测）需裁定：另立任务修 DADAO gem5 的取指可见性，或明确「gem5 不支持自修改代码，I 侧只在 QEMU/chipyard 侧验收」；② 上条 ②（BootROM 脏行）建议并入 020 后续（`cache-model=on` 交接时 flush L1）；③ cfx5 未接 cfx 两轴权限（不进 `kCfxhaMap` ⇒ 无 mode 行可查 `cfx_reg`/`cg_reg_deleg`），与「其余组合一律 `CFXREG`」一并保持 021 前行为；④ 只验功能覆盖，无周期判据（任务书「不做」）。**待裁定**：① 的处置方式。
