# m16-gem5-006: 访存时序（XBar + SimpleMemory）

**模块**：gem5
**项目里程碑**：M16
**依赖**：`m16-gem5-001`（钩子）、`m16-gem5-002`（表）
**可并行分片**：否（同改 `components/gem5/patches/**`；组件单写者）
**预估**：3–4 h
**状态**：已验证

## 目标

让 `ld/st` 的 4–7 拍由真实内存系统承载，并给出 Atomic vs Timing 墙钟比。

## 前置（`m16-gem5-001` 实测发现）

- `TimingSimpleCPU` 走 `ISA::readMem/writeMem`，而 DADAO 侧当前**未实现**（真实 ELF 访存在 Timing 上会 panic）⇒ 本任务须先接通 `src/arch/dadao/isa.cc` 的 `readMem`/`writeMem`（复用 `DummyISA`/`X86ISA` 的 atomic-memory 实现形态），再谈延迟参数。
- 真实 ELF（含访存）在 Timing 上的 `numCycles` 对比，以本任务为准；`001` 只用无访存 guest 证明钩子等价。

## 范围

- `NoncoherentXBar` + `SimpleMemory` 延迟参数化；`configs/dadao/se_timing.py` 新增（**不改** 现有 `se.py`）
- 取指 8-beat 暂按现有 icache 路径，二期再细化

## 待裁定

1. **`readMem/writeMem` 的落点：只能在 `src/arch/dadao/**` 内，且 Timing 的数据访问只能是 functional（不定时）**
   - 事实：gem5 v25.1 **没有 ISA 级 `readMem`**（`src/arch/{generic,dummy,x86}` 均无）；`ExecContext::readMem` 直调 CPU 的
     `BaseSimpleCPU::readMem`（`src/cpu/simple/base.hh` 内 `panic`），任务的「参考 DummyISA/X86ISA atomic-memory 形态」在该版本不存在
     （x86/riscv 的 load 走 `initiateAcc/completeAcc` 两阶段）。⇒ 按任务书「若须动 `src/cpu/simple/**` 就停下写待裁定」，
     **未动 `src/cpu/simple/**`**，改把实现落 `src/arch/dadao/inst.cc` 的内存上下文（`Gem5B1Context`）。
   - 自决：内存上下文在 `system.mem_mode == timing` 时改用 `SETranslatingPortProxy` 功能访问（与 SE 系统调用层、ELF 装载同一条路），
     其余模式原样调 `xc->readMem/writeMem`（Atomic 行为不变）。
   - 后果（须用户知悉）：Timing 下数据访问**正确但不计时**；`NoncoherentXBar`+`SimpleMemory` 的真实时序只作用于**取指**；
     `ld/st` 的 9/10 拍由周期模型（001–005 的钩子）承载，不是内存系统。要在 Timing 上得到真实访存时序，须把执行核改成
     `initiateAcc/completeAcc` 两阶段（DADAO 是 bundle 执行、`execute()` 内同步取数）⇒ 执行模型重构，建议二期立项。
   - 建议：接受本任务的「功能正确 + 模型计拍」口径。

2. **C 类模型取值：用文档自己解出的 D 模型在 N=1 求值（9 拍），不用 §2/§3 的 `4–7`**
   - 实测（WumingTiny，同 inst 相邻 `ip+4` 取差再取 min，方法同 005）：`ld.sb/ub/sw/uw/st/ut/o/t` **全为 9**（max 10）；
     `st.b/w/t/o` **全为 10**（min=max）。宽度无关。
   - 文档 §3 01 的 C 行上界注明「含背压」、窄宽度注明「其余宽度外推」⇒ 不能定一条指令的拍数；而其**实测的** D 行解出
     `per_element=1 / per_beat=8` ⇒ 一次访存 = 1 元素 + 1 beat = 9。故 C 行按同一解出的模型在 N=1 求值（生成器把
     `per_element/per_beat/elem_width` 也发给 C 行；策略 `multiElementCycles(row, 1)`）。**未改文档、未改表值**。
   - 结果：13/13 个 C 宽度与 chipyard 差 ≤1 拍（ld 差 0，st 差 1）。**建议**：`m16-chipyard-001` 回填 C 行为 9/10，并按文档
     §6「差 >2× 登记原因」记 `4–7` 为外推失效。

3. **store 恒比模型多 1 拍（零方差）**：`st.*` 实测 10、模型 9；与 005 的 `stm` +1 同源（写应答多一拍）。模型不加常数
   （禁手抄），差异落在容差 1 拍内且逐行可见（比对表 `[C] st-* -1`）。**建议**：001 一并复核写路径。

4. **functional 数据访问的故障语义与 Atomic 不同**：`SETranslatingPortProxy` 默认 `NextPage`（=系统调用层口径）只对**写**的下一页
   做分配；越界/未映射的**读**在 Timing 上 `panic`（fail loud，不静默错值），Atomic 则产生 guest fault。SE 单核下 `lr/sc` 的保留
   状态仍由 ISA 侧维护，功能路径不参与 gem5 的 LLSC 协议（等价）。**建议**：接受；二期两阶段访存后该差异自然消失。

5. **未做 chipyard 对照的行**：`ld.o rf`（文档归 B4，实测 13）等「单次访存」的 B4 行仍按文档值，未纳入 C 类逐宽度表。
